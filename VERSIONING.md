# Versioning policy

How the agent-board-toolkit is versioned, released, and tagged. Mirrors the agent-webhook-bridge and kanban-board projects' process; see [`feedback-git-workflow`](../.claude/projects/-home-kanban/memory/feedback-git-workflow.md) for the operating rule.

## The core rules

1. **Single source of truth for the version:** the [`VERSION`](VERSION) file at the repo root, containing one semver string and a trailing newline. Consumers read it with `tr -d '\n' < VERSION` (or the release tooling's `version_file`/`version_regex` in [`.release-pr.json`](.release-pr.json)). **One guarded restatement exists:** a `bin/` file that answers `--tool-version` embeds the value as a line-initial `ABTK_TOOL_VERSION='<version>'`, because a copied file has no `VERSION` beside it to read. [`tests/tool-version-stamp-selftest.sh`](tests/tool-version-stamp-selftest.sh) reds any PR where a stamp, or a `--tool-version` answer, differs from `VERSION`.
2. **Version bumps happen on `dev` in a dedicated release PR**, NOT on each feature PR. The bump + CHANGELOG entry is the release act.
3. **Every release tag `v<version>` corresponds to a [`docs/CHANGELOG.md`](docs/CHANGELOG.md) entry** describing the bundle of merged PRs in the release.
4. **Tags are created on `main`, not `dev`, by CI.** After the user merges the release PR (`dev` → `main`), the [`auto-tag-version.yml`](.github/workflows/auto-tag-version.yml) workflow fires on the push to `main`, reads `VERSION`, and tags the merge commit `v<VERSION>` (the tag SHA equals the merge commit's SHA). It is **tag-only** — unlike agent-webhook-bridge's, it does not yet publish a GitHub Release from the CHANGELOG. **Claude does not hand-tag** — the workflow owns it (idempotent; a tag already at a *different* SHA fails loud, meaning the release PR forgot to bump `VERSION`).
5. **Back-merge `main` → `dev` after every release** (`sync/main-to-dev-post-v<version>`) so the branches don't diverge. The user's confirmation that the release PR merged to `main` IS the authorization for the back-merge sync PR — it is opened autonomously and auto-merged on green with a **merge commit** (never squashed — squashing a back-merge breaks the next release PR's diff).

## Branching model

Two long-lived branches: **`main`** (releases only) and **`dev`** (integration). All feature work branches off `dev` and PRs back to `dev`. Only the user merges to `main` (release PRs). Same shape as agent-webhook-bridge and kanban-board, adopted wholesale.

## Bump sizing

The toolkit is pre-1.0. The effective cadence — matching the actual tag history (e.g. v0.8.0 feature → v0.8.1 fix) — is:

- **Patch** (`x.y.Z+1`) — bug fixes, refactors, docs, internal-only changes, no new user-visible surface **and no acceptance narrowing** (below).
- **Minor** (`x.Y+1.0`) — new user-visible additions (a new `bin/` tool, a new flag, a new capability) — **and every acceptance narrowing** (below), whether or not the release adds anything.
- **Major** (`X+1.0.0`) — reserved for post-1.0 breaking changes to the public CLI/flag surface.

When a release mixes a feature with fixes, lean toward minor; a release that is only fixes/refactors/docs is a patch. When in doubt, state the reasoning in the release PR.

### An acceptance narrowing takes a MINOR, and the test is what the input did BEFORE (card#9956)

**A release in which an input that previously SUCCEEDED now fails takes a minor at minimum — whatever else is or is not in it.** Until card#9956 the three buckets above had no home for that change: it adds no surface, so the minor bucket's test answers no; major is reserved for post-1.0, so that bucket is closed; and it landed in **patch by elimination** — the one bump that tells a vendoring consumer their working caller is safe. Every such bump was correct under the rule as written. The rule is what had no bucket.

**The test — one question per refused input, answered from measurement.** *What did that exact input do before this change?*

- **It completed** — `rc 0`, and the effect it asked for happened: a value was stored, a report printed, a step went green. ⇒ **acceptance narrowing, minor.** This holds where the old result was WRONG, which is the case that feels like an exception and is not: the caller's script exited 0 and now exits non-zero, and *"the old answer was wrong anyway"* is the argument that makes every break sound like a fix.
- **It already failed** — non-zero then, or an error one layer down that the caller was already receiving. ⇒ **not a narrowing for sizing; patch-eligible.** The change moves where and how legibly it fails, not whether. v0.32.0 is the worked case: `run-coverage-check --repo owner/name.git` was accepted by a shape regex, interpolated into a request path and **answered 404 by GitHub**, so refusing it at the flag regresses nothing. **Taking this branch obliges you to state the old exit status in the release notes** — it is a claim about measured behaviour, and it is the branch that can be taken by impression.

**The surface is everything a consumer can reach from outside this tree**, not the CLI alone: arguments and flags, config keys read from `.release-pr.json` and `~/.kanban-*-board.env`, the composite actions' inputs (`promote/`, `release-artifacts/`, `release-tag-check/`), environment variables, and the symbols of `bin/_kb-board-lib.sh` — a vendored file, so its predicates are somebody's call site (v0.30.0's `kb_is_uint` leading-zero refusal). **Three shapes ARE narrowings and are covered, so they need not be re-argued each time:** removing a flag, verb or tool; making an optional config key required (v0.32.0's `.promote.source`); and a gate that reds a consumer's CI run that used to go green (v0.28.0's `retired_artifacts` arm).

**What the shipped history shows — this replaces an accident, not a judgement.** Re-derive it rather than trusting this paragraph: `awk '/^## \[/{v=$0} tolower($0)~/narrow|acceptance change/{print v": "NR}' docs/CHANGELOG.md` prints a release heading per hit, and the hits have to be **read** rather than counted — the wording drifts release to release, two of them (v0.26.0, v0.27.0) are the *negative* declaration, and several hits in v0.31.0/v0.33.0 use "narrow" about something else entirely. Read that way, the bump has tracked whether the release ADDED anything, never whether it narrowed anything. v0.24.0 (*"⚠ UPGRADING — four things narrow what the tools accept"*), v0.25.0, v0.29.0, v0.30.0, v0.32.0 and v0.34.0 each carried narrowings and each took a **minor** — for their additions. v0.23.1, v0.30.1 and v0.35.1 each carried narrowings, added nothing, and took a **patch**. v0.23.1 states the mechanism in its own words, reasoning *"Per `VERSIONING.md` § Bump sizing this is a **patch**: every change is a fix … no new `bin/` tool, no new flag, no new capability"* in the paragraph directly above *"⚠ UPGRADING — the CLIs now reject `--flag ""` where they previously accepted it silently."* The same consumer-visible break has therefore shipped under both signals, sorted by something that has nothing to do with it. This rule changes only the second group: it makes the narrowing a floor of its own instead of a passenger.

**Why the minor and not a major — semver does not say what it looks like it says.** [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html) scopes its patch, minor and major clauses (6–8) to `x > 0` / `X > 0`, and its clause 4 reads *"Major version zero (0.y.z) is for initial development. Anything MAY change at any time. The public API SHOULD NOT be considered stable."* Pre-1.0 the spec imposes **no** rule here at all, which is exactly why this repo has to state one rather than cite one. Major is unavailable on its own terms too: the next major from `0.x` is **1.0.0**, which under clause 5 *defines the public API* — shipping that as the side effect of refusing a leading zero would assert a stability commitment nobody made. The minor is the leftmost position that can move pre-1.0, so that is where the narrowing goes. Post-1.0 the same change is a major under clause 8, and this subsection is re-derived at the 1.0 cut rather than carried over.

**Say it on the release, because the bump is read off that sentence.** A release's CHANGELOG summary states its narrowings or states that it has none — v0.26.0 and v0.27.0 already say *"No narrowings this release"* — and that line is both what the bump size is derived from and the only thing a later audit can read. Omission must never be how a release says "nothing narrowed", for the same reason § The §6 upgrade-action rule carries an explicit no-action line.

**Not retroactive.** A released version keeps the number it shipped under; the entries in `docs/UPGRADE.md` §6 are what walk an upgrader across the releases that predate this rule, and the three named above are among them.

**What this rule does NOT cover.** Each of these can break a consumer just as hard. None is sized here, and reading this subsection as covering them is the misreading it is written to prevent.

1. **Output shape at `rc 0`** — what a tool PRINTS while still succeeding: stdout format, a field name, the wording of a message a caller greps. v0.34.0's `release-pr-body` stdout contract change and v0.35.1's removal of clauses from a refusal message are that class, and nothing in this document sizes it.
2. **Behaviour changes where the input is still accepted** — a default that moves, a write that writes less, an action that stops acting until it is armed (`hooks/post-checkout`'s opt-in). Nothing fails, so the test above answers "not a narrowing" — correctly, and that class is open.
3. **Post-1.0**, per the clause-8 note above.
4. **Whether the narrowing should ship at all.** Sizing is not approval — several of the narrowings above record their own in the changelog (*asked and granted*, *operator-approved*), and this subsection does not stand in for that gate.
5. **The `[Unreleased]` and §6 obligations**, which are owed identically at every bump size and are owned by the two sections below.

**It is a floor, never a ceiling.** It cannot lower a bump, and it does not make a release that also adds surface anything other than the minor it already was.

## The `[Unreleased]` entry rule — every card-carrying PR, not the release

**A PR whose title carries a `card#<id>` token adds a line-initial `- **card#<id>** — …` bullet to `[Unreleased]` in [`docs/CHANGELOG.md`](docs/CHANGELOG.md), in the same PR.** The release (step 4 below) *collects* those bullets; it does not author them. A PR with no `card#` token (a `chore(deps)` bump, a `docs(orientation)` sync) owes nothing.

**One bullet is the floor, not the ceiling — a card whose change spans two Keep-a-Changelog kinds files one bullet per kind (card#10176).** A PR that adds a feature *and* narrows what an existing input accepts owes a `### Added` bullet and a `### Changed` one, because the heading is a claim about the **kind** of change and a reader scanning `### Changed` for what an upgrade will break does not read `### Added`. Folding a ⚠ BREAKING note into a feature bullet to keep the count at one is the wrong trade. What the gate forbids is two bullets for one card from one PR **under the same heading** — that is the superseded-wording shape (`_stale_dupes` in the selftest owns the predicate and the residuals it buys; until card#10176 it counted bullets per card and reported the legitimate split as a duplicate).

**Line-initial is the rule, not "the file mentions the card"** — a mention can be prose that misinforms. `docs/CHANGELOG.md` once carried *"card#5374 proposes the selftest…"* inside a different card's entry, written before card#5374 shipped it, so a release cut from that file told the reader the gate was proposed rather than delivered. A PR that folds two cards owes **two** bullets; one bullet naming both discharges only the card it leads with.

This is gated, not conventional: [`tests/changelog-card-entry-selftest.sh`](tests/changelog-card-entry-selftest.sh) (its own [`changelog-card-entry.yml`](.github/workflows/changelog-card-entry.yml) workflow, which subscribes `edited` so a **title edit** re-runs it) derives obligations from the commit subjects since the last release tag **plus the PR title** — under squash-merge the title *is* the coming subject, so the check fires before the merge rather than reddening `dev` after it.

**On a squash-merged PR the duplicate leg reads the diff your PR will LAND, not the commits it is made of (card#10338).** A squash erases a branch's internal removals, so reworking your own `[Unreleased]` wording in a follow-up commit used to make the pre-merge check *weaker* than the post-merge one: the branch passed and `dev` went red on the squash (measured on #388). On such a run the leg now diffs the base tip against the merge commit — the squashed commit's own diff — so a green PR cannot red `dev` on merge. **A consequence worth knowing before you push:** rewording a bullet you filed earlier on the same branch no longer buys you a second bullet for that card under the same heading; if the change genuinely spans two kinds, file it under two headings (above), which is what the gate blesses.

**⛔ That basis applies to squash-merged PRs ONLY, and the gate derives which those are rather than being told (card#10338).** A release PR and a back-merge sync PR are merge-commits (§ Anti-patterns below), so their commits land individually and the diff-the-whole-thing basis would fold every PR in the release into one group — reddening correct, already-shipped history: replaying all 44 release merges in this repo's history through it reddens #295 (card#6645 and card#7038, two entries this convention explicitly blesses) and #308 (card#7536). `_squash_ends` in the selftest refuses on any pull request whose delta would cover commits that are already released, or that already carry a `(#NNN)` of their own — the two properties that are false exactly on those classes — and the run prints which basis answered. **If you are looking at this because a release PR went red on `Changelog card entry`, the delta basis is not the cause: check the run's own output, which names the basis it used.** Until card#5767 the rule was enforced by nothing and written down nowhere, and 3 of the 24 cards merged since v0.23.1 had no entry.

**The section is part of the rule, and is now part of the gate too (card#7293).** A discharging bullet must sit *inside* the unreleased region — the gate reads from `## [Unreleased]` down to the last released version's header — so a bullet parked in the preamble above the `# Changelog` H1 discharges nothing and reds. Until card#7293 the region had no floor and one such bullet passed.

**A branch cut before a release fold gets a different MESSAGE, not a different verdict (card#8442).** The merge carries such a branch's `[Unreleased]` bullet under the folded `## [X.Y.Z]` heading, so the gate reds correctly — and where it can *assert* that the heading was cut while the branch was open it names the move ("move it back to `[Unreleased]`") instead of reporting the entry missing. **Do not answer that red by filing a second bullet**; that is how one change ends up with two wordings. `_prefold_heading` in the selftest owns the predicate and the residuals it buys — nothing here restates them.

**The floor is the literal `## [Unreleased]`, which makes it a check on step 4 below as well.** Step 4 retitles the accumulated block as `## [X.Y.Z]` *and opens a fresh, empty `## [Unreleased]` above it*, so on a correct release PR the region runs `[Unreleased]` → `[X.Y.Z]` → the previous version's header and every bullet in the retitled section still discharges — measured at v0.29.0, not assumed: of the 42 `v*` tags then, 31 carried a `docs/CHANGELOG.md` and 29 of those had `## [Unreleased]` as their first section header (only the pre-rule v0.23.0/v0.23.1 did not). A release PR that retitles without opening the fresh header reds **on that PR**, where the omission is. The alternative — floor at whatever the first `## [` header happens to be — would pass that PR, and the cost lands on everyone else: once merged and tagged, the retitled section *is* the stop header, so the region is empty and the gate reds every subsequent PR on `dev`.

## The §6 upgrade-action rule — every release, action or not

**Every release adds an entry to [`docs/UPGRADE.md`](docs/UPGRADE.md) § 6 (Version-specific upgrade actions): either the actions the release requires of an upgrader, or the explicit `- **No upgrade action.**` line. A release PR that moves `VERSION` and does not move that section is incomplete.** The entry is a `### v<version>` heading in ascending order at the end of §6, in the voice of the entries already there, carrying §6's audience tags (`[host]` / `[vendor]` / `[release-CI]`).

This is an obligation because the alternative already failed twice. §6 tells the reader to *"find your installed version and walk forward from the next entry"*, so a release with no entry is indistinguishable from a release that required nothing — and that silence is what an upgrader acts on. It went stale first at v0.9.0–v0.13.0 (repaired by #104 in v0.15.0) and again at v0.15.0–v0.27.0, both times because writing the entry depended on someone remembering to, at exactly the moment the release-PR checklist did not mention it. Hence the no-action line: **omission must never be the way a release says "nothing to do"**, because it is also the way a release says nothing at all.

**What counts as an action** — anything an upgrader must *do* or knowingly accept: set or move a config key, add a file, re-run the `PATH` symlink loop (a release that ADDS a bin always owes this) or `install-board-hooks`, re-vendor a specific tool for correctness, deploy in a particular order against a server-side change, or absorb a narrowed input surface / changed default. A release whose whole content is internal (a test-only guard, a refactor with byte-identical behavior, a docs sync) owes the no-action line and a sentence saying what it was.

**It is gated, not conventional.** `docs/UPGRADE.md` is a member of [`.release-pr.json`](.release-pr.json)'s `artifacts` array, so [`release-artifacts-gate.yml`](.github/workflows/release-artifacts-gate.yml) reds a release PR whose changes do not include it. Know the strength of that gate: the member takes `release-artifacts-check`'s **content-mention** arm — it asserts the file moved and that the version being shipped appears somewhere in it, *not* that the §6 heading is well-formed or that the entry says anything true. It closes the "forgot entirely" failure, which is the one that has actually happened; the content is still on the author.

## Release flow

Hybrid policy: ask before opening every PR; auto-merge dev-targeted PRs on green; only the user merges to `main`.

1. **Pick the next version** per the bump-sizing rule above (`tr -d '\n' < VERSION` for the current one).
2. **Feature branch off `dev`:** `release/v<version>`.
3. **Bump `VERSION`** to the new semver, **and re-stamp every `bin/` file carrying `ABTK_TOOL_VERSION`** in the same commit — the set is derived, not listed: `command grep -l '^ABTK_TOOL_VERSION=' bin/*`. For each file it prints, `sed -i "s/^ABTK_TOOL_VERSION=.*/ABTK_TOOL_VERSION='<version>'/" <file>`. Skipping this reds `tool-version-stamp-selftest` on the release PR (rule 1).
4. **Update [`docs/CHANGELOG.md`](docs/CHANGELOG.md):** retitle the accumulated `## [Unreleased]` block as `## [X.Y.Z] - YYYY-MM-DD` and open a fresh, empty `## [Unreleased]` above it — **both halves, or the changelog-entry gate reds this PR** (§ The `[Unreleased]` entry rule above: that header is the scanned region's floor). The bullets are already there — each landed with its own PR (see § The `[Unreleased]` entry rule above); this step collects them, and authoring one here means a PR shipped without its entry. Keep the Keep-a-Changelog headers; add only what is genuinely release-level (an upgrade note, a bundling summary). **The same release's upgrade note has a second, consumer-facing home that this PR must also move — `docs/UPGRADE.md` §6, as a full entry or the explicit no-action line (see § The §6 upgrade-action rule above).**
5. **Add a `CLAUDE.md § Recent releases` row** at the top of the table, and **trim the oldest row back to 10**. The table is the ergonomic snapshot and is always truncated to its stated cap; `docs/CHANGELOG.md` (step 4) is the canonical record and is never truncated, so a trimmed row is still fully documented there.
6. **ASK the user** before opening the release PR.
7. Open the release PR `release/v<version>` → **`main`** with full release notes. **CRITICAL: the PR head must be the `release/v<version>` branch, NOT `dev` directly** — a `dev`-headed PR merged with auto-delete-head-branches enabled deletes `dev`.

    **Run the card-coverage check over the release range as part of preparing the body.** With `KANBAN_WRITEBACK_TOKEN`, `KANBAN_API_BASE` and `KANBAN_EXPECTED_HOST` set (`docs/INSTALL.md` §4 — the committed `api_base` is a placeholder, so the tool refuses without the first and the last), `promote-released-cards --dry-run` names every shipped ref that has no tracking card — and, on a repo-qualified board, separately names every ref whose card **exists but carries no by-ref source**, which wants a stamp rather than a new card (`docs/INSTALL.md` §4, the `promote.source` box) — while fixing it is still cheap — otherwise the gap first surfaces as a red post-merge promote run needing board surgery. `release-pr-body` runs it for you and prints the verdict on **stderr** as `release-pr-body: card coverage:` lines — never in the body — **only when its preconditions hold** (the `CARD COVERAGE PRECONDITIONS` block above `card_coverage_report()` in `bin/release-pr-body` is the one statement of when that is), so a run printing **no** coverage line means the check **did not run** — not that it passed. The obligation lives here for the same reason as the merge-method rule in the next step: a body section whose whole content is "this was not checked here" is process narration, and it was struck by hand from a release PR that grew one — which does not hold, because the next release re-emits it.

8. Wait for ALL CI checks (if the repo has CI) to complete + pass. **The mechanical half of this step is the `ci-gate` job in [`ci.yml`](.github/workflows/ci.yml), which depends on every other job in that file and reports even when one of them fails.** It is **not** the whole required set: `needs:` cannot cross a workflow file, so PR-triggered gates living in sibling workflows are not covered by it and are required by name themselves — that array is where they are enumerated. [`tests/ci-gate-selftest.sh`](tests/ci-gate-selftest.sh) is the one place that set is declared, and it holds the declaration level with the workflow directory — it is not restated here or in `ci.yml`. Whether the repository's branch protection **actually** carries those contexts is a settings fact no file in this tree can assert, so **read it rather than a sentence** — that selftest carries the runnable one-liner beside the declaration, over `branches/<branch>/protection`, for both `main` and `dev`. **Claude does NOT `gh pr merge` a `main`-targeted PR** regardless of CI state. **Merge it with "Create a merge commit", never "Squash and merge"** — a squashed release loses the bundled commits' identity and breaks the next release PR's diff, and GitHub's merge button is **sticky**, so after any routine squash-merged `dev` PR it will be pre-set to the wrong method. This rule lives here, not in the release PR's body: a PR body is the wrong home for a process warning that applies to every release (`coord:release-pr` § PR body — write it like a senior dev).
9. **After the user merges to `main` and confirms:** that confirmation authorizes the back-merge sync PR — no separate ask. (On the main-push, `auto-tag-version.yml` mints the `v<VERSION>` tag and `release-promote-cards.yml` moves board-12 tracking cards to Released. Both are automatic and Claude does not hand-tag or hand-promote — but they are **two independent workflow runs sharing one trigger, not one coupled step**, and they can diverge: promote starts at the same moment as auto-tag, so it reaches the board *before* the tag exists on every release, and on v0.28.0 the tag never arrived at all — auto-tag's push was refused with a 403 — while promote reported success and stamped the cards Released against a tag that did not exist. Since card#6579 promote **waits for the tag and refuses to stamp Released if it never appears**, so that divergence is now a red run instead of a false board state. A red promote run therefore means *check whether the tag exists*, not *the board write failed*.)
10. Open the back-merge sync PR `sync/main-to-dev-post-v<version>` → `dev`; auto-merge on green with a **merge commit**.
11. **DEPLOY the release to the host that actually runs the tools. A tag is not a deploy** (the sibling of agent-webhook-bridge's release≠deploy rule — this repo lacked the step entirely until v0.15.0 shipped and the on-PATH runtime silently stayed at v0.14.0):
    ```bash
    # <pinned-runtime> is a SECOND checkout kept deliberately DETACHED at a release tag.
    # Do not run this against a clone that tracks main (docs/INSTALL.md §1 Option A) — and do
    # not relay this line as an upgrade recipe to anyone who has one: `checkout` would convert
    # their self-advancing install into a pin. That topology upgrades with `git pull --ff-only`
    # (docs/UPGRADE.md §2), which lands the identical bits.
    git -C <pinned-runtime> fetch --tags && git -C <pinned-runtime> checkout "v<version>"
    for t in <pinned-runtime>/bin/*; do [ -f "$t" ] || { echo "skipped (not a regular file): $t" >&2; continue; }; ln -sfn "$t" ~/.local/bin/"$(basename "$t")"; done   # REQUIRED
    hash -r && agent-board-toolkit-runtime-check                                            # must print `ok — … @ v<version>`
    ```
    **This is the ONE sanctioned second copy of `docs/INSTALL.md` §2's `PATH` symlink loop** — it links a *different* source checkout (the release pin, not `~/agent-board-toolkit`), so it cannot be a pointer to §2 without a substitution the reader has to make by hand in a deploy step. The `[ -f "$t" ]` guard and the `-n` are not decoration: `ln -sf` **follows** a symlink-to-directory instead of replacing it, so an unguarded loop links a directory in `bin/` onto `PATH` and then, on the next run, plants a symlink cycle inside the pinned checkout — silently, at rc 0. §2 owns the reasoning; `tests/path-link-recipe-selftest.sh` executes both copies against a fixture, so the two cannot drift apart and a *third* copy reds. **Correcting this line means correcting §2 in the same change.**

    **Re-running the symlink loop is not optional even on a symlink install:** a symlink tracks its target's *content*, not the *set* of tools — a release that ADDS a bin (v0.12.0 `adopt-to-dl`, v0.15.0 `agent-board-toolkit-runtime-check`) never appears on `PATH` without it. Then **exercise one real command** (`kbcard show --task <id>`), because a green tag is not a working install.
    > **⚠ A release that adds a CHECK must force that check's first run by hand, here.** A guard shipped *in* the artifact it guards cannot bootstrap: v0.15.0's `agent-board-toolkit-runtime-check` exists to catch a stale pin, and a stale pin is exactly what stops it from existing on `PATH` — it was `command not found` on the maintainer's own host while the condition it detects was live. From the next release on, `board-snapshot` surfaces it at every SessionStart (folded to **stdout** — a stderr-only warning is discarded by the hook and the guard would be silently unread).
12. **Measure the framework's mirror against the tag you just cut** (card#9939). README declares the agent-board-framework's `templates/release/` copies of its release bins mirrors synced at toolkit tags; this repo is the declaring end, so it owns the check. It is run here and not in CI because the framework repo is private and CI holds no credential for it; the check's header states what one run can and cannot see.

    **⚠ RUN IT ONCE PER ARTIFACT — a verdict about one is not a verdict about the other.** The check reads exactly ONE framework artifact per invocation, and a clone's branch and an installed plugin are different bytes. After `git fetch --tags` here, run **both**:
    ```bash
    tests/framework-mirror-check.sh --ref origin/dev <framework-clone>   # the repo the re-sync lands in
    tests/framework-mirror-check.sh ~/.claude/plugins/cache/agent-board-framework/coord/<version>
    ```
    The second is **not optional**: the plugin cache is the copy a seat actually EXECUTES, and it lags the clone by a plugin release. A clean clone beside a stale plugin is the normal state mid-cycle, and only the second run can say so.

    **Reading the result.** Right after a release the check is **expected to red on any file the release changed** — that red is the sync request: relay it to the framework's owner as a re-sync **from the tag**, naming the files and the tag, never as a patch to their copy. A red on a file this release did NOT change means the mirror had already drifted. `UNMEASURED` (rc 3) is neither: it means a file the toolkit declares travels is missing from the mirror, or its bytes could not be read — chase that before reading anything else in the run, because nothing about that file was measured.

    **⚠ ONE STANDING EXPECTED RED, AND IT IS NOT DRIFT.** The far-end `promote-released-cards` carries `MIRROR NOTE` blocks marking deliberate framework-local content — at this writing, a fix ahead of the toolkit authority and a comment block with no toolkit counterpart. The check compares BYTES, so that file reports `DIVERGED` **through every re-sync** until those notes are upstreamed as toolkit PRs. Before relaying a `DIVERGED` row as a sync request, open the far-end file and look for `MIRROR NOTE`: a note that names the divergence is a framework-local fix owed **upstream to this repo** (README: framework-side needs land as toolkit PRs, never as a fork of the mirror), and relaying "re-sync from the tag" for it would ask its owner to delete work. No note ⇒ it is ordinary drift and the re-sync is the right ask. **Derive it, do not trust this paragraph's description of the far end:** `command grep -n 'MIRROR NOTE' <framework-clone>/plugins/coord/templates/release/*` prints the live set, which is the only thing that can have moved since this line was written.

The [`.release-pr.json`](.release-pr.json) config drives the toolkit's own `bin/release-pr-body` generator (deterministic bundled-work list + artifact checklist from git truth; **both ends of the range are resolved by fetching from `origin`** — the baseline from `origin/main`, because the local `main` ref is a release behind by design under this flow (it is never checked out, steps 2–10) and would misreport already-shipped PRs as new; and the head from `origin/dev`, because the local `dev` ref lags every merge that lands after the release worktree is cut, and a short range silently drops PRs from the bundled table **and** from the `shipped-cards` manifest footer. No network → the tool fails loud, and each leg carries its own explicit override, `--base <tag>` and `--head <ref>`, each skipping only its own leg's fetch — so an offline run passes **both**, and an explicit ref that does not resolve in the checkout is refused at rc 2 rather than silently yielding an empty bundle, since skipping the fetch is exactly why nothing else would notice) and `bin/promote-released-cards` — invoked by [`release-promote-cards.yml`](.github/workflows/release-promote-cards.yml) on the main-push (via the local `./promote` composite action) to move board-12 tracking cards (matched by their `dl_number`/`pr_number` against the shipped git range) to the released stage.

Its **`artifacts` array is the must-move-together release set** — steps 3, 4 and 5 above plus the §6 upgrade-action entry (§ The §6 upgrade-action rule), one entry each — and it is **asserted**, not merely printed: [`release-artifacts-gate.yml`](.github/workflows/release-artifacts-gate.yml) runs `bin/release-artifacts-check` on every PR, and on a release PR — which it classifies from the `VERSION` file at the **fork point** and at head, by the rule [`docs/INSTALL.md`](docs/INSTALL.md) §6c owns — the check **goes red** if any declared member is absent from the PR's own changes, no longer exists at head, or does not carry the version being shipped. A red check does not by itself prevent a merge — step 8 below ("wait for ALL CI checks to complete + pass") is what makes it binding, and the `release-artifacts` job being one of `main`'s required status **contexts** is what makes it binding mechanically (it is declared as such in [`tests/ci-gate-selftest.sh`](tests/ci-gate-selftest.sh)'s `REQUIRE_BESIDE_CI_GATE`, whose header carries the command that re-prints what protection live answers — a vendoring repo has to set it on its own branches). The range is `merge-base(base, head)..head` rather than base's tip, which is load-bearing on both halves: a commit landing on `main` after the release branch was cut would otherwise make an untouched member look moved, and a version bump arriving on the base branch would make a real release PR read as "version unchanged" and skip the gate entirely. Before this the array was a `- [ ]` checklist in the generated body and nothing else, so a forgotten CHANGELOG heading or `CLAUDE.md` row shipped in silence. A **non**-release PR asserts no member — but it is not exempt from the check: the declared set is read from the **fork point** and compared on every PR class, so an ordinary PR that drops an `artifacts` entry without acknowledging it in `retired_artifacts` goes red too (the removal and its acknowledgement are wanted in the same PR). [`docs/INSTALL.md`](docs/INSTALL.md) §6c owns the classification rule and what the check reads; the post-merge `auto-tag-version.yml` stays fail-soft by design, because at that point the fix is a retag rather than a commit — fail-soft as to the MERGE, which is already in; it is no longer silent DOWNSTREAM, since [`release-promote-cards.yml`](.github/workflows/release-promote-cards.yml) now refuses to report the release as shipped while the tag is missing (card#6579).

## Anti-patterns

- **Don't tag a release before doc-sync.** The CHANGELOG entry lands in the same release PR as the version bump.
- **Don't bump the version on a regular feature PR.** Version bumps belong to release events.
- **Don't reuse a tag.** Tags are immutable; if a release is broken, ship `vX.Y.Z+1`.
- **Don't tag `dev`.** Only `main` gets tags.
- **Don't PR `dev` directly to `main`.** Use a disposable `release/v<version>` branch as the PR head (see rule 7).
- **Don't squash a release PR or a back-merge sync PR** — either one breaks the next release PR's diff. Both use a merge commit; only `dev`-targeted PRs are squashed.
