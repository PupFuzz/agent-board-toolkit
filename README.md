# agent-board-toolkit

Single source of truth for kanban-dev's **bash** board tooling — the CLI + helpers that drive a kanban board from the agent host and from release CI. One versioned copy, consumed by the agent host (via symlink) and by product repos that run a tool in CI — GitHub-Actions repos via the SHA-pinned [`promote/`](promote/action.yml) composite action, others via a drift-checked vendor.

> **Scope.** This is **kanban-dev's** within-runtime code-share (Task-tracking standard §8): it serves the agent host + the `kanbanboard` and `agent-webhook-bridge` repos. The PM projects' (sola/aimla) *primary* board-ops sharing is Python (`coord.kanban_common`) — but because this is portable `bash` + `curl` + `jq`, a PM project **may also vendor these tools directly** (vendor + drift-check), routing any shared-board need through FRs to this repo, **never a silent fork**. (§8 amended 2026-06-19 at AIMLA PM's request: the original wording *excluded* PM projects, on a cross-runtime-ceiling assumption that doesn't hold for the bash layer.) The canonical three-way shared surface is still the **contract** — the by-ref shape, the `DL-NNN` token, `dl_number`, the writeback outcomes — and the **v3 API substrate**, not this code.

| `bin/kbcard` | board CRUD CLI: `create-card` / `move` / `patch` (including `move --stamp-owner` — the seat owner tag `owner:<project>/<seat>`, stamped on card start and removed by a terminal move, see [§ The seat owner tag](#the-seat-owner-tag--ownerprojectseat); `move --card-start` — the opt-in **work-start guard**: a **pinned** card, or one that is not in Backlog / Prioritized, is **refused rather than moved**, so an automated starter cannot pull a Shipped / Released / Won't-Do card back to In Progress (the predicate is the toolkit lib's, shared with `bin/board-card-start`); `--assign <seat>` / `--unassign` — the board's native `assigned_user_id`, the kanban **assignee** and not the seat owner, with a **refusal** rather than an overwrite when another user already holds the card, see [§ `kbcard patch --assign`](#kbcard-patch---assign--which-seat-is-already-working-this-card); | `bin/promote-released-cards` | move a release's shipped cards to the "released" stage, then remove their seat owner tags (run by release CI; see [§ The seat owner tag](#the-seat-owner-tag--ownerprojectseat)). Each move is reported from a **read-back of the card**, never from the `PATCH`'s status (the rule it adopted is the read-back bullet below). A matched card carrying the **`program`** tag is a PARENT naming several legs, so one release's ref may not take it terminal: it is **withheld** — named, counted in its own summary segment, never moved — and the run continues; a withheld card never turns a run that exited 0 non-zero. **Both that predicate and its exit ladder are published by the tool and restated nowhere: `promote-released-cards --help`, § THE PROGRAM-PARENT WITHHOLD and § EXIT CODES** |
| `bin/card-completeness` | answer, per card, whether its work is COMPLETE as of a release head in one repo — the oracle `promote-released-cards --require-complete` refuses a terminal move on. A card is INCOMPLETE while a pull request whose HEAD BRANCH carries its token is OPEN, or was MERGED into the integration branch by a commit the release head does not contain; COMPLETE otherwise; **UNMEASURED — never COMPLETE — if either population cannot be read**. It exists because a card's `pr_number` holds ONE pull request, so a card whose work spans several reaches its shipped stage on whichever part merged first and is then eligible for the terminal stage nobody re-reads. ⛔ **Read its header before turning the gate on**: the predicate, every alternative it rejects (the board's own state, branch-tip reachability under squash-merge, the PR body as a surface) and everything it cannot see — including a part whose branch names the card only by a DL — are stated there and nowhere else. It reads GitHub with `$GITHUB_TOKEN`/`$GH_TOKEN` (`pull-requests: read` + `contents: read`), is vendored standalone beside the mover, and is consulted only under that flag |
| `promote/action.yml` | SHA-pinned composite-action wrapper around `bin/promote-released-cards` for GitHub-Actions consumers (INSTALL.md §6a) |
| `bin/release-pr-body` | generate the release-PR body/scaffold from repo config — or, with `--tag`, print just the git tag name `.release-pr.json`'s `tag_format` maps a version to (the query mode `release-tag-check` uses so the mapping has one implementation; it returns before any fetch, so it answers with the remote unreachable). **stdout is the release PR body and only the body** — the scope line, `## Highlights`, `## Bundled`, `## Release artifacts` (when `artifacts` is configured) and the `release-manifest` footers. The builder diagnostics are prefixed **stderr** lines (`release-pr-body: correlation gap:` / `release-pr-body: card coverage:`), and a successful body run ends stderr with one machine-readable **`announce:begin` … `announce:end`** block for a release tool to lift instead of re-deriving. What the block carries, and its stability rules, are declared in the tool's usage header (`release-pr-body --help`) and nowhere else; `tests/release-pr-body-selftest.sh` holds that declaration equal to what the tool emits. Never merge stderr into the body file (`2>&1`), and never close it (`2>&-`): a closed stderr fails the run at rc 1. **`--tool-version` prints the toolkit version the file itself is** (`--version` stays the RELEASE version, an input). It is stamped into the file, so a copy with no checkout beside it answers too, from any directory, with no config. The stamp names a release: a copy taken from `dev` between releases reports the last one, and `git hash-object <copy>` fed to `git log --all --find-object=<blob>` in a toolkit checkout finds the exact commits. **Bootstrap bound:** only a copy new enough to carry the flag can answer. Every older copy refuses it as `unknown arg '--tool-version'` at rc 2, which means "older than the flag", never a version. **This copy is authoritative** — same as `promote-released-cards`: the toolkit owns both release bins (tests + release discipline live here); the agent-board-framework's `templates/release/` copies are mirrors synced at toolkit tags. Framework-side needs land as toolkit PRs first, never as a fork of the mirror. **That lockstep is a declaration, and `tests/framework-mirror-check.sh` is its check** — it reds when a mirror is not byte-identical to the newest toolkit tag's copy and names the one framework artifact it read (a framework clone or an installed plugin, which can differ). It cannot run in this repo's CI, because the framework repo is private; `VERSIONING.md`'s release flow runs it |
| `bin/release-artifacts-check` | assert every member of `.release-pr.json`'s `artifacts` array actually moved in a release PR — present in the PR's own changes, still exists at head, and carries the version being shipped. The `artifacts` array's other consumer, `release-pr-body`, only **prints** it as a checklist; this one **fails the check run** (it blocks a merge only once you add its job as a required status check — see `VERSIONING.md` § Release flow step 8). The range is `merge-base(base, head)..head`, never base's tip, so base-branch drift after the fork can neither fake a "moved" member nor hide a release. The declared set itself is read from the **fork point**, which the PR cannot edit, and head may only widen it — so it runs on every PR, and a **non**-release one asserts no member but is still refused if it drops a declared entry without acknowledging it in `retired_artifacts`. It also guards the three CORRELATION keys (`promote.source`, `ref_token_regex`, `card_token_regex`): a config declaring a `promote` block must declare all three or name the missing one in `unset_correlation_keys`, since a missing token key fails **silently** downstream (`docs/INSTALL.md` §4, the `unset_correlation_keys` note, shows what that looks like). `docs/INSTALL.md` §6c owns the classification rule and what the check reads |
| `bin/release-tag-check` | post-merge, refuse to report a release as shipped until its tag actually exists. `auto-tag-version.yml` and `release-promote-cards.yml` both fire on `push: main` as independent runs with no `needs:` between them, so the promote side wins the race on **every** release and used to stamp cards "Released to main" before the tag was created — and on one release the tag never arrived at all (the tag push took a 403) while promote still reported success. This **waits** for the tag rather than refusing on sight (an immediate refusal would red every release), then **fails loudly** if it never appears, or if it appears at a different commit. A remote it could not READ is a third outcome, never scored as an absent tag: each poll is bounded, `git ls-remote`'s own error is kept, and the refusal at the bound says the tag is UNMEASURED rather than blaming the tagging workflow. A non-release push asserts nothing: the release classification is delegated to `release-artifacts-check --classify-only`, so there is one definition of "this range is a release", not two. WHICH tag it waits for is delegated the same way — to `release-pr-body --tag`, the one reader of `.release-pr.json`'s `tag_format` — so a repo on a non-`v` scheme is asserted against the tag that scheme actually produces (it hardcoded `v<version>` until card#7203, which made it wait out its whole bound and refuse **every** release for such a repo). It reads refs only — it needs no write permission and widens no token |
| `release-artifacts/action.yml` | SHA-pinned composite-action wrapper around `bin/release-artifacts-check` for GitHub-Actions consumers (INSTALL.md §6c) |
| `release-tag-check/action.yml` | SHA-pinned composite-action wrapper around `bin/release-tag-check` for GitHub-Actions consumers (INSTALL.md §6d). Wire it as a step BEFORE whatever reports the release — a gate placed after the thing it guards guards nothing |
| `bin/board-snapshot` | session-start board snapshot |
| `bin/board-stats` | per-board **stock + flow** report over one board (`--board <name>`) or every board in the roster (`--all`, the default), as text or `--format json`. The two sections come from two different surfaces on purpose: **stock** (per-column card counts, plus the oldest card's age in the pullable columns) is a *state* question and is read from the card snapshot; **flow** over a `--since 24h`/`7d`/past-ISO window (cards created, every stage-changing `from -> to` transition counted and split human/service, swimlane-only moves counted separately as **same-stage moves** rather than mistaken for transitions, resolutions listed **per destination stage**, and each terminal→non-terminal move as its own **wash** row) is a *rate* question and is read from the board **changelog** event log — never from a card's `last_stage_move`, which is a snapshot field and therefore loses a multi-hop card's intermediate transitions, hides a resolution that was later washed, and reports a release batch as fresh resolutions. Terminal/pullable stages are **derived from the board's own `lane_type`** (`done` / `backlog_inventory`), with the board env's `KB_STAGE_*` ids as a per-key override, and a class that ends up empty is reported rather than rendered as zeros. A window the log cannot fill is never reported as a complete one, on either of the two routes it can fail by: a **stop** that bounds it (the page cap, or a changelog that does not reach back to the cutoff) is flagged truncated and carries the oldest timestamp the log holds, while a page the tool could not **read** — no response, a non-2xx, or a 2xx carrying no event array — ends the walk and is named on the board's own ⚠ line as an incomplete window whose counts are a floor. **A floor says so ON THE NUMBER, not only on the line above it:** a partial card read prefixes every stock count and queue age with `≥`, and a partly-read window does the same for every flow count, so a value cannot be read as a total even quoted out of the ⚠ that qualifies it — and the two states are separate, so one section can be floored while the other is not. A genuinely empty log is neither: zero events is what it holds. Read-only; fail-soft per board (an unreadable board is reported, never omitted, and the report says it is partial) |
| `bin/board-session-close` | session-close board↔git reconcile — plus a report-only **git-hook dispatch check** (does each local checkout's `post-checkout` still reach `board-card-start`? see [`docs/HOOKS.md`](docs/HOOKS.md#is-the-hook-still-wired--the-dispatch-check)) |
| `bin/board-hooks-check` | **is each toolkit hook LIVE on this seat?** One read-only answer across both delivery mechanisms, per hook: the Claude Code dispatch hook (`hooks/agent-dispatch-card-start`, registered by hand in settings — it reads the user `settings.json`, the project `settings.json` and `settings.local.json`, and the managed `managed-settings.json` for a `PreToolUse` entry whose matcher covers `Agent`; the other settings and hook sources are not read, and every run prints that bound) and, per `<repo-dir>` named, the git hooks (`post-checkout`, `pre-push`) — reporting **WIRED** and **ARMED** as separate facts, because wired-but-unarmed reads as working and moves nothing. Three verdicts, never two: **LIVE**, **NOT-LIVE** (determined — the line names what is missing) and **UNMEASURED** (a settings file it cannot read, a matcher, command or handler field it does not evaluate, a path that is not a checkout), carried on the exit code as `0` / `1` / `4`, `install-board-hooks`' own determined-vs-indeterminate split. The git half calls `board-session-close`'s dispatch-leg reader rather than copying it. It never prints a hook command. Installs, arms and registers nothing — see [`docs/HOOKS.md` § Is each hook live on this seat?](docs/HOOKS.md#is-each-hook-live-on-this-seat--board-hooks-check) |
| `bin/next-dl` | next `DL-NNN` number — **atomically claims** server-side when the board exposes the DL-sequence endpoint (race-free; DL-157), else offline `max+1` over local `## DL-NNN` headers **plus** the board's stamped `dl_number`s, which **refuses** rather than mints if that board read is not whole (card#6631). `--peek` = non-consuming read of that same counter (falls back to `max+1` only when the endpoint is absent). **Every fall-back to the offline scan is announced on stderr, naming WHICH cause fired** (config unresolved / unreachable / `404`-absent / a `2xx` carrying no usable value — one line each, because one generic line hides the difference that decides what an operator does next), and **`--require-counter`** turns the fall-back into a **refusal at rc 4** for a caller that needs an atomic number or none (card#7214). **Two of those causes — *unreachable* and *a `2xx` carrying no usable value* — are a fall-back only on the non-consuming `--peek`; on the atomic CLAIM each is a refusal at rc 1 with nothing minted, because the `POST` may already have spent a number and the offline scan cannot see a spent-but-unstamped one** (card#10230). On the CLAIM route the fall-back is reached **only** on a positive *no number was allocated* declaration from the transport — any other outcome refuses at rc 1, so a code path nobody has written yet fails closed rather than minting a duplicate (card#10230) |
| `bin/board-card-start` | move a feature branch's correlated card to In Progress, then stamp the seat owner tag in a separate write (idempotent, fail-soft; see [§ The seat owner tag](#the-seat-owner-tag--ownerprojectseat)); records the board's verdict on the branch, which its `--lint` (the `pre-push` hook) repeats without a request — see [docs/HOOKS.md § The board verdict leg](docs/HOOKS.md#the-board-verdict-leg-dl-225) |
| `bin/adopt-to-dl` | **pull-into-build adoption seam:** stamp an existing plain card with `dl_number` + a source-qualified placeholder `pr_url` in one atomic write (via `next-dl` + `kbcard patch`), then fail-loud-verify by `by-ref?system=dl&ref=N&source=<repo>`. Refuses to re-mint over an already-adopted card (`--dl N` re-stamps idempotently for a crash-retry), and refuses — before minting — a card whose `pr_number` already names a real PR, which the placeholder stamp would contradict |

| `bin/agent-board-toolkit-runtime-check` | what `agent-board-toolkit-drift-check` is for a vendored copy, but for the **`PATH` install itself**: resolves each on-PATH tool through its symlink chain to the runtime that actually executes, and fails loud on a stale runtime (a pin left behind **or** a clone that never pulled — the remediation it prints branches on which), stale copies, or a mixed-runtime split. | `bin/dependabot-deploy-reconcile` | **does the fix a CLOSED Dependabot alert claims actually exist in what is deployed and running?** An alert closes when its fix reaches the default branch; production serves something cut by a separate process, so a repo reading 0-open can be serving the vulnerable version with no symptom. Implements one leg — an installed npm dependency tree, resolved from the MCP config that launches the deployed server (never a hardcoded path) — and compares each alerted package's installed version against the alert's own `first_patched_version` under SemVer 2.0 precedence. Fail-closed: `FIXED_CONFIRMED` / `STILL_EXPOSED` / `PROCESS_PREDATES_TREE` / `UNDECIDABLE` / `UNVERIFIABLE`, never a silent skip. **The read is bound to the RUNNING process, or it is not an answer:** a version read off disk is a claim about a file, while the question is about the code a live process loaded, and the two part company the moment the tree is written after the process started (`npm ci` into the install of a server nobody restarted). Every run compares the oldest running process's start time against the newest write anywhere under `node_modules` and, whenever it reports at all, **states the binding** — measured either way, or an explicit `NOT MEASURED` where the run died before the tree scan, because a report that only speaks up on trouble cannot be told apart from one that never looked — with that binding's own limitations printed beside it (mtime is the only evidence, so a timestamp-preserving replacement reads as unchanged; the binding is tree-level, so one write unbinds every row). A tree written after the process started is `PROCESS_PREDATES_TREE`, its own word rather than one more `UNVERIFIABLE`, because it is the state that silently turns every other row into a confident answer about the wrong artifact — and such a row still carries what the tree **on disk** says (its `installed_version`, plus an explicitly on-disk verdict in the detail and in `on_disk_disposition` where that read succeeded), because a word for what cannot be known must not also erase what is. Other channel-server installs detected on this host get a stated `UNVERIFIABLE` line each — named and never measured, not skipped. Every alert query passes a series of gates — deliberately **not** enumerated here, because this list was incomplete twice before anyone noticed; `tests/dependabot-reconcile-selftest.sh` asserts each gate can fire and is the authority. Their shared purpose: a wrong answer at HTTP 200 must not read as a real one (that includes summing all four per-state counts against an unfiltered query, so a short read of the *population* is caught too), because this API answers 200 with `[]` for an *unknown* state value — a typo'd filter reads as an empty population at a success status (a mis-cased *known* value is filtered case-insensitively, so it is the enum guard and not casing luck that keeps a typo out). **Fixed scope, host-local by design:** alerts are queried for `PupFuzz/agent-webhook-bridge` only, and the deployed directory is resolved from this host's `kanbanboard-agent` MCP server entry — it is the agent host's own session instrument, not a vendorable per-repo tool. A host with no such entry is *not configured*, not broken: one line, no artifact, rc 0. Read-only apart from its JSON artifact under `~/.cache/coord/dependabot-reconcile/`; runs no git command; advisory step of `board-session-close` |
| `bin/dl-a1-register-field` | **DL-board setup:** register the `dl_number` custom field **as a `string`** + real-surface-verify the `system=dl` by-ref derivation, then fully remove the throwaway (idempotent) — so the toolkit can *stand up* a DL board, not just operate one. **The type is the prerequisite, not a detail:** every writer of that field stamps the canonical `DL-NNNN` **string**, so a `number`-typed `dl_number` answers every `--dl` write `422 Must be a number.` — and the by-ref index, which canonicalizes by stripping non-digits, resolves from either type and so never surfaces it. A pre-existing definition of the wrong type is **refused (rc 1) before any card is created**, printing the in-place `kbcard field retype --field dl_number --to string --restamp-dl` remedy (card#6517). **A by-ref read it cannot decode is `rc 3` UNMEASURED**, distinct from the `rc 1` of a measured failure and never folded into the `rc 0` pass: a `2xx` carrying a gateway/WAF/maintenance page (or a non-2xx, or a request that never completed) at a by-ref read replaces THAT read's line with an UNMEASURED one — so *“after clear: … empty”* and *“zero residue”* are each printed only from a read that succeeded — and withholds the `OK` verdict; a run that also MEASURED a failure at another read still exits `1` (card#10241) |
| `bin/dl-a0-backfill-triaged` | **DL-board setup:** backfill the `triaged` tag onto pre-existing `id:*-pr-*` cards (dry-run default; `--apply` / `--remove`), so untriaged-discovery doesn't read the legacy corpus as untriaged |
| `bin/gh-code-search` | **a GitHub code search that refuses to report a count GitHub has said it cannot stand behind.** `GET /search/code` answers **HTTP 200** with **`total_count: 0`** on a private repository — for a term that certainly exists and a term that cannot exist alike, byte-identically — so the ordinary spelling (`gh api search/code --jq '.total_count'`) hands back a `0` that reads as a finding, and cross-repository claims ("this codebase never emits X") get made from a search that never ran. The discriminator, `incomplete_results`, is already in that body and the `--jq` throws it away. This tool's contract is **error / partial / complete — never a count**, carried by the **exit code**: **0** COMPLETE, **3** PARTIAL (flagged, with a non-zero count **and** at least one item — the matches are printed and usable, the count is not authoritative, and the non-zero rc is what stops a caller consuming it by default), **4** UNANSWERED (flagged with **nothing to stand on** — a count of zero, an **empty item set**, or both — fatal; **no result set is emitted at all**, because an empty result set is precisely the wrong answer. Either half reading empty is enough, and the union is measured behaviour rather than a widening for symmetry: `{"total_count":17,"incomplete_results":true,"items":[]}` is **rc 4** with `results=WITHHELD`, because the count is an ESTIMATE and so is not evidence that results exist, while the item set is what was actually measured and so an empty one is not evidence that they do not), **1** ERROR (`gh` exited non-zero, or a 200 body that is not a readable code-search envelope — a secondary-rate-limit object, an HTML error page, a mistyped field: **an unreadable response is not an empty one**), **2** usage. `total_count` never appears without `incomplete_results` on the same stdout line or in the same JSON object, and is always tagged **ESTIMATE** — code search coarsens it with magnitude and `search/*` counts drift between identical calls, so it is never an equality or threshold input; a caller needing an exact figure must paginate `items`. **No modulus and no stability heuristic are encoded** — both were proposed, both were refuted (`repo:laravel/framework class` → 2460 is not divisible by 8; every `incomplete_results: false` sample either seat has taken was a consecutive repeat of an identical request, so "stable ⇒ trustworthy" is confounded with caching). Every refusal names the way through: `git/trees?recursive=1` to enumerate paths, then `contents` to read them — measured working on the same private repo and token that code search cannot answer for. One request, no pagination; a full page is reported `items_truncated=true`. `--format json` for machine consumers. Read-only |
| `bin/run-coverage-check` | **a CI check that never ran is indistinguishable from one that passed.** GitHub creates *no workflow runs at all* for a PR whose merge ref it cannot compute, `mergeStateStatus` does not separate never-ran from passed, and for a `paths:`-filtered workflow zero runs is the NORMAL state — so "never ran", "correctly skipped" and "passed" are one reading. Given `--repo`/`--pr` it derives, per workflow, whether THIS PR matches the `on:` triggers and the `paths:`/`branches:` filters (against the PR's real changed-file list) and compares that against the runs that exist for the full 40-hex head SHA — reporting **RAN** / **SKIPPED** / **MISSING** as three separate states, with the verdict on the exit code (`0` covered, `1` missing, `2` stands behind nothing). A truncated changed-file list makes path verdicts UNMEASURED rather than SKIPPED. **Report-only: it gates nothing, is wired into no workflow, and issues only GETs** |
| `bin/gitignore-secret-family-check` | **a `.gitignore` rule for a secret-bearing file covers the NAME, not the backup FAMILY.** `.env` being ignored says nothing about `.env~`, `.env.bak`, `.env.save`, `.env.dpkg-old` or `#.env#` — each holds a byte-identical copy of the same secret, none of them reds, and each sits in `git status` as an ordinary untracked file (found live on a peer install as a 4,339-byte `.env~` that had been in the tree for nine days). Rules alone do not close it: the per-rule fix that preceded this tool omitted `*.swp` **in its own first pass**, leaving `auth.json.swp` stageable — the defect bit the person fixing it, inside the fix. This asserts the property instead. **Both halves are derived, not listed:** which rules are secret-bearing comes from the `.gitignore` itself (a secret-ish keyword in the rule's own text, *or* in the contiguous comment block above it — so a rule whose name says nothing, like `.kanban-*`, is still classified, and a secret file added tomorrow is classified with no edit here); the AFFIX table is a declared enumeration because there is nothing to derive one from, and every entry names the producer it was taken from — `vim` `backupext`, `patch(1)`'s `.orig`/`.rej`, `nano`'s `.save`, `dpkg`'s `.dpkg-old`, `git mergetool`'s variants, emacs's `#<name>#` — each read off that producer's own documentation or measured on a real box. It plants nothing: `git check-ignore` answers about pathnames, so the tool never creates the very file it is checking for. `--no-index` is load-bearing — `check-ignore` suppresses INDEXED paths and answers "not ignored" for them, so without it a **tracked** `.env.example` would be reported as an uncovered member, a false finding this must never emit. Fails **closed**: a run that derives ZERO secret-bearing rules is a REFUSAL (rc 2), not a pass, because an empty population satisfies every assertion made over it — `--allow-empty` is how a repo that genuinely ignores no secret says so on the record — and a rule whose sample cannot be instantiated surfaces as `UNRESOLVED` rather than shrinking the population silently. **⛔ Read the verdict for exactly what it is:** it measures the rules in THAT repo AT THAT REF. It says nothing about which ref any *install* runs (an install pinned to an older tag runs the old rules and has to be asked separately), and the affix table is a **lower bound** on an unbounded family — `nano` writes `.save.1`, `.save.2`, … without limit and `cp .env .env.for-alice` invents a suffix on the spot. A trailing-`*` rule (`.env*`) is the only construction that covers a whole suffix family unconditionally; the remediation says so |

Since this is the *only* list of the tools (ADOPTION.md points here rather than keeping a second copy), CI asserts it: [`tests/readme-bin-coverage-selftest.sh`](tests/readme-bin-coverage-selftest.sh) fails the build on a tool with no row **or** a row with no tool. ## Configuration model (no IDs are hard-coded; nothing secret is stored in this repo)

The tools read all environment-specific values from files **outside** this repo:

- **`~/.kanban-host.env`** — the **host-level, board-independent** settings every tool reads: `KBCARD_API` (the api base) and `KANBAN_EXPECTED_HOST` (**required, no default**). `KANBAN_EXPECTED_HOST` is now load-bearing for *every* tool, not just the promote/checkout guards: the resolved `KBCARD_API` is preflighted against it, and an api host nobody declared is a **refusal**, not a fallback. Optionally a host-wide `KBCARD_TOKEN_FILE` default. Template: [`examples/kanban-host.env.example`](examples/kanban-host.env.example).
- **`~/.kanban-<name>-board.env`** — board/stage/type/custom-field IDs, the optional `KB_USER_<SEAT>` seat→kanban-user-id map `patch --assign` resolves names through, and this board's own `KBCARD_TOKEN_FILE`. One per board. **Not the API base** — `KBCARD_API` is host-level, and a board env that sets it is refused (see [`docs/INSTALL.md`](docs/INSTALL.md) §3). Template: [`examples/kanban-board.env.example`](examples/kanban-board.env.example).
- **`~/.kanban-<name>-token`** — a file containing **only** the bearer token (`chmod 600`, never committed). Token precedence: a board env's `KBCARD_TOKEN_FILE` > the host env's > an ambient one > the coord credential store's `[kanban] api_token_file` **pointer** (card#7316 — read POINTER-ONLY; an inline `api_token` value is refused, never read). **There is no baked default:** a board for which no tier names a token file is refused, naming the file to add the line to. `~/.kanban-dev-token` used to be that default, and one file standing in for every board is what let a single overwrite take all of them out at once (card#7245). The store tier is last because it is DISCOVERED — an operator's own declaration must beat one the toolkit went looking for — and a host with no such store is refused exactly as it was before that tier existed.
- **`<repo>/.release-pr.json`** — per-repo release config (only for repos that cut releases). Template: [`examples/release-pr.json.example`](examples/release-pr.json.example). **Security-sensitive:** the `api_base` it names is the host the release-CI writeback token (`KANBAN_WRITEBACK_TOKEN`) is sent to — a PR that edits `api_base` to an attacker host would exfiltrate the token on the next promote run. `promote-released-cards` / `board-card-start` therefore reject any `api_base` that is not `https://` on the expected host (`$KANBAN_EXPECTED_HOST`) before sending the token. **Leave the committed value a placeholder and name the real host out-of-band** — `promote-released-cards` reads `$KANBAN_API_BASE` in preference to `.promote.api_base`, `board-card-start` falls back to `KBCARD_API` from `~/.kanban-host.env`, and both resolutions meet the same guard (INSTALL.md §4). **`KANBAN_EXPECTED_HOST` is REQUIRED — there is no baked default** (this toolkit is vendored onto operators' own kanban hosts, so it assumes none). **Pin `KANBAN_EXPECTED_HOST` in the promote-CI env** as a repo/org variable (out-of-band from the PR-editable config); if it is unset the guard fails closed and refuses to send the token. Treat any `api_base` change in review as a credential-scope change. **`promote.source` is REQUIRED and has no default** — `"<owner>/<repo>"` when the board tracks several repos, or `"*"` to **declare** that it tracks exactly one; `dl_number`/`pr_number` are repo-scoped counters, so an unqualified match on a multi-repo board promotes another repo's cards into a terminal stage, and `promote-released-cards` refuses before any board read until the key is set — and refuses again if the value is not `$GITHUB_REPOSITORY`, since a typo'd slug otherwise promotes 0 cards at rc 0 (INSTALL.md §4).

## Reliability posture (fail-loud / fail-closed)

The value-emitting tools never silently truncate a board read or emit a garbage value — a partial read that looks "complete" drives wrong reconciles (cards the tool never saw look absent → spurious creates / missed moves), and a garbage value stamped downstream corrupts state. That is a claim about shipped behaviour, not an aspiration, so the bullets below are its **exact quantifier** — where a boundary is still open they say so and say what is needed to reach it, rather than letting the sentence above cover it.

- **Loud-on-cap pagination.** A board listing that would exceed a page cap **fails loud** (exits non-zero, no partial output) rather than returning a truncated set. The cap is configurable:
  - `BOARD_PAGE_CAP` (default `50`) — `kbcard list`.
  - `PROMOTE_PAGE_CAP` (default `50`) — `promote-released-cards` (refuses to promote on a truncated board read).
  - `next-dl`'s fallback board-max scan refuses to mint when a configured board does not answer a whole read — a >200-card board that can't be scanned safely, and (card#6631) a board whose page 1 could not be read at all (the atomic claim endpoint is the race-free primary path and is unaffected). **It also refuses a whole read this tool cannot PROJECT (card#10230):** a card whose `payload` is not a JSON object (`{"id":9,"payload":[]}`, the empty-map spelling a PHP backend emits) faults the `dl_number` projection at jq's rc 5, which emits nothing — and that used to reach the caller as the same "this board carries no stamp" outcome as an empty board, dropping the board's DL floor and minting from the local `max+1` scan alone, at rc 0, silently. The benign outcome now **declares itself** and everything else refuses, so the two are no longer one signal. ⚠ Not covered, and named rather than implied: a `2xx` whose `.data` array holds an element that is not an object faults the paginator's own dedup and still reads as an empty board (card#6630, open).
- **A DL number that came from the offline scan SAYS so, and can be refused (card#7214).** `next-dl`'s primary path is the board's server-side atomic claim; when that counter cannot answer, it degrades to the non-atomic `max+1` scan — and that degrade used to be **silent**: rc 0, a number on stdout, an empty stderr, byte-identical on every channel to a reserved claim, so two concurrent allocators could be handed the same DL by the tool whose purpose is to prevent exactly that. Now **every degrade writes its CAUSE to stderr in that cause's own words**, and they are kept apart deliberately — *this board's config did not resolve, so nothing was called* / *the endpoint could not be REACHED (transport failure, no HTTP status, so whether the route exists here is unknown)* / *the endpoint is NOT DEPLOYED (`404`)* / *it answered `2xx` but carried no usable number* — because "not there" and "could not reach it" prescribe different actions, and one generic line would re-mint the conflation being closed. The **disposition** line follows the cause and names the consequence (not atomic; a floor that cannot see a claimed-but-unstamped DL). `--require-counter` makes that disposition a **refusal: rc 4, nothing minted**. It is **opt-in and the default is unchanged** — a single-stream caller on an install whose kanban predates the DL-sequence route is safe on the scan, and flipping the default would start failing it; a present-but-errored endpoint still aborts at **rc 1** as before, with or without the flag. For an existing caller nothing changes but the appearance of a stderr line on the degraded path.
  - **A CONSUMING call FAILS CLOSED wherever it may have SPENT a number and the outcome is unknown — one ruling over the arm SET, not a patch per arm (card#10230).** One transport serves both DL-sequence routes, and **two** of its arms used to send both callers to the benign fallback: a `2xx` carrying no usable number, and a **curl transport failure**. On the **non-consuming** `--peek` that is correct and is unchanged in both — a `GET` allocates nothing, and an unreadable body is indistinguishable from an older response shape, so refusing would break every board predating the route. On the **atomic claim** each was a **fail-open**: the `POST` may already have allocated a number server-side, and the offline `max+1` scan *cannot see a claimed-but-unstamped DL* (card#6232) — so the number it hands back is at or **below** the one just burned, and two cards end up carrying the same DL, which is a correlation key nobody re-checks. Neither producer is exotic: a gateway answering `200` with HTML (an expired SSO session, a WAF block page, a maintenance page), and an ordinary network flake — curl exits non-zero for a lost response, a mid-transfer reset or a timeout just as it does for a refused connection, and *the request did not complete* is **not** evidence that it never arrived (the reading `kb_api`'s `$KB_API_RC_TRANSPORT` contract already states for every write in this tree). The claim now **refuses at rc 1 with empty stdout** on both, naming the cause, saying a number may already be spent — and, on the transport arm, that the tool **cannot tell** a claim the server applied from one that never arrived — and pointing at `--peek`; a burned-but-unused claim is a **gap**, which is expected and fine and needs no recovery action (the refusal names no runbook: [`docs/DL-COUNTER-RECOVERY.md`](docs/DL-COUNTER-RECOVERY.md) is for a counter STRANDED in the wrong range and its remedy force-deletes cards). **[host]** a seat whose board answers the claim endpoint through such a gateway, or whose claim `POST` dies in transport, now gets a refusal where it used to get a number — that number was a duplicate. The CAUSE set is unchanged (one line each); what moved is the **disposition** of two of them, and only for the caller that spent. Mechanically, `dl_sequence_call` takes the consumption as an **argument the decision reads**, not as the prose it prints, and both refusals go through **one** shared refusal so a new arm inherits the ruling instead of re-deciding it — patching a single arm is exactly how the transport arm survived the first pass at this card. **What makes that a guarantee is the CALL SITE, not the arm set**, and saying otherwise is what let the same defect back in twice. The claim's call site falls back to the offline scan **only** when `dl_sequence_call` positively declares that no number was allocated; every other way out of it — whatever status it carries, whatever arm produced it — **refuses**. The arm-set rule above remains the design rule for whoever edits that `case` (obey it and the operator gets that arm's own words), but it is not itself checkable: no static scan has *every arm a future editor writes* as its population, and two were planted that it did not have. `tests/next-dl-selftest.sh` still lifts `dl_sequence_call`'s body and reds on any `exit 1` past the request that is neither guarded by the `non-consuming` test nor pinned `NOTHING WAS SPENT` beside itself — a useful first line that names the offending arm, watched RED against a re-planted "treat 502/503/504 as temporarily down" arm — and it **separately** drives the call-site belt against planted arms spelled with no terminator, with `return 1` and with `exit 1`, each seen minting `DL-0301` at `rc 0` before the belt and refusing after. A **miswired call site** — the argument misspelled, or omitted entirely — refuses on the same side rather than minting, and the arity is checked *before* any positional is read, because under `set -u` the read itself would otherwise kill the call at the rc the caller treats as a benign fallback.
- **A filtered `list` names its denominator, and its projection is the filterable surface.** `kbcard list` emits a **fixed** row projection — `id`, `name`, `stage`, `type`, `swimlane_id`, `swimlane`, `external_id`, `tags`, `assigned_user_id`, `assignee`, `dl`, `pr` — so a downstream `grep`/`jq` over anything else (`description`, any other payload key) answers `0` no matter what the board holds; read a card whole with `kbcard show`, or hunt one **by its body** with `kbcard search`, which is the verb for that question (this projection cannot answer it at any width worth paying for — `description` is unbounded free text on every row of a whole-board read). One qualifier inside that set: `stage` is the **native numeric** `workflow_stage_id` while every `--column` flag takes a **name**, and those ids are **per-install** — read the map with [`kbcard stages`](#kbcard-stages--the-stage-id--column-name-map) rather than pinning a number, which is a join two seats got wrong on one day (card#7694). A second qualifier: `type` is the **native** `card_type_id`, so it is `null` on every row of an all-tag board (and on a mixed board's tag-typed cards), where the type rides `tags` as `type:<alias>` — select on `tags` there, because `--type <alias>` still matches those cards while a filter keyed on the projected `type` returns a confident `0`. And because a filtered `[]` is indistinguishable from an empty board, any filter flag adds one **stderr** line — `list <flags>: <M> of <N> board cards matched` — while stdout stays exactly the array it always was. Unfiltered there is no line: the array's own length is the denominator.

- **A correlation value that is not one POSITIVE integer is refused at the tool, before any request.** `kbcard`'s `create-card` / `patch` are the operator path that *mints* a card's `payload.pr_number` / `issue_number`, so `--pr` and `--issue` require a value naming **one positive integer, optionally decorated** (`178`, `#178`, `PR-178`); no digits, or several digit runs (`1.5`, `2026-08-23`, `PR 12 of 34`), is **rc 2 with no traffic**, naming the flag and the value — and so is a **negative** value (`-5`) or **zero in any spelling** (`0`, `00`, `#0`, `PR-000`). The shape half is the board's own rule for deriving a card's by-ref key, enforced where the value is still unambiguous: a stamp the board derives **no** reference from correlates the card to nothing while looking set, and a reader that instead concatenates the runs derives a **real but different** PR or issue (`1.5` → `15`) — one stored value, two readers, two answers, neither an error. **The sign/zero half is deliberately stricter than that rule**, because pull requests and issues are numbered from 1: `-5` is one decorated integer under it and was therefore accepted and stored, while the board drops the sign with the rest of the decoration and correlates the card to a real but different ref, and the reconciler's positive-only admission test declines the value outright — stored, mis-correlated and invisible at once, and `0` is the same defect one value over. Refusing costs no legitimate caller and collapses those answers into one at the mint site, which is the cheapest place to do it. It is otherwise a check on the value's **shape**, not on the field's declared type: a decorated value passes here and is then refused server-side by a `number`-typed field, which is a different question. `--dl` has always been strict the same way (`kb_dl_canon`, which refuses a sign by anchoring and refuses `0` in its own words), and `--external-id` (`kb_is_uint`) never admitted a sign either; `--pr-url` / `--issue-url` are URLs and are not covered — the pre-PR placeholder `.../pull/0` is one, and rides there untouched by this shape rule (the pair rule in the next bullet still reads it). All of `patch`'s correlation **shape** refusals land **above** its task-ref lookup, with the rest of the offline preflight, so none of them costs a request. Writing either half of a `pr` / `issue` number–URL pair without the other — `--pr`, `--issue`, `--pr-url` or `--issue-url` alone (next bullet) — is decided after a `GET` of the card, still before any write, and is `rc 1` on a card that cannot be read.
- **`kbcard patch` refuses to write one half of a correlation pair over a stored other half that names a different number — `--pr` without `--pr-url`, `--issue` without `--issue-url`, and the mirrors `--pr-url` without `--pr`, `--issue-url` without `--issue` (card#9837, card#9846).** The board merges `payload` per key and derives a card's by-ref `source` (`owner/repo`) from a URL — but only where no `payload.repo` outranks it, and [`docs/INSTALL.md` §4](docs/INSTALL.md) states the whole derivation rather than this page — never from `pr_number` / `issue_number`, so writing one half alone used to leave the card naming one ref by number and another by URL at `rc 0` — attributed to the old URL's repo after `--pr N`, or to the new URL's repo while still naming the old number after `--pr-url U` (so, for the `pr` pair, that repo's release shipping the old number promotes the card — promote reads no issue key: card#9935). `patch` now reads the card first (one `GET`, only when a pair's other half is not in the same call) and refuses at `rc 2`, **writing nothing**, with a message naming the missing flag; pass both halves. Numbers are compared after the tool's own normalisation (`#178`, `PR-178` and `178` agree), and a URL's number is read from `…/pull/<N>` or `…/issues/<N>` for either pair (GitHub numbers issues and PRs in one sequence). Unchanged: no stored counterpart (absent, null or empty), one naming the same number, a STORED pre-PR placeholder `…/pull/0` / `…/issues/0` ("no PR yet"), a STORED number of `0` (in any spelling — it names no ref, so no URL written over it diverges from anything), both halves in one call, and a call that nulls the stored half — `--clear pr-url` / `--clear issue-url`, or a `wont_do` decline without `--keep-refs`, which nulls `pr_number` and `pr_url` (not the issue pair). A GIVEN placeholder is not exempt: `--pr-url …/pull/0` (or `--issue-url …/issues/0`) alone over a card whose number names a real ref is refused like any other divergence — it would say "no PR yet" about a card that names one, and (where the URL is what sets it) move its source — so `bin/adopt-to-dl`, whose stamp is exactly that, refuses such a card before it mints a DL. Nor is a URL — GIVEN or STORED — that names no number but still yields a repo — a `commit`/`tree`/`blob` URL, a `pull`/`issues` segment with no digits, or a value whose only number sits in a different repo's URL: `--pr-url U` alone over a stored real number, and `--pr N` alone over such a stored URL (the `issue` pair likewise), are refused, naming the missing flag and the derived repo, because the card would end up naming that number with a URL naming none. **Every refusal states the divergence and the flag to pass, and no downstream consequence** — not who the card ends up attributed to, not what a release in that repo would promote: those follow from the card's `source`, which the pair does not decide, and a `payload.repo` containing `/` outranks every URL (card#9918). "A URL that yields a repo" is decided by the promote side's own `repo_from_gh_url`, held by the lib as `KB_JQ_REPO_FROM_GH_URL` and pinned identical to the standalone's copy by `tests/mirror-pair-parity-selftest.sh`. A URL, given or stored, that yields NO repo (a non-GitHub URL, a bare `github.com/<owner>/<repo>`), or a stored number naming no one number, proceeds with a notice that no check was made. No message echoes a URL — a refusal names only the derived `owner/repo` and number — and a card that cannot be read is `rc 1` with nothing written. Which pairs a call writes by half is decided offline on **every** `patch`, ahead of the external-id lookup and the `--assign` read, so a `kbcard` beside a lib that predates the check refuses every `patch` at `rc 2` before any request, naming the missing function (card#9756's rule for a guard that cannot be applied). `create-card` is unaffected — there is no stored value to diverge from. **The check's limit:** it compares a half only against the other half of its OWN pair, so `--pr N` on a card with no `pr_url` proceeds silently even when the card's `source` comes from one of the other keys [`docs/INSTALL.md` §4](docs/INSTALL.md) enumerates, naming a repo the PR is not in — refusing that would also refuse the ordinary issue card linking a same-repo PR, so it is a product decision, not part of this rule.
- **A `kbcard` write verb reports the mutation from a READ-BACK, never from the status class — and has a third exit code for "cannot say" (card#8556).** A `2xx` is the server saying it accepted the request; it is not the board saying it holds the result. So a write verb rules on a READ rather than on the status — most of them on a surface the caller can go and read for itself: the card (`delete`, `archive`, `comment`), the card's `linked_tasks` (`link`, and `unlink` already did), or the board's custom-field index (`field create` / `delete` / `set-options` / `retype`). **Four do not take that second read** and rule on the write's own response instead; they are named in *What this does NOT claim*, below, because the difference is what the claim above is worth. **The exit codes are `0` applied · `1` NOT applied and KNOWN (refused, or a read-back that MEASURED the mutation missing — reported as *HARD FAILURE*, quoting what the board holds) · `2` bad invocation, nothing sent — except `patch --tags`/`--type`/`--triaged` on an unreadable tag list and `patch` writing one half of a `pr` / `issue` number–URL pair that the card's stored other half disagrees with (card#9837, card#9846), which read the card first and still write nothing; a guard whose lib invariant gives no answer (a `_kb-board-lib.sh` older than the bin) is `2` too, nothing written · `3` UNVERIFIED WRITE — the request went out and the confirming read could not be made** (it did not complete, was refused `401`/`403`, or answered a `2xx` nothing could be read out of). `3` is a **third** outcome, not a rename of `1`: every state that was `1` and is still knowable is still `1`, so a caller testing `non-zero` is unaffected and only a caller that must not act on an unconfirmed write needs to read it. The distinction is an exit code rather than a word in a message so it survives `2>/dev/null` and needs no prose parsing. **The `--hard` delete is why the rule is not cosmetic:** a false success there says the card's DL ref is **released**, and that release is an input to the next DL mint ([`docs/DL-COUNTER-RECOVERY.md`](docs/DL-COUNTER-RECOVERY.md)), so the wrong answer propagates into the numbering instead of stopping at one bad print. Its re-read passes **`?trashed=1`**, which is the whole discriminator: `GET /tasks/<id>.json` `404`s a merely **trashed** card unless that parameter is sent, so a bare re-read cannot tell a soft delete from a purge — and under `--hard` a soft step this run could not confirm sends **no force-delete at all**, because an irreversible request does not go out behind a precondition nobody read. **What this does NOT claim:** `create-card`, `move`, `patch --column` and `reorder` rule on what the server **echoed** rather than on a second request (a real check — the echo is the server's post-write resource — but not an independent read). The first three compare the stage asked for, and only `workflow_stage_id`; `reorder` re-reads nothing at all and rules entirely on its write's own response — the ranked collection's `position` values, which the request never supplied, plus the `meta` brackets — so a server that echoed a transaction it then failed to commit satisfies it and would not satisfy a re-read. For the first three, `name` / `tags` / `external_id` / `payload` ride the server's own normalization and are deliberately not compared, because a byte-wise compare there would manufacture a failure on a write that landed exactly as asked. `tests/readback-before-success-census.sh` re-derives the population of un-read-back writes across `bin/` on demand; it is a census, not a gate, and its header states what it cannot see. **The rule is no longer `kbcard`'s alone (card#9938).** `bin/promote-released-cards` adopted the same ladder for the card move that a release's board record depends on: after the stage `PATCH` it re-reads the card and rules on `workflow_stage_id`, so `✓ … moved` now quotes the stage it READ, a card that reads back in another stage is `✗ … move NOT APPLIED` (*NOT APPLIED and KNOWN*, quoting the board), and a read that is not a measurement (refused, never completed, or a `2xx` carrying no readable stage) is `⚠ … move UNVERIFIED` — **each on its own counter**, neither folded into `failed`, and each on the summary line only when there is one. **What rc that run exits, and what each rc is conditional on, is stated by that tool and by nothing else — `promote-released-cards --help`, § EXIT CODES.** Deliberately not restated here: this page published the pre-change rule for a round after the tool changed, because each surface was fixed by hand instead of from a derived list. The mover is vendored standalone and can source neither the lib nor `kbcard`, so the rc and the ruling exist twice on purpose; `tests/mirror-pair-parity-selftest.sh` § 6 holds the two `RC_UNVERIFIED` values equal and drives promote's `stage_verdict` beside `kbcard`'s `_kbc_confirm_stage` over one corpus, with the one declared divergence asserted as a value. **Why it was not cosmetic there either:** on 2026-05-22 a release promoted 28 of 28 cards at `2xx` with `updated_at` bumped and `workflow_stage_id` unchanged on every one, printed 28 successes and exited 0.
- **Fail-closed.** A non-2xx API response → exit non-zero with **empty stdout** (never a partial/garbage value); a non-positive/garbage id is rejected rather than sent. Empty stdout means "do not act."
- **A `2xx` nothing can be read out of is refused by the tool, in the tool's own words.** Success is decided on the **HTTP status class alone** — deliberately, because the shapes a body can take are not a reliable success signal (the un-suffixed comments path answers `404` with well-formed JSON) — which means a `2xx` carrying a proxy's HTML error page, a captive-portal interstitial or a truncated read reaches every projection as a success. One shared tolerant parse (`kb_parse_resp` in `_kb-board-lib.sh`) is applied at the **FIRST projection off a response body** — every single-card/field read and every write echo — **not at every `jq` in these files**: a value that has already come through it, or through a guard that refuses on empty, is projected bare afterwards on purpose (`_kbc_annotate_card` and the comment count are two such). **Three bare projections are neither, and are recorded rather than implied:** `archive`'s board projection and the populated-card census behind `field delete` and `field retype --restamp-dl` both read the paginator's output, not a `kb_api` body (the census additionally refuses on *every* non-zero paginator rc before its filter runs), and the `field` verbs project off `_kbc_fetch_fields`, whose non-empty guard admits a `.data` that is not a list — all three carry named blockers in [`docs/CONSOLIDATION-PLAN.md`](docs/CONSOLIDATION-PLAN.md). So an unreadable body yields an **empty value** that lands in the refusal each verb already has, at that verb's own documented rc, never a raw `jq` parse error at an exit status the tool documents nowhere. **The quantifier is exact, and the half it does not reach is named rather than implied:** the whole-board paginator `fetch_board_cards` is **not** on that parse — it reads each page with its own inline `jq … 2>/dev/null` — but it reaches the same posture by its own route, on **every page** (card#6594, card#6630): a body carrying no `.data` **array** is refused at one of the paginator's existing rcs — **rc 1** on page 1, where nothing of the board was read, and **rc 2** on a later page, the rc its contract already assigns to *a page > 1 failed mid-pagination* — instead of being reported as the `[]` a genuinely empty board returns, which the two were previously indistinguishable in (measured: `kbcard list` against a `200` carrying `<html>502</html>` gave `[]` at rc 0 with an empty stderr, and now gives rc 1 with empty stdout). The page selects the rc; the cause is the same one. **The refusal is unconditional; the paginator's stderr LINE is not.** That line is printed only under `KB_FETCH_LOUD`, which two of the six consumer bins set (`kbcard`, `dl-a0-backfill-triaged`); the other four — `next-dl`, `board-card-start`, `board-snapshot`, `board-stats` — read the paginator silently, which is what keeps a fail-soft display quiet, and each says so in its OWN words at its own surface. So "the tool's own words" is exactly right and "a line on stderr from the paginator" would not be. The predicate is the **envelope, not the row count** — a real empty result is `{"data":[],…,"meta":{…,"total":0}}` — so a **genuinely empty board is still a rc-0 success everywhere** and only an unreadable body refuses. Deliberately narrower than the co-vendored `promote-released-cards` mirror, which dies on zero *cards*: a mover can treat an empty board as never a working state, a read verb cannot. **One residual, named rather than implied** — the later-page half was the second, and card#6630's fix closed it **in this paginator** (and, in a second change, in the class's third instance: `bin/board-stats`'s cursor-paged changelog window, where the same envelope read as an exhausted log — measured, closed, and recorded in [`docs/CONSOLIDATION-PLAN.md`](docs/CONSOLIDATION-PLAN.md)): an unreadable body on page > 1 used to read as `[]`, which is a **short page**, which ENDS the scan, so the caller got rc 0 and a board it had only partly read. On a server that DECLARES `meta.total` the short-read census caught that at **rc 4** with a loud `INCOMPLETE` — this API declared it on every probe taken for card#6594, which was an observation and not a guarantee, so the SILENT case needed a server that omits it. **The census-caught case was not therefore harmless, and "a server that declares meta.total is unaffected" is measurably false** — rc 4 EMITS its partial array, and the two consumers that render on 3|4 rendered it: measured through the shipped bins against a page 1 of 200 rows with `meta.total: 201` and a page 2 of `{"error":…}`, `board-snapshot` printed a board line **derived from the truncated read** (`• Board 5 (kanban-board): in-flight 0`) with the `INCOMPLETE` warning on a stderr its SessionStart display does not show, and now prints `(board read failed — fetch rc=2)`. The refuse-policy consumers' disposition is unchanged on that server; only the rc in their message moves (4 → 2). It is now **rc 2** in the lib and a `die` in the mirror, reached *before* the census in both, because *page 2 was unreadable* and *the board is bigger than what arrived* are different operator actions. The census is unchanged and still runs. What remains: a board the token cannot see is answered by this API with the *same* well-formed empty envelope as a board with no cards, so that case still reads as an empty board here. The API behaviour is shared with the mirror; **the consequence is not** — `promote-released-cards` refuses it, because it dies on zero *cards* and can afford to (for a mover an empty board is never a working state), while `fetch_board_cards` must not adopt that predicate at all: a read verb has to let a genuinely empty board succeed, so a zero-row refusal would refuse a legitimate read. Closing this residual needs a membership signal the envelope does not carry, not a stricter row count. Every consumer of the paginator inherits the refusal, and what each does with it is its own documented policy — the dispositions below are the **rc-1** (page-1) ones; a page-2 refusal arrives as rc 2, which every consumer already had a disposition for, unchanged and registered in `tests/fetch-board-cards-caller-claims-selftest.sh`: `kbcard list` and `dl-a0-backfill-triaged` abort, `board-snapshot` prints `(board read failed — fetch rc=1)`, `board-stats` marks the stock section unavailable, `board-card-start` skips the move rather than falling through to a card-id token, and `next-dl`'s fallback board-max scan **refuses** on rc 1 as it already did on rc 2/3/4 — it used to keep a fail-soft posture there and mint from the local `CLAUDE_DECISIONS.md` scan alone with the board's DL floor dropped, which is how a used DL gets re-minted; that residual was **card#6631** and is closed (measured through `adopt-to-dl`: against a board answering `200` + `<html>502</html>` with a local floor of `DL-0300`, the old path stamped **DL-0301** on the card, and the new one aborts before any stamp with the reason on stderr). **Two bounds, stated because the refusal is not total — and the line is resolve-failure vs fetch-failure, not "a board is configured" vs "no board is configured":** a **resolve failure**, where no request is issued at all — `bin/next-dl`'s own header owns the member list, and it is not copied here, because the copy that used to stand in this spot named rcs 3/4/5 and went stale the day `kb_resolve_env` grew rcs 6 and 7 (an api host nobody declared; no token file declared) — and a **complete, successful read of a board that carries no `dl_number` stamp**, which exits `board_dl_max` the same way a resolve failure does. Both still mint from the header scan alone, and a named, reachable board reaches either — `bin/next-dl`'s own header and exit-code note own the enumeration, and name the known-open cases where a board answering `200` still minted. `kbcard archive`'s twin check swallows the rc and substitutes `[]`, which is the safe direction and is now measured rather than argued: the same card with an empty census returns `blocked … no surviving twin — archive withheld (fail-closed)` where a populated one returns `ok`, so a failed board read can only withhold more archives, never permit one. Two consequences worth relying on: a **read** never reports "no such card" / "no comments" / "no custom fields" for a body it could not read (those are claims about the board, and a read that never reached one cannot make them), and a **write** whose echo is unreadable is reported as an UNVERIFIED write at **rc 3** rather than printed (see the read-back bullet above for the full exit-code contract). **One measured exception to the first, stated because a known hole is worth more than a clean sentence:** `comments` tests its list with `(.data.comments // []) | select(type == "array")`, and jq's `//` substitutes its right-hand side for `false` as well as for `null` — so the container test never sees a `comments` of `false`, and `{"data":{"id":505,"comments":false}}` prints **"card 505 has no comments" at rc 0**. The fix is known and moves that verb from rc 0 to rc 1, i.e. a change to what a **read** verb accepts, so it is ask-gated and open; it is filed with its now-closed write-path twin as one class in [`docs/CONSOLIDATION-PLAN.md`](docs/CONSOLIDATION-PLAN.md). What this does **not** cover, and one place it deliberately does: a `2xx` that is valid JSON of the wrong shape still reaches some **read** projections as an empty-but-plausible value, or exits at jq's rc 5 where the projection then indexes it — rejecting it there would change what those verbs *accept*, which is a separate decision. The exception is every read whose result **decides a write**: there an unreadable body refuses the write, **with no PATCH**, instead of being taken as an answer. The rule is stated in the exit-code contract at the top of `bin/kbcard` (`WHAT A WRITE VERB'S EXIT CODE MEANS` and the paragraph under it); each such read's own rc lives in its helper's header — deliberately not listed here. The sharpest of them is the read whose result is re-sent as a **wholesale replacement** of what it read: `patch --tags/--type/--triaged` shape-tests the tag read — `.data` must be an **object** and its `tags` must be an **array** (or absent/null) — and refuses at **rc 2 with no PATCH** otherwise. Both halves are load-bearing, and so is the ORDER the second one is applied in: `{"ok":true}` and `{"data":null}` parse cleanly and yield `[]`, so a tolerant parse alone would let them destroy every tag on the card; a `tags` that is a JSON **object** does not fault either, because jq's `map` iterates an object's *values* — `{"tags":{"0":"keep-me"}}` with `--type` wrote `["keep-me","type:fr"]` and dropped every other tag; and the container test runs on the **near side of the `// []` default**, because jq's `//` yields its right-hand side for `false` exactly as it does for `null` — with the test downstream of that default, `{"tags":false}` was handed `[]` and `--triaged` PATCHed `{"tags":["triaged"]}` at **rc 0**, the same wipe reaching through the guard a third way. What the array **contains** is deliberately not tested (`{"tags":[1,2]}` still patches `[1,2,"triaged"]`) — that would change what this verb accepts and is a separate decision.
- **Fail-soft display/hook tools** (`board-snapshot`, `board-card-start`, hooks) stay non-blocking by design (a hook must not abort a checkout), but surface a **loud notice** on a truncated read rather than presenting it as complete — **on the channel that tool's consumer actually reads**, which is the half that makes the claim mean anything: a notice on a stream the consumer discards is not one. For `board-snapshot` that is **stdout**, the only stream its SessionStart hook surfaces (every count of a partial read carries a `≥` and each section carries its own `card list INCOMPLETE (fetch rc=…)` note — card#6365; the paginator's own `INCOMPLETE` line goes to stderr, which that hook throws away). A board it could not read **at all** says so in **both** sections too, for the same reason: an empty untriaged section under a header promising that none may be silently missed is a completeness claim about a board nobody read. For `board-card-start` the channel is the **durable log file**, because the installed `post-checkout` wrapper discards both streams.
- **Token never in argv.** Every API call feeds the bearer token to `curl` out-of-band via a stdin herestring (`-H @- <<<…`), never as a `-H "Authorization: Bearer …"` argv token — so it can't leak via `ps aux` / world-readable `/proc/<pid>/cmdline` on a multi-user host. The herestring also redirects a regular temp file onto fd 0 rather than a `/dev/fd` named pipe, so it works on native mingw64/Git-Bash curl (where `-H @<(…)` process substitution fails to open its fd). **And a message quoting a server's response body masks that token in the quote, before the excerpt is cut** — the token goes out in a header, and a server rendering debug output echoes request headers into its own error page, so the body a refusal quotes is a channel the credential can come back on. The mask is a literal match on the wire token, applied **before** the length bound because cutting first splits the credential and half a token no longer equals it (card#7500's trap); `next-dl`'s `resp_excerpt` and `promote-released-cards`' `resp_detail` are the two renderers that carry it, and both also scrub the body to one line with no C0 control byte and no DEL, so a body chosen by a third party cannot move the cursor, ring the bell, or overwrite the refusal line it is quoted in (C1, `0x80`-`0x9F`, is the stated limit — deleting it would corrupt legitimate UTF-8). `tests/mirror-pair-parity-selftest.sh` drives both copies over one control-byte corpus, so the two cannot drift apart silently. ⚠ A session identifier the **third party** minted — the `?sid=` in a gateway SSO page — is not masked and is bounded only by the excerpt length; a key-name pattern list would be one spelling behind the next gateway while reading like a guarantee.
- **Fail-closed host guard.** Before the writeback token is sent, the **resolved** `api_base` — the out-of-band value (`$KANBAN_API_BASE` for `promote-released-cards`, `KBCARD_API` for `board-card-start`) where one is set, else the committed `.release-pr.json` value — is validated to be `https://` on the expected host (`$KANBAN_EXPECTED_HOST`, or a subdomain of it); a mismatch **refuses to send the token** (`promote-released-cards` exits non-zero; `board-card-start` warns loudly and stays fail-soft). `KANBAN_EXPECTED_HOST` is **required with no default** — if it is unset/empty the guard also fails closed, so an operator must set it in their promote-CI env for the token ever to be sent.
- **Fail-closed api-host preflight — and it covers the host env, not just the committed config.** The guard above judges the api base a release tool is about to send the writeback token to, from whichever channel supplied it. A second guard, on the same `$KANBAN_EXPECTED_HOST` and the same RFC 3986 authority parser, judges the api base the tools actually resolve from `~/.kanban-host.env` (or `$KANBAN_HOST_ENV`): before any token file is located, the resolved `KBCARD_API`'s host must be the declared host or a subdomain of it, or the run **refuses at setup** — `kbcard` and the `--board`-driven tools exit 2, `board-stats` exits 1, `board-snapshot` prints a SKIPPED line and stays non-blocking. Its predicate is the **host alone** (an `http://127.0.0.1` board is a legitimate install — with one exception that is not this guard's: `board-card-start` additionally requires `https://` before sending the token, so card automation on checkout does not run on a plaintext board; docs/INSTALL.md §3), and an unset/empty `KANBAN_EXPECTED_HOST` refuses too, because with nothing declared every host is unrecognised. This exists because an unrecognised endpoint used to surface twenty minutes later as an `HTTP 401`, long after a config rewrite nobody noticed (card#7245).

## `kbcard` free-text flags — the file form is the convention

The `kbcard` flags that carry **prose** — text long enough that someone other than the caller may have written it — come in pairs: `--name` / `--name-file` and `--description` / `--description-file` on `create-card` and `patch`, `--block-reason` / `--block-reason-file` on `patch`, `--content` / `--content-file` on `comment`. Pass **exactly one** of a pair — both is `rc 2`.

**Use the file form for any text you did not author yourself** — a description written by someone else, a bug report, a pasted log, a review comment. An inline value is expanded by the **caller's shell** before `kbcard` is started, so a `$(…)` or a backtick anywhere in that text **runs as a command** on the invoking box, and `argv` already holds its output by the time `kbcard` can look at it. Nothing in the tool can detect that — the expansion happened in another process — which is why this is a **convention plus a safe route**, and deliberately **not** a validator: a `$(`-sniffing check on the inline flag would be a check incapable of detecting the thing it names. The file form is the safe route because its bytes are read by `kbcard` itself and never meet a shell.

- The file argument is a **path**, absolute or relative. `-` is refused **by name** — it is not a stdin token here. The claim is about the token, not the descriptor: a caller who means stdin passes the path `/dev/stdin`, which is read like any other path.
- A missing, unreadable or **text-free** (empty / whitespace-only) file is `rc 2` **before any request**, so a bad invocation costs no traffic.
- What a file puts on the wire: interior newlines and leading whitespace **verbatim**, **trailing newlines trimmed**, and **CRLF normalized to LF** — a file written on Windows/Git-Bash would otherwise send a literal `\r`, which a reader renders as `?` at the end of every line; a *lone* `\r` is not a line ending and is left to that sanitizer.
- ⛔ **The text-free refusal is the one rule every pair obeys through *both* halves:** an empty or whitespace-only value is `rc 2` **before any request** whether it arrived inline or in a file, on every pair named above. What it buys differs per field, and neither half is "a blank card gets written": a blank **`--name`** used to be **sent**, and the board answered **HTTP 422** (`name` is not nullable, and Laravel's `TrimStrings` → `ConvertEmptyStringsToNull` had already made it `null`) — so the caller paid a round trip for `rc 1` and a server-worded error naming neither the flag nor the real problem. A blank **`--description`** used to be **accepted at `rc 0`** and, by that same rewrite, **CLEARED the field** — the quiet-wrong this refusal actually removes, because `--description "$BODY"` with a `$BODY` that came back empty-with-padding **wiped a card's description while reporting success**. (Clearing it *on purpose* is now `--clear-description`, below.)
- **What counts as blank is exactly six ASCII characters — space, tab, CR, LF, VT (`\v`), FF (`\f`) — decided inside an `LC_ALL=C` window,** so identical bytes get the identical verdict on every box whatever the caller's locale. They did not before `card#9222`: `[[:space:]]` in a bash pattern is a **locale** class, and a lone U+2003 EM SPACE was refused under `en_US.UTF-8` and accepted under `LC_ALL=C` — one product, two answers on one input. The six are exactly what `[[:space:]]` means under the C locale, and they are one lib predicate, `kb_is_blank`, shared with the toolkit's other blank verdicts (`card#9337`). **The residue is deliberate and named rather than hidden:** a value made only of non-ASCII blanks (U+00A0 NO-BREAK SPACE, U+2003, U+3000) is **content**, is **accepted**, and is **sent** — what the board then stores is the board's rule and is not measured from here. Refusing those is a wider contract than has been asked for, and an explicit Unicode-blank list would drift with every Unicode revision with nothing here able to re-derive it.
- **`--content` and `--block-reason` apply the two *rewrites* to their inline value too** — CRLF folded, trailing newlines trimmed, exactly as the file half. (`--content`'s pair is also *required* — neither source is `rc 2`, because for `comment` the text **is** the request; `--name`, `--description` and `--block-reason` are optional field setters, and an omitted pair leaves the field alone.)
- **`--name` / `--description` are the one exception, and only on the *bytes*:** their inline spelling predates its file twin, so an inline value still reaches the wire exactly as typed — a CRLF one included, trailing newlines untrimmed. Rewriting those bytes would narrow what an already-shipped flag accepts, which is an acceptance change nobody has asked for. Blank-checking them **was** one, and it was asked and granted (`card#9222`): before that, `--name-file` refused a whitespace-only value at `rc 2` while the inline half **sent it** — one product answering two ways at two doors, and the inline answer was a wasted request (`rc 1` on the board's 422) or, for `--description`, a **silent clear**.
- **The payload text flags — `--pr-url`, `--issue-url`, `--version` and `--origin` on `create-card` and `patch` — take the same text-free refusal**, `rc 2` **before any request**, by the same six-character rule. They have no file twin, and a value with any text is sent **as typed, as a JSON string** — padding, CR and newlines included. It is never re-typed (`" 123 "`, `"1.10"` and `"nan"` stay strings) and never split (a newline cannot end the value or add a payload key). Until `card#9423` the payload assembler split values into `key=value` lines and coerced each through jq's `tonumber`; retiring that was an acceptance change, asked and granted. Only `--pr` / `--issue` go out as JSON numbers: a numeric spelling (`178`, `00123`, or one padded with spaces, tabs, CRs or newlines) as a number, the same on every jq version, and a decorated one (`#178`) as the string, exactly as passed. A blank one used to be **sent**, and the board's trim-then-null rewrite **cleared the stored field at `rc 0`** (measured on `--origin`); a blank `--pr-url` / `--issue-url` can additionally detach the card from its repo (they set its by-ref `source`), and a repo-qualified release promote then skips it — unless the card carries a `payload.repo` that is a string containing `/`, which outranks every URL, so its source survives the clear. Refusing it was an acceptance change, asked and granted (`card#9338`). Emptying one **on purpose** is `patch --clear <field>`, below.
- **`--tags` on `create-card` and `patch` takes the same text-free refusal**, `rc 2` **before any request**, by the same six-character rule, decided on the value as passed — before `create-card` appends `type:<alias>` or `triaged`. A value with any text is split on commas **exactly as before**, and a blank *member* (`"a, ,b"`, `"a,"`) is not refused: it still goes on the wire as its own element. A blank `--tags` used to be **sent** as its own element, beside any `type:`/`triaged` the call appends — `rc 0` wherever the board accepted it, and on `patch` that **replaces the card's whole tag list** (`patch --tags` replaces it wholesale); what the board does with it is not measured from here. Refusing it was an acceptance change, asked and granted (`card#9421`).

- **`kbcard patch --clear <field>[,<field>…]`** is how the payload text fields above are **removed**, each named by its setter flag's spelling. The clearable set is declared once, in `_kbc_clearable` in `bin/kbcard`; any other name is `rc 2` before any request, and that refusal prints the accepted set (`kbcard patch --task <id> --clear '?'` shows it). Each named field goes out as an explicit JSON `null` for its payload key (`version` → `version_target`), which the board's per-key payload merge **removes**. For `pr-url` / `issue-url` that **can** drop the card's by-ref `source`: the board re-derives it from what remains — `payload.repo` OUTRANKS every URL when it is a string containing `/`, so on such a card clearing a URL cannot drop the source at all; otherwise the other URL keys, then a GitHub `external_link`. Several fields are **one comma list** (`--clear origin,version`), the spelling `--tags` uses — a second `--clear` is `rc 2` rather than a silent last-wins that would drop a clear — and members are matched exactly (no trimming; an empty member is an unknown field). Naming a field **and** its setter (`--pr-url X --clear pr-url`) is `rc 2` before any request. The write echo shows each cleared key raw under `payload`, so a removed one reads `null`. On a board with no `version_target` field, `--clear version` is ignored with the warning `--version` gets. Beside `--column wont_do` a clear composes with the decline nulls and, like an explicit ref flag, wins over `--keep-refs`, whose notice then leaves the cleared key out of what it retained. `create-card` has no such flag. It exists because `card#9338`'s refusal closed the only deliberate route that used to clear these fields — a `wont_do` decline also nulls `pr_url`, as a side effect of declining (`card#9420`).
- **`kbcard patch --clear-description`** is how a description is **removed**. It writes an explicit JSON `null` — the API merges per key, so an omitted key leaves the field alone and a `null` clears it — and is **mutually exclusive with both halves of the `--description` pair** (`rc 2` before any request), exactly as `--unblock` is with `--block-reason`. It exists because the refusal above closed the only route that used to clear the field, and that route was a clear **inferred** from a value that means nothing, delivered by *another repo's* middleware; this one is **said**. The write echo prints the raw `description` on such a call, so the caller sees the `null` without re-reading the card. `create-card` has no such flag — there is nothing to clear at birth.

## `kbcard field` — custom-field schema

Per-board custom fields define which keys a card's `tasks.payload` may carry (an unregistered key 422s on a task write). The `field` verb reads that schema, reconciles enum option sets, and owns the definition lifecycle (create / delete / re-type). Board selection uses the global `--board` flag, like every other `kbcard` verb.

- **`kbcard --board <key> field list`** — list the board's custom fields (`id` / `key` / `label` / `type`); `enum` and `multi_select` fields include their full `{value,label}` option set. Reads the board index (`GET /boards/<id>/custom_fields.json`) — the only field read surface (there is no per-field GET).
- **`kbcard --board <key> field create --key <k> --label <l> --type <t> [--options a,b,c]`** — define a new field and print the **created field id** on stdout; that id is the write verification, and a `2xx` carrying no id is reported as an **unverified write** (rc 3) rather than printed as a plausible `null`. The definition is then **read back off the board's field index** — the only read surface a field has: not defined there is **rc 1** *HARD FAILURE*, an index that could not be re-read is **rc 3**. `--type` is one of `string number date enum multi_select boolean url`. `enum`/`multi_select` **require** `--options`; every other type **refuses** it (the server stores the array and never interprets it — the same silent no-effect `set-options` refuses). A key already defined on the board is **rc 2 before the POST**: a key is unique per board, so creating over the top is not a re-type — `field retype` is (it converts the type in place).
- **`kbcard --board <key> field delete --field <name|id> [--orphan-values]`** — drop a definition, **fail-closed on the carriers it can see**. The board is enumerated first and the denominator `N of M board cards carry <key>` **always** goes to stderr, so a census that *ran* and returned zero is distinguishable from one that never ran. With `N > 0` this **refuses (rc 2)** unless `--orphan-values`, which still prints a loud warning naming both consequences below. A board read that failed or came back **incomplete** (page cap, short read) refuses at rc 1 — a truncated denominator is not a denominator, and the dangerous shape is precisely a truncated read whose visible cards carry nothing. ⚠ **That refusal covers the incompleteness the read can DETECT, and one blind spot it cannot.** The census is `GET /tasks/search.json`, which applies the soft-delete scope and `archived_at IS NULL`, while both consequences below are **board-wide** — the definition delete leaves `tasks.payload` alone for *every* carrier and `purgeField` is `board_id` + `field_key` with no archive and no trash filter. So a board whose only carriers are archived reports `0 of M`, does not refuse, prints no orphan warning and purges the index for all of them; un-archiving one puts an undefined payload key back into the live set. A complete read returns none of those cards and reports no rc, so nothing can refuse on them: the scope is **disclosed on the denominator line itself** (both consumers of that census inherit it), and whether the refusal should widen to carriers the tool cannot see is a change to what this verb rejects — recorded as a request, not made here.
- **`kbcard --board <key> field retype --field <name|id> --to <type> [--options a,b,c] [--accept-ref-impact] [--restamp-dl]`** — change a field's **type**, as **one call** on the server's atomic conversion route (`POST /custom_fields/<id>/change-type.json`). The server converts the **definition** and every stored `tasks.payload` value keyed by it in **one transaction**, rebuilds the search index for the key inside it, and touches no other attribute — `placeholder`, `mask`, `multiline`, `is_filterable` and `position` all survive, which the client-side delete-and-recreate this replaces could not do. The converted **type is read back off the board's field index** before the run reports a conversion, and **before** any `--restamp-dl` pass — a canonicalization sweep over a definition this run has not confirmed converted would be rewriting card values against a type it guessed; a definition still declaring the old type is **rc 1** *HARD FAILURE* (every DSL filter on the key is silently matching the old type, which is invisible from every other surface an operator looks at), and an index that could not be re-read is **rc 3**. This verb issues **no delete, no recreate and no per-card cast**: there is nothing left here for a crash to leave half-migrated, and the whole cast matrix / capture / stranded-board apparatus that existed to make that window survivable is **deleted**, not kept in step.
  - **There is no dry run, and none is simulated.** `--check` exists only on the server's own `php artisan kanban:change-custom-field-type`; the HTTP route does not take it. **Preview-by-refusal** is what the API offers instead: the whole board is scanned **before** anything is written, so a conversion any card value blocks answers **422** naming **every** offending card — each with a `category` (`source_nonconformant` / `projection_impossible` / `target_rejects` / `ref_impact`) and the validator's own message — and leaves the board byte-identical. The refusal **is** the preflight.
  - **`from_type` is always sent.** Resolving `--field` already reads the definition's current type (there is no per-field GET, so the board index is read either way), which makes the compare-and-swap free rather than optional — and a definition whose type moved between that read and this write is its **own** outcome (**412**, *the field's type changed under you*, nothing written), never folded in with a 422.
  - **`--options` is a passthrough.** Every rule about it belongs to the server and is surfaced verbatim rather than re-derived here: options are **required** converting into `enum`/`multi_select` from a non-option source and are **never inherited from the stored column**, **optional** between the two option types (omitted = carried over verbatim), **prohibited** otherwise, and — the fourth, which is the one a re-run reaches — **refused on a request that does not change the type at all**, where `assertOptionsMatchTarget` (which runs *before* the same-type no-op short-circuit) calls them an *options edit* and sends them to `PATCH /custom_fields/<id>.json`. That last one is why a landed conversion carrying `--options` does **not** answer a re-run as a no-op: it answers **422**. The comma list is turned into the server's `[{value}]` wire shape and sent; nothing else about it is this tool's opinion. The list is split and trimmed, and an empty value or an empty list is refused before the wire — those two **are** the server's own rules (`options => array|min:1`, `options.*.value => required`), reached by derivation and not by coincidence, so they refuse nothing the wire would have accepted. ⚠ **One documented exception:** a **duplicate** value is refused at **rc 2** by this tool and the **server has no uniqueness rule on an option set at all** (`assertOptionsMatchTarget` validates the array, the value's presence/type/length and an optional label, and nothing more). The rule is `set-options`' — a converge-to-set target must be distinct — shared by `create`, and it applies here too, so `--options a,a` never reaches the wire. The refusal **says whose rule it is**, so nobody is sent to argue with the server about a rule the server does not have.
  - ⚠ **`--options` REPLACES the whole option set, so between `enum` and `multi_select` it destroys the definition's explicit labels.** The server assigns `$locked->options = $options` outright, and a comma list carries no labels, so every value written this way ends up with `label = value` — the server's default for an omitted label. The run **names each label it dropped**, off the definition it had already read (no extra request). **Omit `--options`** to carry the existing set over verbatim, labels included.
  - **`--accept-ref-impact` is the second half of a two-call handshake, and it never skips the first call.** The one refusal that can be opted into is a conversion that would **move** a card's external-reference correlation. The un-acknowledged POST is always made; its 422 reports the exact card id set under `meta.ref_impact_task_ids`; only then is a second POST sent acknowledging **exactly that set**. The server re-derives the set under the row lock and refuses one that grew or changed, so a set this client guessed would either be refused or — if it happened to match — would launder the one gate that makes a correlation move deliberate. Without the flag the ids and the server's message are printed, nothing is written, and the rc is non-zero. The two `meta` keys are capped differently — `meta.offenders` is truncated at the server's reporting cap while `meta.ref_impact_task_ids` is not — so when the run acknowledges more moves than the refusal named it says so on this path too, rather than showing 50 and acknowledging 200.
  - **`--restamp-dl` is a separate pass after a successful conversion, not part of it.** The cast matrix's text rule for a `number` source is `json_encode`, so the stored number `1` converts to the string `"1"` — **not** `"DL-0001"`. Correlation itself is not at risk (the server canonicalizes `DL-028` / `28` / `#28` to one key), but a custom-field DSL filter written as `DL-0001` **string-misses** a card storing `"1"`, so the conversion alone leaves a DL migration half-done. Each populated card's value is rewritten through the **one canonical DL renderer** (`kb_dl_canon`, the same one `next-dl` and `adopt-to-dl` stamp through) and **verified by re-reading the card**; a card already holding the canonical form is left **unwritten**, so a re-run costs no writes. ⚠ **The pass sees a smaller population than the conversion did, and no run of it can tell you the field is done.** The server's conversion population is every carrier of the key **including archived and soft-deleted cards** (`candidateQuery` is `withTrashed()` with no archive filter); this pass's census is a board read, which returns neither. The run compares the server's own `meta.converted_task_count` against its census, and that compare is **one-directional**: where the conversion touched more, a remainder is **proven** — counted, reported as its own outcome, at rc 1. Where it did not, **nothing is proven either way**, because the two numbers are counts taken at two different moments rather than sets (a card entering the live set between the conversion and the census masks an archived carrier one for one), and because a re-run against the field's current type is the server's **no-op** — no scan, `converted_task_count: 0` — so the difference is structurally zero whatever the board holds. So **every line this pass emits that could be read as "done" carries the census scope with it, unconditionally**, naming which of the two states the run is in; those cards are never read and never written here, and un-archiving one puts a non-canonical value back into the live set. Seven outcomes are reported as the seven different boards they are: **canonicalized** · **already canonical** · **PATCH failed** (the write did not complete, so never counted as verified — and never claimed untouched either: the transport cannot tell a timed-out `PATCH` the server committed from one it never received) · **read back different** · **the verification read could not observe it** (state UNKNOWN — a failed GET and a `2xx` carrying no readable value are the same non-observation, and neither supports a claim about that card) · **not a DL number at all** · **outside this pass's census** (the remainder above). Requires `--to string`.
  - **Every other outcome is reported as itself**, with the server's own body on stderr: **413** the conversion is over one of the server's **two** resource rails — the board-scan rail counts the board's cards, the examined-carriers rail counts the cards holding a value for *this field*, so the client names neither and the server's own message (echoed, because it also carries the operator-supervised escape hatch) says which — **404** the definition was deleted since the run read the field index, **422** in three shapes rather than the two the endpoint documents — the conversion's own refusals both carry `meta` and are told apart by the presence of `meta.offenders` (named cards vs a **pair** refusal: no conversion exists between those two types at all, decided before a single task row was read, so no card is at fault), while the **option rules** are a plain `ValidationException` carrying **no `meta` at all** and are reported as what they are, a request the server rejected as invalid (measured on the sandbox: reporting that third class as a pair refusal told the operator a conversion the server *does* define does not exist) — a **transport failure** (`000`, which every non-zero `curl` exit collapses to) an **UNKNOWN** outcome rather than a safe one — a timed-out or reset write may already be committed, so the run says it cannot tell and names the idempotent re-run — and a **`2xx` nothing can be read out of** an **unverified** conversion at rc 3 that deliberately does **not** go on to restamp: the write landed, but this run cannot say what it landed as. **What the run tells you to re-run depends on the command it was given and on whether the arm can tell that it landed**, and the sentence is one owner fed both: without `--options`, re-running the exact command is safe on either arm — the conversion half answers as a server-side no-op. **With** `--options` there is no directive that is true both ways, because once the conversion has landed the identical command is a same-type request still carrying options, which the server refuses (422) as an options edit belonging to the `PATCH` route, while a conversion that has **not** landed still needs them. So the two arms say different things. The unreadable-`2xx` arm names the re-run **without** them outright — its `2xx` **is** the landed-ness guarantee, since the server does not answer `2xx` for a refusal. The `000` transport arm, which read no answer at all, prescribes the **definition read first** (`field list` — where the `412` arm already sends you) and branches on what it shows: the **target** type means the conversion **landed**, so re-run without `--options`; the **source** type means it did **not**, so re-run the exact command. That first step is correct whichever way the write went, which is the property no single directive on that arm can have. The `000` arm also prints the sentence **minus its restamp clause** — it names no pass on either branch, because it reports a response and only a `2xx` ever reaches the pass. On the unreadable-`2xx` arm, what the sentence says about the restamp pass depends on whether one was asked for: **with `--restamp-dl`**, the re-run also **runs** the pass this run skipped, and whether that pass *finishes* is its own reported outcome (a stored value that is not a DL number is canonicalized by no run of it); **without it**, the line names no pass at all — none was requested, so this run skipped none and a re-run runs none.
- **`kbcard --board <key> field set-options --field <name|id> --options a,b,c`** — an **idempotent converge-to-set** on an `enum`/`multi_select` field's options: after the call the option set equals **exactly** the given comma list, in that order — and that is **read back off the board's field index** before the reconcile is reported, so the claim is made from the board rather than from the PATCH's own echo (a set that did not converge is **rc 1** *HARD FAILURE* naming what the board holds; an index that could not be re-read is **rc 3**). It reconciles by value (a second call with the same list detects no drift and **skips the PATCH** — a no-op it reports on stderr). Values only; each label defaults to its value (labels for retained values are not preserved across a rewrite). Refuses a non-`enum`/`multi_select` field, empty/duplicate values, and an unresolved `--field` (which then enumerates the board's defined fields). The consumer is a provisioning preflight that calls it with a full derived set and expects any drift to heal in one call.

> **Why `delete` is fail-closed, and why `retype` is not built out of it — two measured server behaviours** (pinned against the sandbox instance; both are load-bearing for anyone migrating a field by hand). **(A) Deleting a definition does not cascade to `tasks.payload`.** Resident values survive, orphaned, and are **never revalidated** — a later create over the same key leaves them holding whatever JSON type they were written as. **(B) Deleting *purges* the search-index side table for the key, and creating does *not* rebuild it.** Only a payload **write** touching the key re-indexes it. Composed, those make the obvious hand-rolled type migration — delete, create, done — produce a board that **reads migrated** (the definition says `string`) while every DSL filter on the key matches **zero** cards and every resident value still carries the old JSON type. Nothing about that state is visible without asking each card individually. That is why `delete` refuses a populated field outright instead of being the sharp half of a two-step nobody finishes. **`retype` does not compose those two routes at all**: the server's conversion route converts the definition and every stored value in one transaction and rebuilds the index inside it, so neither (A) nor (B) is on its path — and a type change made by hand through `delete` + `create` is still the trap above, which is what the refusal points at.

> **Observed option-removal semantic** (empirically pinned against the sandbox instance, board 1162; stated here and in `--help` because the server behavior is load-bearing for consumers): **removing an option is a definition-only change.** A card still holding a removed value **keeps it verbatim** in `tasks.payload` — the value is orphaned (no longer a defined option) but preserved, **not cleared and not cascaded**. **Whether the removal PATCH is refused, though, is a property of your server:** without kanban's DL-242 — in no kanban release through v0.41.0 — it is **not rejected** (HTTP 200) even while a card references the dropped value, and that card is stranded silently; with it, the same PATCH is refused **422**, naming the offenders, when the removal would strand a value the **current** definition still accepts. Two limits of that check, both easy to overstate: it is a **delta**, so a carrier whose value the current definition *already* rejects is skipped by design (refusing on it would leave the field uneditable, including the widening that would re-admit the value), and the board-**import** route still narrows unchecked — it is **not** the case that all narrowing is now checked. Either way `set-options` never mutates card data; converging a field's option set away from a value in use leaves that card's stored value intact (and now undefined). `add-option` / `rename-option` are intentionally not provided (deferred to v2).

## `kbcard comment` / `kbcard comments` — the card audit trail

- **`kbcard comment --task <id-or-ext> --content "text" | --content-file PATH`** — post a comment and print the **created comment id** on stdout. Text sourcing is the shared contract in [§ `kbcard` free-text flags](#kbcard-free-text-flags--the-file-form-is-the-convention), with the one difference stated there: this pair is **required** (neither source is `rc 2`, not a no-op — for `comment` the text *is* the request) and **both** its sources are normalized and blank-checked, so `--content "  "` is `rc 2` exactly as an all-whitespace `--content-file` is. A comment's own indentation is content and survives.
- **`kbcard comments --task <id-or-ext>`** — read them back, one block per comment (`comment <id> · user <user_id> · <created_at>` then the content, indented). Comment content is untrusted text going to a terminal, so every **C0 control character except the newline and the tab** (an embedded `ESC` is a terminal *command* — `ESC[2K ESC[1A` erases the attribution line above it) is rendered as `?`; the tab is exempt because it cannot move the cursor *backward*, so it cannot reach that line, while replacing it damages every pasted diff or indented block. The **header line's own fields come from the same untrusted body** and are sanitized too, more strictly — **every** C0 control there, newline and tab included, because a newline in `created_at` would forge a second attribution block where one in the content cannot (content is indented line by line). A card with none prints one explicit *no comments* line at rc 0 — a `2xx` **no comment list can be read out of** is never reported that way; it takes this verb's own `rc 1` refusal, per *Reliability posture* above (which owns that rule for every verb). Two body shapes are covered by it specifically because this verb renders rows rather than emitting them: a `.data.comments` that is **not an array**, and a row whose `content` is **not a string** — the latter would otherwise fail *part way through*, leaving a truncated audit trail that looks complete.

> **Measured semantics** (empirically pinned against the sandbox instance, board 1162), because each one is load-bearing for consumers: **(1)** the write is verified from the **echoed comment id**, never from a card timestamp — whether a comment write moves the card's `updated_at` is the kanban API's to state (its `docs/api-stability-contract.md`, DL-269), and this verification reads neither answer — so a success carrying no id is reported as an **unverified write** (rc 3) rather than printed as a plausible `null`. That id is then **read back** in the card's own `comments` array (measurement (6) below is what makes that array an audit trail rather than a first page, so a posted id missing from it is a real absence): absent is **rc 1** *HARD FAILURE*, a card that could not be re-read is **rc 3**. **(2)** There is **no comment read route** — `GET` on the comments path is `405` (POST only) — so `comments` projects the `comments` array the task-detail `GET` already carries, i.e. the same array `show` returns whole. **(3)** The request body is **flat** `{"content": …}`; the wrapped `{"comment":{…}}` form is refused (`422`). **(4)** The author is a bare `user_id` — that is the only author field a comment row carries. **(5)** `DELETE` on a comment is a **soft** delete — it `200`s echoing the row with `deleted_at` stamped, the row still live — and the task-detail array then **excludes** it rather than carrying it with that timestamp, so `deleted_at` is null on every row this read can return and is deliberately not rendered. **(6)** That array is **complete and ordered**, which is what makes projecting it an *audit-trail* read rather than a first-page one: **60** comments posted to one scratch card came back as **60** rows, `created_at` **ascending**, first and last matching the first and last posted, and the returned content set equal to the posted set (no gap, no duplicate) — the read is not paged and takes no page argument. Corroborated in the server's own source (`Task::comments()` is a `hasMany` ordered by `created_at` with **no limit**, eager-loaded whole by the task-detail resource), which is the argument that there is no cap at any *N*; the probe is what bounds the **observation** — no cap and no re-ordering at 60.

## `kbcard search` — find a card by what its body says

**`kbcard search <query> [--column COL] [--type ALIAS] [--brief | --count]`** — the board's own free-text search, printed as one **block per hit**: a `card <id> · stage <sid> · <name>` header line, then that card's **full `description`**, indented two spaces on every line. A card that matched on its name and carries no body says `(no description)` rather than printing an empty block, because an empty block reads as a rendering fault.

**Why the description is printed and not projected away.** `list` emits a fixed row set that excludes `description` (see *Reliability posture* above), so grepping a card **body** through it returns `0` whatever the board holds — the miss this verb exists to close. A search result that hid the field it had *matched on* would move that miss one layer over rather than fix it, so printing it is the verb's contract, not a formatting choice. The population is the server's match set, not the board, which is what makes printing unbounded free text affordable here.

**What the query is.** The endpoint's own `q=` token stream, sent **after** this board's `board_id=` term — a `board_id=` token of your own is ANDed with it, never swapped for it, so a query cannot retarget the read. The whole term is percent-encoded as one value, so a space, `&` or `#` in it adds no parameter. Practically: bare words are free text over `name` + `description`; **`name:<needle>` and `description:<needle>`** narrow to one column; and the rest of the DSL rides through unchanged (`tags:"x"`, `comments_count>=1`, `updated_at>:2026-08-01`, `custom_field_<key>:v`). A token the server does not recognise is **not refused** — it falls through and is searched as free text, so a mistyped filter silently becomes a word search.

**How a free-text word matches is the server's rule, and it is not one rule.** On the MariaDB instance each word is required and matched as a **prefix** through the `FULLTEXT(name, description)` index — `cat` reaches `category`, not `concatenate` — while a query carrying any word shorter than the index's minimum token length (the server pins that at **3**, MariaDB's default) falls back to a **literal substring match of the whole term**, which is a *phrase* and not an AND of words. If a multi-word query gives a surprising answer, suspect that fallback first. **No hit counts are quoted here on purpose** — a figure measured against a live board is stale the next time anyone files a card, and this paragraph has drifted twice that way. **Which arm runs is the server's rule and it is version-dependent**: newer servers narrow the fallback to an AND of words and disclose the arm that ran in the response meta, older ones do neither, and this tool cannot tell you which instance you are pointed at. Read the kanban API's own free-text contract for that instance rather than inferring it here. **Comment content IS searched** — the free-text arms cover `name` + `description` + comment content, so a word appearing *only* in a comment does reach the card (verified live). Separately, `comments_count<op>N` filters on the **count**, never the content: two different things, and only the second is about counting.

**Refusals and denominators.** `--column` / `--type` filter the matched set client-side exactly as on `list`, and add the same `<M> of <N>` stderr denominator line. A search that matched nothing prints one explicit line at **rc 0** — never a silent empty stdout — and a query that *did* match cards which the filter flags then removed says **that** instead, because they are different answers. A blank or whitespace-only query is **rc 2 before any request**: it matches every card on the board, which is not a search. An incomplete board read is **rc 1 with nothing printed** — a match set missing whatever was on the page that failed reads as *not on the board*, which is a wrong answer rather than a short one. Card bodies are untrusted text going to a terminal, so they pass through the same C0 sanitizer `comments` uses (the header line's fields under the stricter half of it).

**Two opt-in projections, and the block form stays the default.** A handful of hits on a large board is tens of KB of bodies, so a caller who cannot afford that falls back to `list` + a title match — which is *structurally incapable* of answering a body question and hands back a candidate set dressed as a derived population. `--brief` prints the **header lines only**, and they are the **same bytes** the block form's header already carries (one renderer owns that line, so nothing downstream needs a second parser and the two cannot drift). `--count` prints **one line and no bodies** — the `<M> of <N>` denominator above, in the same words, on **stdout** because with that flag the count *is* the requested output; it also replaces the zero-result prose, so `0 of 0` and `0 of N` are what separate *nothing matched* from *the filter removed everything*. Neither flag changes **which** cards match, so the filter flags and the stderr denominator are untouched. **Forgetting a flag costs you too much output, never a silent truncation** — which is why the two together are **rc 2 before any request** rather than one silently winning: they answer different questions, and handing back a number where header lines were asked for is the shape both exist to prevent.

## `kbcard reorder` — rank cards within a column

```
kbcard reorder --ids "10309,10221" --placement top|bottom
kbcard reorder --ids "10309,10221" --before-task 10207
kbcard reorder --ids "10309,10221" --after-task  10207
```

**Sets the ORDER of one or more cards inside one column, by placing them against an anchor.** It is the client half of the board's own stage-scoped ranking route: `move` decides a card's **column** and lets the board put it wherever it lands, and until this verb existed there was no sanctioned way to say *"put this card at the top"* at all — so a seat that needed to rank a column either did nothing or built a private wrapper around the API, which is exactly what one board-tool method exists to prevent.

**It writes `position` and only `position`.** Nothing here can move a card between columns or between swimlanes — `move` / `patch --column` own the column, `patch --swimlane` owns the lane, and this verb is not a third route to either. **Scope is the stage, across every swimlane in it:** all the ids must be active cards of one column (a list spanning two is refused by the board, there being no ordering between columns to express), while a list spanning several swimlanes of one column is the ordinary case — on a board where the swimlane is the owning repo, one ranking question spans them, and a per-lane order would answer it with N incomparable orders instead of one.

**`--ids` is the moving block, in target order,** as one comma list (the spelling `--tags` and `--clear` use). Each member is an `ID-OR-EXT` resolved through the same resolver every `--task` takes, so an external id works and a numeric id costs no request.

⭐ **Exactly one placement, and this tool decides that offline.** Zero, or more than one, is **rc 2 before any request**, naming what was passed; `--placement` takes `top` or `bottom` and nothing else. It is the board's own rule — the same call is refused server-side — applied where the flags are typed, so a malformed invocation costs no traffic. Three more refusals are offline for the same reason: no `--ids`; an `--ids` member that is visually blank (`"5,,6"`, `"5,"`) — a token naming no card is a mistake about *which* cards are being ranked, and dropping it silently would land a **different order at rc 0**; and **the same card named twice once resolved, or an anchor that is itself in `--ids`** — one shape, both reachable *without typing a repeat*, since an id and that card's external id are two spellings of one card (`--ids 901 --after-task EXT-A` with `EXT-A` resolving to `901`). Both are decided from values already in hand: no board read, and no stage rule re-derived. Surrounding blanks on a member are trimmed before it is resolved — the board trims the same list, but **the two character sets are not asserted equal and must not be read as equal** (this one is `kb_is_blank`'s six ASCII characters under `LC_ALL=C`; the board's is its own language's default, which differs at the edges). What the trim is for is the ordinary padded spelling, not parity.

**The board's own refusals are relayed, never re-derived here** — ids spanning two columns, an id naming no active card, an anchor outside the column. The rule is exactly *a fact about rows this call never reads*: each of the three needs rows only the board holds, and a second copy of its stage rules inside a client is the divergence this verb exists to remove one layer up.

⭐ **What it prints is the board's own collection, and the placement is confirmed from it.** The `200` carries the ranked cards in their new order with their new `position`, plus a `meta` naming the untouched cards **bracketing** the block — the route returns that precisely so a caller can confirm the *achieved* placement from data rather than from a status class. `stdout` is one object: `{workflow_stage_id, before_task_id, after_task_id, renumbered, ranked: [{id, name, workflow_stage_id, swimlane_id, position}, …]}`.

**Three comparisons are made against it before anything is called a success, and they answer three different questions — they are not interchangeable:**

1. **Which cards.** The ids echoed must be the ids asked for, in that order. ⚠ **This is a consistency check, not evidence of the achieved order:** the board builds that collection from the request's *own* ordered id list, so it agrees with the request by construction and can disagree only on a server already wrong about much more.
2. **The order inside the block.** The `position` values must be **strictly increasing** in the order returned. This is the gate that measures what `--ids` asked for, because `position` is the one value in the response the request never supplied — the board computes it from the column's live coordinates. Not strictly increasing (ties included) is **rc 1 `HARD FAILURE`**; a row carrying no *numeric* position is not a wrong order but **no order that can be read**, so it is an **`UNVERIFIED WRITE` at rc 3** rather than a claim nobody measured.
3. **Where the block landed.** The bracket must be the one asked for (`top` ⇒ no card before the block, `bottom` ⇒ none after, `--before-task X` ⇒ X is the card *after* it, `--after-task X` ⇒ X is the card *before* it). **rc 1 `HARD FAILURE`** on a disagreement.

A `2xx` carrying no readable collection, or no `meta`, is an **`UNVERIFIED WRITE` at rc 3** (§ Reliability posture). ⚠ The two `HARD FAILURE` arms in 2 and 3 are **applied-but-not-as-asked**, not *did not take* — they say so, because the caller's next action is to re-read the column rather than to assume nothing happened.

⚠ **That second comparison is a claim about the board's code, and nothing in this repo can check it.** It was read at the kanban tag the route shipped in: the brackets are *derived* from the positions actually written — the last untouched card below the block, the first above it — not echoed back out of the request, which is what makes them worth comparing against. A server build that changed that derivation would make this verb report `HARD FAILURE` over a write that **landed**, the costlier direction to be wrong in, so it is named here rather than assumed. `bin/kbcard`'s `reorder` header carries the same warning for the reader at a terminal.

⚠ **`renumbered: true` is not movement, and is never reported as any.** On the rare request whose placement exhausts the float gap between two neighbours, the column's position **coordinates** are rebuilt onto an even ladder and **no card's rank changes**; the board records that as one `lane.cards_renumbered` event, never as N moves. `ranked` is the cards this call ranked and never the re-spaced ones, and the flag is called out on stderr in those words.

## `kbcard stages` — the stage id → column name map

**`kbcard --board <key> stages`** — the id → column-name pairs as JSON, symmetric with `field list`: one `{"id": <n>, "name": "<column>"}` object per mapped stage, and no other key. This is the join `list` needs. It exists because nothing read the map out, so every consumer hardcoded or **inferred** it — and both failure modes are a confident wrong number rather than an error: one seat inferred a stage id from the ordering of the `--column` enum, another filtered a board sweep on the wrong key and read `0` over a real backlog, twice.

⚠ **It reads this caller's own config, not the server.** The pairs are the `KB_STAGE_*` variables **visible to the process** — `~/.kanban-<board>-board.env` (selected by the global `--board` flag), **plus any `KB_STAGE_*` the calling shell exported**, which the board-env resolve does not clear — and **no request is issued**. That is what makes the read worth having rather than what weakens it: the ids are **per-install**, so a consumer that bakes one in is guaranteed wrong on somebody else's box. A `name` here is a `KB_STAGE_*` variable's **suffix, lowercased** — *this install's* word for the column, not the board's own label.

⚠ **Every successful call writes that caveat to stderr, and `stages` is therefore NOT safe to run with stderr merged into stdout.** `kbcard stages 2>&1 | jq .` dies at `jq: parse error` on line 1 — redirect stderr separately (`2>/dev/null`, or to a file) when you pipe the JSON. The declaration rides stderr rather than a third row key because stdout's contract is the `{"id","name"}`-and-no-other-key join `list --column` depends on; widening it to carry a caveat would break every consumer to warn the one that never reads. **`stdout` is byte-for-byte what it was before the declaration existed.** A board env mapping **no** stage is **rc 1 with nothing on stdout** — every column this tool can address needs a `KB_STAGE_*` var, so an empty map is a config fault and not a board with no columns — and a `KB_STAGE_*` whose value is not a stage id (including the `000` placeholder a copied board-env template still carries) is **named on stderr** rather than dropped.

**There is no ordinal field, deliberately.** Nothing this read can see carries the board's column **order** — the env is an unordered set of `name=id` pairs — so an ordinal would be a plausible-looking sequence with no source, i.e. the same defect one layer over. Rows are emitted **sorted by name** for determinism; that is not the board's order and is not offered as one.

**The name half is `stage_name`'s** — the same resolver `show` fills a card's `column` from — so this read cannot disagree with it: **any** `KB_STAGE_*` var maps (a board's own taxonomy, not just the eight `--column` aliases) and a duplicate id resolves once.

## The seat owner tag — `owner:<project>/<seat>`

**The seat working a card is recorded as one tag, `owner:<project>/<seat>`.** This section is the one statement of its rules: the tools, the hooks and the other docs point here rather than restating them. `<project>` is the `project` value of the coord config, which is the file `$COORD_CONFIG` names, or `~/.config/coord/coordination.config.json` when it is unset. `<seat>` is `$COORD_AGENT`, which must equal one of that config's `roster[].name`. No other config key is read. It is a **tag, not `assigned_user_id`**, because seats commonly share one kanban user, so a user id cannot tell them apart. It is **project-qualified** because seat names repeat across installs that work the same board, and a bare `owner:<seat>` would compare equal across them.

- **Written after the move, never on it.** No writer puts the owner tag on the move `PATCH`. That `PATCH` is stage-only, `workflow_stage_id` alone, unless the mover's own rule adds a key: `kbcard`'s terminal-column assignment clear is one that does, and what that costs the token is [§ `kbcard patch --assign`](#kbcard-patch---assign--which-seat-is-already-working-this-card), in the *A terminal move clears the assignment in the same `PATCH`* paragraph and the one after it. Only once the move has succeeded does the writer write the owner tag, in a second `PATCH` whose only key is `tags`. The kanban server authorizes a stage-only `PATCH` as a **move** and a `PATCH` with any other key as an **update**, and it validates every tag. A tag carried on the move would therefore let a rejected tag refuse the move itself, and would make every move, stage-only ones included, need update permission. A refused tag write prints `owner tag … NOT stamped` or `owner tags NOT cleared` with the HTTP status and the server's own reason. The move's outcome and the command's exit code do not change. **`promote-released-cards`' clear reports from a READ-BACK of the card's tags, not from the `PATCH`'s status (card#9938)** — `✓ … removed owner tag(s) …` is printed only once the card has been re-read carrying none, a `2xx` that left an `owner:*` tag in place is `✗ … owner tags NOT cleared … the card STILL carries …`, and a write whose outcome could not be read says so as UNVERIFIED. That outcome still changes no count and no exit code: the card IS released, and a stale tag is a claim nobody is acting on, which is why the same read-back moves the MOVE's exit code (`promote-released-cards --help`, § EXIT CODES — the one place that ladder is published) and takes this nowhere. `kbcard` and `board-card-start` share one implementation of the write, the toolkit lib's `kb_owner_tag_write`. `promote-released-cards` is vendored standalone and cannot call it, so it carries its own copy of the clear. ⚠ **The read-back above is that COPY's, and only that copy's: `kb_owner_tag_write` still reports `owner tag … stamped` / `removed owner tag(s) …` from the `PATCH`'s status class, with no re-read, so a `2xx` that changed no tag prints the same sentence there as one that worked.** The two therefore disagree on this one property — named here rather than left to be inferred from the mirror claim. It is **not fixed under card#9938 and needs its own change**: the lib function is shared, and changing what `kbcard` and `board-card-start` print about a write is an acceptance change on those tools, with their own callers and their own approval. `tests/mirror-pair-parity-selftest.sh` pins that copy's tag rules (`owner_card_tags` / `owner_strip` / `owner_list`) to the lib's, row by row. It does not compare the clear's control flow; `tests/promote-refusal-detail-selftest.sh` tests that separately, in § 7 *A released card loses its seat owner tags*, and `tests/promote-move-readback-selftest.sh` § 5 drives the read-back half, including the `2xx` that changes no tag. **Three arms are driven by no leg, named rather than left to look covered:** a tag write that never completes (`owner tag clear NOT CONFIRMED`), and the clear's own read-back failing or yielding no readable tag list — both of those need the card read AFTER the tag write to fail while the move's read-back succeeded, and the test stub's card-read knobs are per-run.
- **Stamped on card start.** `bin/board-card-start` (post-checkout) and `hooks/agent-dispatch-card-start` (through `kbcard move --stamp-owner --card-start`) stamp the tag after they move a card to In Progress. `board-card-start` stamps only after it has **read the move back on the card** (card#10029: a `PATCH`'s 2xx is not the board holding the stage), so a move it measured as un-applied — or one it could not confirm at all — gets no owner tag. ⚠ **The two starters do not confirm the same way:** the dispatch path's move is confirmed from the stage the move `PATCH` itself **echoed** (`_kbc_confirm_stage`, the posture card#8556 shipped for `create-card` / `move` / `patch --column`), not from a second request — so a 2xx echoing a stage the board did not hold stamps the tag there where it would not here, and closing that is a change to `kbcard`'s own write contract rather than this one. A card the hook does not move is not stamped — and since card#9556 both starters ask the same shared work-start guard: neither stamps nor moves a **pinned** card, and neither promotes a card outside Backlog / Prioritized — **except that a Held card still advances at checkout on a genuine branch creation**, a work-start signal a dispatch does not have, so `bin/board-card-start` promotes it there — in an **armed** repo, the only kind where it runs at all (card#9845) — while `kbcard move --card-start` always refuses it. The decline sets are deliberately unequal in that one case, which is why the shared stage verdict answers Held with its own return code instead of a boolean. `--stamp-owner` beside a terminal column is refused at rc 2, before any request.
- **Read before replace.** The API replaces `tags` wholesale, so the card is read fresh and its whole list is re-sent. **If the tags cannot be read, no tag list is sent**: a non-2xx read and a body with no tag list in it both count as unreadable, because a list built from nothing would wipe the card's other tags.
- **When the tag is not stamped.** In each of these cases no tag is written and the reason is printed:
  - another project/seat already holds the card. The holder is named, its tag is left untouched, and no second owner tag is added. There is **no steal path** in the hooks: a hook runs with no human at hand to make a takeover deliberate, so a takeover is a deliberate tag edit;
  - the coord config is missing or unreadable, is not a JSON object, or has no non-empty `project`;
  - `COORD_AGENT` is unset, or is not one of the roster's names;
  - `project` or the seat contains `/`, the separator between them;
  - the tag would be longer than 64 characters, the board's per-tag limit;
  - the card's tags cannot be read (above).

  The same owner already present writes nothing and prints nothing. `board-card-start` also appends every line it prints about the owner tag to its durable log (`docs/HOOKS.md` § Scope / limits), because its installed wrapper discards stderr. The dispatch hook relays kbcard's `owner tag` lines to its own stderr.
- ⚠ **What the tag write REPORTS is decided from its `PATCH`'s status, not from a read-back.** `kb_owner_tag_write` in `bin/_kb-board-lib.sh` — the one writer behind both card-start paths and `kbcard move --stamp-owner` / the terminal-column clear — prints `owner tag … stamped` / `removed owner tag(s) …` on any 2xx, so a 2xx that changed no tag says the same sentence as one that worked. The **move** it follows is read back (card#10029); this write is not, and it is named here rather than left to read as covered. Changing it changes what every caller of that shared lib reports, so it is its own change.
- **Removed when the card's work is finished.** The terminal columns are `shipped_to_dev`, `released_to_main` and `wont_do`. `kbcard move --column` and `kbcard patch --column` to one of them remove **every** `owner:*` tag after the move and keep every other tag. The same set clears the assignment ([below](#kbcard-patch---assign--which-seat-is-already-working-this-card)). `bin/promote-released-cards` removes them from every card it moves to the released stage. A card with no owner tag gets no tag write. The set is **by alias**: a board column to the right of Shipped or Released is not treated as terminal because of where it sits, which is where the toolkit differs from the bridge, whose terminal set extends by column position. ⚠ A terminal move made by another writer, such as a board-UI drag or a merge-driven writeback, clears nothing on the toolkit side.
- **⚠ Known limit: the read and the write are not atomic.** The tag write is a read followed by a wholesale replace, and the server offers no compare-and-swap for it. A tag edit that lands between the two is overwritten. Two seats starting the same card at the same moment can both read it unowned and both stamp it, and the later write replaces the earlier one. Closing this needs server support. The conflict refusal catches every start whose read comes after the first stamp has landed.

## `kbcard patch --assign` — which seat is already working this card

**`--assign` sets the kanban assignee, not the seat owner.** On an install whose seats share one kanban user, the seat working a card is the [`owner:` tag](#the-seat-owner-tag--ownerprojectseat), and `--assign` neither reads nor writes it.

**`kbcard --board <key> patch --task <id> --assign <seat|user-id>`** (and `--unassign`) writes the board's **native `assigned_user_id`**. The question it answers is not "who owns this" but **"is somebody already on it"** — a card whose **column never moved** looks unclaimed and is not, which is how two seats come to pull the same work with nothing to notice.

⭐ **The refusal is the detector, not the write.** A card already assigned to a **different** user is **`rc 1`, the holder named, and no `PATCH` issued at all** — so the second seat is told whose work it was about to redo. A writer that silently overwrote the field would leave the same board state either way and detect nothing. `--steal` is the opt-out and **says loudly whose assignment it took**, naming both ends; assigning the seat that already holds the card is not a conflict and needs no flag (an interrupted take can be re-run). **The read that decides this is fail-closed:** a card whose assignment could not be *read* — a `403`, or a `2xx` no card can be read out of — refuses too, because an unread card and an unassigned one look identical to a filter that projects the field alone, and those are opposite answers here.

**`--unassign` is deliberately not gated the same way,** and the reason is a fact about the tool rather than a preference: `kbcard` has no notion of **which seat is running it** — the map resolves names to ids, never "me" — so it cannot tell a seat releasing its **own** card, the ordinary case, from one clearing somebody else's. Gating it would make `--steal` routine, and a loud line nobody can avoid stops being loud. It **names the holder it released** instead, so nothing goes silently.

**The seat→id map is `KB_USER_<SEAT>=<id>` in this board's env** — the same config-driven shape as `KB_STAGE_*` / `KB_TYPE_*`, and **deliberately not** another product's agent config: `kbcard` is a standalone CLI and has to work on a seat where that product is not installed, so reaching into a file it does not own would be a dependency on something that need not exist. A **numeric id passes through** (a board that declares no seats can still assign), and ⚠ **an unknown seat name is `rc 2` before any request**, naming the var to declare and enumerating the ones this board env does define — an unresolvable name is a config gap, and *doing something other than what the caller believed* is the failure the verb exists to remove. **Nothing here needs a fleet-wide seat table, which is what keeps it free of cross-repo drift:** a writer resolves only the one seat it was told to write, and a reader needs the map only to put a **name** on an id it can already print raw. A seat name carrying a hyphen is declared with underscores (`KB_USER_KANBAN_SOLO`) and renders that way; both spellings resolve to the same var, so a rendered name is always accepted back by `--assign`.

**Reading it back:** `list` projects `assigned_user_id` (always the raw id) **and** `assignee` (the seat name where this env maps that id, `null` where it does not); `show` annotates `assignee` and **omits** the key rather than emitting `null` when it cannot resolve one — the same omit-don't-null rule `column` follows, because an emitted `"assignee": null` on a card that *is* assigned reads as "nobody is working this", which is the exact claim the field exists to make readable. The raw id is on the row either way, so an unmapped seat costs a **name**, not an answer.

⭐ **A terminal move clears the assignment in the same `PATCH`** — the terminal columns are the ones [§ The seat owner tag](#the-seat-owner-tag--ownerprojectseat) names, from `move` and from `patch --column` alike, because both write through **one primitive** that owns the rule rather than each mover remembering it. A finished card that still names a holder is the stale claim this field exists to make readable. An assignment named **explicitly** in the same call wins (the same "explicit beats hygiene" rule the decline-stamp clear follows) and the notice says which of the two happened.

⚠ **This is a write the toolkit did not previously make, and the token has to be allowed to make it.** A `401`/`403` on a write carrying `assigned_user_id` is reported as an **install fault by name** — the board token's role (writing an assignee needs `task.update`), or a board that is read-only to it — rather than as a generic HTTP line: it is permanent for that token, so retrying and editing the card change nothing.

## `kbcard patch --block-reason` — the blocker a burn-down can actually render

**`kbcard --board <key> patch --task <id> --block-reason "why this is stuck"`** (and **`--unblock`**) writes the board's own top-level **`block_reason`** — the field a sprint burn-down renders as its **"Blocker / next action"** column.

**Nothing on any product surface wrote that field before this flag** — not this CLI, not the board's web UI; it was reachable only by a hand-rolled API call. So the column read **empty on every row of every board**, and an operator reading a race-to-release page reasonably concluded that **nothing was blocked**. That is a false answer produced by a *working renderer with no writer*, which is worse than a missing column: the blank cell is indistinguishable from a measurement. A blocker recorded in a card **comment**, the only place an agent had, is not readable there at all.

⛔ **`--unblock` is the clearer, and it is not optional dressing.** A reason that can be set and not unset **goes stale in a structured field** — which is precisely the failure [`bin/_kbc-stale-blocker.py`](bin/_kbc-stale-blocker.py) exists to report, a card still asserting a constraint that was true when it was written and that nothing re-reads. A setter shipped alone would mint the defect the feature is justified by, so the two land together.

- **It writes an explicit JSON `null`, not an empty string.** The distinction that is *real* is the API's **per-key merge**: an *omitted* key leaves the field alone, a `null` **clears** it. `""` is a third thing **on the wire** and **not** a third stored state — the board runs Laravel's `TrimStrings` then `ConvertEmptyStringsToNull` over JSON bodies, so `""` (and any all-whitespace value) reaches the controller as `null` and stores **NULL**, collapsing into the clear. Sending `null` explicitly is the spelling that does not *depend* on that: it asks for the clear rather than being rewritten into one. The three writes are distinct **on the wire**, which is what the selftest asserts (on the JSON **type**) — it makes no claim about three stored states.
  - ⚠ **That is a claim about another repo and nothing here can check it.** Read at the `kanban-board` declaring end — its bootstrap leaves the global stack's `TrimStrings` / `ConvertEmptyStringsToNull` in place, `TransformsRequest::clean` covers a JSON body, and the board's own test header states the rewrite in its own words — and **measured** against the live board. A board that excepted that middleware would make `""` a stored value again with this repo's suite unmoved, so it is named rather than assumed.
- ⛔ **A whitespace-only reason is refused, `rc 2` before any request, through *either* half of the pair** — and what it prevents is a **silent no-op**, not a blank-looking blocker. Measured: the same call without this refusal is **`rc 0`, and the board stores `NULL`** (the normalization above), so the card ends up **not blocked** while the caller was told the write landed. The echo was already printing that `null`; the **exit status** said success, and automation reads the status. (Not special to this pair: **every** free-text flag refuses a text-free value through either half — `§ kbcard free-text flags` owns that rule.)
- **An omitted flag leaves the field exactly as it was** — the ordinary `patch` rule. (⚠ Note that `--tags` is the one flag that does *not* work this way: the API replaces that list wholesale.)
- **`--block-reason` and `--unblock` are mutually exclusive**, `rc 2` **before any request** — a call naming both says nothing about what the card should end up holding, and silently picking one is the quiet-wrong this field exists to remove. Naming **both halves of the `--block-reason` / `--block-reason-file` pair** is `rc 2` the same way.

⚠ **The length cap is the board's, and this CLI neither restates nor enforces it.** The API declares a maximum for the column and **refuses a longer value itself, naming it**; `kbcard` sends what it was given and **never truncates** — a silently shortened blocker is a *different sentence* from the one the caller wrote, stored under an `rc 0` that says it landed. Copying that number into the CLI would be a second copy of the board's own rule with nothing comparing the two, so a board that **widened** the column would find itself refused by its own tool; it is the same call `--pr` already makes about the board's declared field type.

**Reading it back:** `show` returns the field with the rest of the card. `list` does **not** project it — that projection is a fixed field set, so a `list`-based grep for a blocker answers `0` whatever the board holds; use `show`.

### ⚠ Setting a reason pins the card against the whole `post-checkout` hook — not just its stage move

[`bin/board-card-start`](bin/board-card-start) treats a non-empty `block_reason` as an opt-out — alongside the `no-automove` tag — and **`exit`s at that guard**. The stage move is the visible half. The half that costs more is below it: the hook's **`payload.dl_number` stamp never runs**, and the file says so in its own words — *a hands-off card gets no automated write at all*, which is why the stamp sits after the guard rather than before it. The same pin refuses `kbcard move --card-start`, which is how [`hooks/agent-dispatch-card-start`](docs/HOOKS.md#agent-dispatch-card-start-hooksagent-dispatch-card-start-card-4945) asks the question — so a pinned card is left alone on the dispatch path too, not only at checkout.

**The sequence that costs a release:**

1. `kbcard patch --task X --block-reason "…"`.
2. Someone checks out a branch naming card X **and** a DL, in a repo **armed** with `git config kanban.automove-on-checkout true`. The hook fires, hits the pin, and exits. (An *unarmed* repo reaches step 3 by a shorter route — the hook never calls the mover at all, so the pin is never even read; same missing stamp, different cause.)
3. `payload.dl_number` is **never stamped** on card X.
4. At release, the DL-correlated movers (bridge writeback, release promote) **no-op on that card** — it is simply missing from the promotion, with nothing failing.

⛔ **`--unblock` releases the pin but does not backfill the missed stamp.** Nothing re-fires when the pin comes off, so a card pinned while its branch was being worked stays unstamped: stamp it by hand (`kbcard patch --task X --dl DL-NNN`), or check the branch out again in a repo **armed** with `git config kanban.automove-on-checkout true` — an unarmed repo never calls the mover, so a re-checkout there backfills nothing ([`docs/HOOKS.md` § Arm it per repo](docs/HOOKS.md#arm-it-per-repo--unset-means-off-card9845)).

The coupling itself predates this flag and is coherent — a blocked card should not be dragged forward by a checkout — but nothing could *set* `block_reason` before, so nothing could trip it. This is the first release in which it is reachable.

**Out of scope, deliberately:** `_kbc-stale-blocker.py` still greps card **prose** for `blocked behind card#N`. That leg has to keep working for every card written before this writer existed, and switching it to the structured field is a separate change with its own denominator.

## Versioning

`VERSION` holds the toolkit's semver. Upgrades bump it; product repos that vendor a tool record the version they vendored (see UPGRADE.md) so `agent-board-toolkit-drift-check` can flag both *content* drift and *version* skew. Composite-action consumers (INSTALL.md §6a) don't vendor — their version is the SHA pin, bumped by dependabot.
