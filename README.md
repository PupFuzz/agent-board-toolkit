# agent-board-toolkit

Single source of truth for kanban-dev's **bash** board tooling — the CLI + helpers that drive a kanban board from the agent host and from release CI. One versioned copy, consumed by the agent host (via symlink) and by product repos that run a tool in CI — GitHub-Actions repos via the SHA-pinned [`promote/`](promote/action.yml) composite action, others via a drift-checked vendor.

> **Scope.** This is **kanban-dev's** within-runtime code-share (Task-tracking standard §8): it serves the agent host + the `kanbanboard` and `agent-webhook-bridge` repos. The PM projects' (sola/aimla) *primary* board-ops sharing is Python (`coord.kanban_common`) — but because this is portable `bash` + `curl` + `jq`, a PM project **may also vendor these tools directly** (vendor + drift-check), routing any shared-board need through FRs to this repo, **never a silent fork**. (§8 amended 2026-06-19 at AIMLA PM's request: the original wording *excluded* PM projects, on a cross-runtime-ceiling assumption that doesn't hold for the bash layer.) The canonical three-way shared surface is still the **contract** — the by-ref shape, the `DL-NNN` token, `dl_number`, the writeback outcomes — and the **v3 API substrate**, not this code.

The declared set itself is read from the **fork point**, which the PR cannot edit, and head may only widen it — so it runs on every PR, and a **non**-release one asserts no member but is still refused if it drops a declared entry without acknowledging it in `retired_artifacts`. `docs/INSTALL.md` §6c owns the classification rule and what the check reads |
| `bin/release-tag-check` | post-merge, refuse to report a release as shipped until its tag actually exists. `auto-tag-version.yml` and `release-promote-cards.yml` both fire on `push: main` as independent runs with no `needs:` between them, so the promote side wins the race on **every** release and used to stamp cards "Released to main" before the tag was created — and on one release the tag never arrived at all (the tag push took a 403) while promote still reported success. This **waits** for the tag rather than refusing on sight (an immediate refusal would red every release), then **fails loudly** if it never appears, or if it appears at a different commit. A remote it could not READ is a third outcome, never scored as an absent tag: each poll is bounded, `git ls-remote`'s own error is kept, and the refusal at the bound says the tag is UNMEASURED rather than blaming the tagging workflow. A non-release push asserts nothing: the release classification is delegated to `release-artifacts-check --classify-only`, so there is one definition of "this range is a release", not two. WHICH tag it waits for is delegated the same way — to `release-pr-body --tag`, the one reader of `.release-pr.json`'s `tag_format` — so a repo on a non-`v` scheme is asserted against the tag that scheme actually produces (it hardcoded `v<version>` until card#7203, which made it wait out its whole bound and refuse **every** release for such a repo). It reads refs only — it needs no write permission and widens no token |
| `release-artifacts/action.yml` | SHA-pinned composite-action wrapper around `bin/release-artifacts-check` for GitHub-Actions consumers (INSTALL.md §6c) |
| `release-tag-check/action.yml` | SHA-pinned composite-action wrapper around `bin/release-tag-check` for GitHub-Actions consumers (INSTALL.md §6d). Wire it as a step BEFORE whatever reports the release — a gate placed after the thing it guards guards nothing |
| `bin/board-snapshot` | session-start board snapshot |
| `bin/board-stats` | per-board **stock + flow** report over one board (`--board <name>`) or every board in the roster (`--all`, the default), as text or `--format json`. The two sections come from two different surfaces on purpose: **stock** (per-column card counts, plus the oldest card's age in the pullable columns) is a *state* question and is read from the card snapshot; **flow** over a `--since 24h`/`7d`/past-ISO window (cards created, every stage-changing `from -> to` transition counted and split human/service, swimlane-only moves counted separately as **same-stage moves** rather than mistaken for transitions, resolutions listed **per destination stage**, and each terminal→non-terminal move as its own **wash** row) is a *rate* question and is read from the board **changelog** event log — never from a card's `last_stage_move`, which is a snapshot field and therefore loses a multi-hop card's intermediate transitions, hides a resolution that was later washed, and reports a release batch as fresh resolutions. Terminal/pullable stages are **derived from the board's own `lane_type`** (`done` / `backlog_inventory`), with the board env's `KB_STAGE_*` ids as a per-key override, and a class that ends up empty is reported rather than rendered as zeros. A window the log cannot fill is never reported as a complete one, on either of the two routes it can fail by: a **stop** that bounds it (the page cap, or a changelog that does not reach back to the cutoff) is flagged truncated and carries the oldest timestamp the log holds, while a page the tool could not **read** — no response, a non-2xx, or a 2xx carrying no event array — ends the walk and is named on the board's own ⚠ line as an incomplete window whose counts are a floor. **A floor says so ON THE NUMBER, not only on the line above it:** a partial card read prefixes every stock count and queue age with `≥`, and a partly-read window does the same for every flow count, so a value cannot be read as a total even quoted out of the ⚠ that qualifies it — and the two states are separate, so one section can be floored while the other is not. A genuinely empty log is neither: zero events is what it holds. Read-only; fail-soft per board (an unreadable board is reported, never omitted, and the report says it is partial) |

| `bin/next-dl` | next `DL-NNN` number — **atomically claims** server-side when the board exposes the DL-sequence endpoint (race-free; DL-157), else offline `max+1` over local `## DL-NNN` headers **plus** the board's stamped `dl_number`s, which **refuses** rather than mints if that board read is not whole (card#6631). `--peek` = non-consuming read of that same counter (falls back to `max+1` only when the endpoint is absent). **Every fall-back to the offline scan is announced on stderr, naming which of the four causes fired** (config unresolved / unreachable / `404`-absent / a `2xx` carrying no usable value — one line each, because one generic line hides the difference that decides what an operator does next), and **`--require-counter`** turns the fall-back into a **refusal at rc 4** for a caller that needs an atomic number or none (card#7214) |
| `bin/board-card-start` | move a feature branch's correlated card to In Progress (idempotent, fail-soft) |
| `bin/adopt-to-dl` | **pull-into-build adoption seam:** stamp an existing plain card with `dl_number` + a source-qualified placeholder `pr_url` in one atomic write (via `next-dl` + `kbcard patch`), then fail-loud-verify by `by-ref?system=dl&ref=N&source=<repo>`. Refuses to re-mint over an already-adopted card (`--dl N` re-stamps idempotently for a crash-retry) |
| `bin/install-board-hooks` | install the `post-checkout` (card auto-move on branch checkout) + `pre-push` (fail-soft branch-name advisory) hooks into a repo — by **symlink**, after probing that this seat can make one; a seat that cannot is refused rather than pinned to silent copies (`--allow-copies` opts in, and reports them as copies) |
| `bin/agent-board-toolkit-drift-check` | verify a repo's vendored copy of a tool matches this toolkit |
| `bin/agent-board-toolkit-runtime-check` | what `agent-board-toolkit-drift-check` is for a vendored copy, but for the **`PATH` install itself**: resolves each on-PATH tool through its symlink chain to the runtime that actually executes, and fails loud on a stale runtime (a pin left behind **or** a clone that never pulled — the remediation it prints branches on which), stale copies, or a mixed-runtime split (`board-snapshot` runs it quietly at SessionStart) |
| `bin/dependabot-deploy-reconcile` | **does the fix a CLOSED Dependabot alert claims actually exist in what is deployed and running?** An alert closes when its fix reaches the default branch; production serves something cut by a separate process, so a repo reading 0-open can be serving the vulnerable version with no symptom. Implements one leg — an installed npm dependency tree, resolved from the MCP config that launches the deployed server (never a hardcoded path) — and compares each alerted package's installed version against the alert's own `first_patched_version` under SemVer 2.0 precedence. Fail-closed: `FIXED_CONFIRMED` / `STILL_EXPOSED` / `PROCESS_PREDATES_TREE` / `UNDECIDABLE` / `UNVERIFIABLE`, never a silent skip. **The read is bound to the RUNNING process, or it is not an answer:** a version read off disk is a claim about a file, while the question is about the code a live process loaded, and the two part company the moment the tree is written after the process started (`npm ci` into the install of a server nobody restarted). Every run compares the oldest running process's start time against the newest write anywhere under `node_modules` and, whenever it reports at all, **states the binding** — measured either way, or an explicit `NOT MEASURED` where the run died before the tree scan, because a report that only speaks up on trouble cannot be told apart from one that never looked — with that binding's own limitations printed beside it (mtime is the only evidence, so a timestamp-preserving replacement reads as unchanged; the binding is tree-level, so one write unbinds every row). A tree written after the process started is `PROCESS_PREDATES_TREE`, its own word rather than one more `UNVERIFIABLE`, because it is the state that silently turns every other row into a confident answer about the wrong artifact — and such a row still carries what the tree **on disk** says (its `installed_version`, plus an explicitly on-disk verdict in the detail and in `on_disk_disposition` where that read succeeded), because a word for what cannot be known must not also erase what is. Other channel-server installs detected on this host get a stated `UNVERIFIABLE` line each — named and never measured, not skipped. Every alert query passes a series of gates — deliberately **not** enumerated here, because this list was incomplete twice before anyone noticed; `tests/dependabot-reconcile-selftest.sh` asserts each gate can fire and is the authority. Their shared purpose: a wrong answer at HTTP 200 must not read as a real one (that includes summing all four per-state counts against an unfiltered query, so a short read of the *population* is caught too), because this API answers 200 with `[]` for an *unknown* state value — a typo'd filter reads as an empty population at a success status (a mis-cased *known* value is filtered case-insensitively, so it is the enum guard and not casing luck that keeps a typo out). **Fixed scope, host-local by design:** alerts are queried for `PupFuzz/agent-webhook-bridge` only, and the deployed directory is resolved from this host's `kanbanboard-agent` MCP server entry — it is the agent host's own session instrument, not a vendorable per-repo tool. A host with no such entry is *not configured*, not broken: one line, no artifact, rc 0. Read-only apart from its JSON artifact under `~/.cache/coord/dependabot-reconcile/`; runs no git command; advisory step of `board-session-close` |
| `bin/dl-a1-register-field` | **DL-board setup:** register the `dl_number` custom field + real-surface-verify the `system=dl` by-ref derivation, then fully remove the throwaway (idempotent) — so the toolkit can *stand up* a DL board, not just operate one |
| `bin/dl-a0-backfill-triaged` | **DL-board setup:** backfill the `triaged` tag onto pre-existing `id:*-pr-*` cards (dry-run default; `--apply` / `--remove`), so untriaged-discovery doesn't read the legacy corpus as untriaged |
| `bin/gh-code-search` | **a GitHub code search that refuses to report a count GitHub has said it cannot stand behind.** `GET /search/code` answers **HTTP 200** with **`total_count: 0`** on a private repository — for a term that certainly exists and a term that cannot exist alike, byte-identically — so the ordinary spelling (`gh api search/code --jq '.total_count'`) hands back a `0` that reads as a finding, and cross-repository claims ("this codebase never emits X") get made from a search that never ran. The discriminator, `incomplete_results`, is already in that body and the `--jq` throws it away. This tool's contract is **error / partial / complete — never a count**, carried by the **exit code**: **0** COMPLETE, **3** PARTIAL (flagged, with a non-zero count **and** at least one item — the matches are printed and usable, the count is not authoritative, and the non-zero rc is what stops a caller consuming it by default), **4** UNANSWERED (flagged with **nothing to stand on** — a count of zero, an **empty item set**, or both — fatal; **no result set is emitted at all**, because an empty result set is precisely the wrong answer. Either half reading empty is enough, and the union is measured behaviour rather than a widening for symmetry: `{"total_count":17,"incomplete_results":true,"items":[]}` is **rc 4** with `results=WITHHELD`, because the count is an ESTIMATE and so is not evidence that results exist, while the item set is what was actually measured and so an empty one is not evidence that they do not), **1** ERROR (`gh` exited non-zero, or a 200 body that is not a readable code-search envelope — a secondary-rate-limit object, an HTML error page, a mistyped field: **an unreadable response is not an empty one**), **2** usage. `total_count` never appears without `incomplete_results` on the same stdout line or in the same JSON object, and is always tagged **ESTIMATE** — code search coarsens it with magnitude and `search/*` counts drift between identical calls, so it is never an equality or threshold input; a caller needing an exact figure must paginate `items`. **No modulus and no stability heuristic are encoded** — both were proposed, both were refuted (`repo:laravel/framework class` → 2460 is not divisible by 8; every `incomplete_results: false` sample either seat has taken was a consecutive repeat of an identical request, so "stable ⇒ trustworthy" is confounded with caching). Every refusal names the way through: `git/trees?recursive=1` to enumerate paths, then `contents` to read them — measured working on the same private repo and token that code search cannot answer for. One request, no pagination; a full page is reported `items_truncated=true`. `--format json` for machine consumers. Read-only |

Since this is the *only* list of the tools (ADOPTION.md points here rather than keeping a second copy), CI asserts it: [`tests/readme-bin-coverage-selftest.sh`](tests/readme-bin-coverage-selftest.sh) fails the build on a tool with no row **or** a row with no tool. That gate compares **names only** — it cannot tell you a row's description is still accurate.

## Configuration model (no IDs are hard-coded; nothing secret is stored in this repo)

The tools read all environment-specific values from files **outside** this repo:

- **`~/.kanban-host.env`** — the **host-level, board-independent** settings every tool reads: `KBCARD_API` (the api base) and `KANBAN_EXPECTED_HOST` (**required, no default**). `KANBAN_EXPECTED_HOST` is now load-bearing for *every* tool, not just the promote/checkout guards: the resolved `KBCARD_API` is preflighted against it, and an api host nobody declared is a **refusal**, not a fallback. Optionally a host-wide `KBCARD_TOKEN_FILE` default. Template: [`examples/kanban-host.env.example`](examples/kanban-host.env.example).
- **`~/.kanban-<name>-board.env`** — board/stage/type/custom-field IDs, and this board's own `KBCARD_TOKEN_FILE`. One per board. **Not the API base** — `KBCARD_API` is host-level, and a board env that sets it is refused (see [`docs/INSTALL.md`](docs/INSTALL.md) §3). Template: [`examples/kanban-board.env.example`](examples/kanban-board.env.example).
- **`~/.kanban-<name>-token`** — a file containing **only** the bearer token (`chmod 600`, never committed). Token precedence: a board env's `KBCARD_TOKEN_FILE` > the host env's > an ambient one > the coord credential store's `[kanban] api_token_file` **pointer** (card#7316 — read POINTER-ONLY; an inline `api_token` value is refused, never read). **There is no baked default:** a board for which no tier names a token file is refused, naming the file to add the line to. `~/.kanban-dev-token` used to be that default, and one file standing in for every board is what let a single overwrite take all of them out at once (card#7245). The store tier is last because it is DISCOVERED — an operator's own declaration must beat one the toolkit went looking for — and a host with no such store is refused exactly as it was before that tier existed.
- **`<repo>/.release-pr.json`** — per-repo release config (only for repos that cut releases). Template: [`examples/release-pr.json.example`](examples/release-pr.json.example). **Security-sensitive:** its `.promote.api_base` is the host the release-CI writeback token (`KANBAN_WRITEBACK_TOKEN`) is sent to — a PR that edits `api_base` to an attacker host would exfiltrate the token on the next promote run. `promote-released-cards` / `board-card-start` therefore reject any `api_base` that is not `https://` on the expected host (`$KANBAN_EXPECTED_HOST`) before sending the token. **`KANBAN_EXPECTED_HOST` is REQUIRED — there is no baked default** (this toolkit is vendored onto operators' own kanban hosts, so it assumes none). **Pin `KANBAN_EXPECTED_HOST` in the promote-CI env** as a repo/org variable (out-of-band from the PR-editable config); if it is unset the guard fails closed and refuses to send the token. Treat any `api_base` change in review as a credential-scope change.

## Reliability posture (fail-loud / fail-closed)

The value-emitting tools never silently truncate a board read or emit a garbage value — a partial read that looks "complete" drives wrong reconciles (cards the tool never saw look absent → spurious creates / missed moves), and a garbage value stamped downstream corrupts state. That is a claim about shipped behaviour, not an aspiration, so the bullets below are its **exact quantifier** — where a boundary is still open they say so and say what is needed to reach it, rather than letting the sentence above cover it.

- **Loud-on-cap pagination.** A board listing that would exceed a page cap **fails loud** (exits non-zero, no partial output) rather than returning a truncated set. The cap is configurable:
  - `BOARD_PAGE_CAP` (default `50`) — `kbcard list`.
  - `PROMOTE_PAGE_CAP` (default `50`) — `promote-released-cards` (refuses to promote on a truncated board read).
  - `next-dl`'s fallback board-max scan refuses to mint when a configured board does not answer a whole read — a >200-card board that can't be scanned safely, and (card#6631) a board whose page 1 could not be read at all (the atomic claim endpoint is the race-free primary path and is unaffected).
- **A DL number that came from the offline scan SAYS so, and can be refused (card#7214).** `next-dl`'s primary path is the board's server-side atomic claim; when that counter cannot answer, it degrades to the non-atomic `max+1` scan — and that degrade used to be **silent**: rc 0, a number on stdout, an empty stderr, byte-identical on every channel to a reserved claim, so two concurrent allocators could be handed the same DL by the tool whose purpose is to prevent exactly that. Now **every degrade writes its CAUSE to stderr in that cause's own words**, and the four are kept apart deliberately — *this board's config did not resolve, so nothing was called* / *the endpoint could not be REACHED (transport failure, no HTTP status, so whether the route exists here is unknown)* / *the endpoint is NOT DEPLOYED (`404`)* / *it answered `2xx` but carried no usable number* — because "not there" and "could not reach it" prescribe different actions, and one generic line would re-mint the conflation being closed. The **disposition** line follows the cause and names the consequence (not atomic; a floor that cannot see a claimed-but-unstamped DL). `--require-counter` makes that disposition a **refusal: rc 4, nothing minted**. It is **opt-in and the default is unchanged** — a single-stream caller on an install whose kanban predates the DL-sequence route is safe on the scan, and flipping the default would start failing it; a present-but-errored endpoint still aborts at **rc 1** as before, with or without the flag. For an existing caller nothing changes but the appearance of a stderr line on the degraded path.
- **A filtered `list` names its denominator, and its projection is the filterable surface.** `kbcard list` emits a **fixed** row projection — `id`, `name`, `stage`, `type`, `swimlane_id`, `swimlane`, `external_id`, `tags`, `dl`, `pr` — so a downstream `grep`/`jq` over anything else (`description`, any other payload key) answers `0` no matter what the board holds; read a card whole with `kbcard show`, or hunt one **by its body** with `kbcard search`, which is the verb for that question (this projection cannot answer it at any width worth paying for — `description` is unbounded free text on every row of a whole-board read). One qualifier inside that set: `type` is the **native** `card_type_id`, so it is `null` on every row of an all-tag board (and on a mixed board's tag-typed cards), where the type rides `tags` as `type:<alias>` — select on `tags` there, because `--type <alias>` still matches those cards while a filter keyed on the projected `type` returns a confident `0`. And because a filtered `[]` is indistinguishable from an empty board, any filter flag adds one **stderr** line — `list <flags>: <M> of <N> board cards matched` — while stdout stays exactly the array it always was. Unfiltered there is no line: the array's own length is the denominator.
- **Fail-closed.** A non-2xx API response → exit non-zero with **empty stdout** (never a partial/garbage value); a non-positive/garbage id is rejected rather than sent. Empty stdout means "do not act."
- **A `2xx` nothing can be read out of is refused by the tool, in the tool's own words.** Success is decided on the **HTTP status class alone** — deliberately, because the shapes a body can take are not a reliable success signal (the un-suffixed comments path answers `404` with well-formed JSON) — which means a `2xx` carrying a proxy's HTML error page, a captive-portal interstitial or a truncated read reaches every projection as a success. One shared tolerant parse (`kb_parse_resp` in `_kb-board-lib.sh`) is applied at the **FIRST projection off a response body** — every single-card/field read and every write echo — **not at every `jq` in these files**: a value that has already come through it, or through a guard that refuses on empty, is projected bare afterwards on purpose (`_kbc_annotate_card` and the comment count are two such). **Three bare projections are neither, and are recorded rather than implied:** `archive`'s board projection and the populated-card census behind `field delete` and `field retype --restamp-dl` both read the paginator's output, not a `kb_api` body (the census additionally refuses on *every* non-zero paginator rc before its filter runs), and the `field` verbs project off `_kbc_fetch_fields`, whose non-empty guard admits a `.data` that is not a list — all three carry named blockers in [`docs/CONSOLIDATION-PLAN.md`](docs/CONSOLIDATION-PLAN.md). So an unreadable body yields an **empty value** that lands in the refusal each verb already has, at that verb's own documented rc, never a raw `jq` parse error at an exit status the tool documents nowhere. **The quantifier is exact, and the half it does not reach is named rather than implied:** the whole-board paginator `fetch_board_cards` is **not** on that parse — it reads each page with its own inline `jq … 2>/dev/null` — but it reaches the same posture by its own route, on **every page** (card#6594, card#6630): a body carrying no `.data` **array** is refused at one of the paginator's existing rcs — **rc 1** on page 1, where nothing of the board was read, and **rc 2** on a later page, the rc its contract already assigns to *a page > 1 failed mid-pagination* — instead of being reported as the `[]` a genuinely empty board returns, which the two were previously indistinguishable in (measured: `kbcard list` against a `200` carrying `<html>502</html>` gave `[]` at rc 0 with an empty stderr, and now gives rc 1 with empty stdout). The page selects the rc; the cause is the same one. **The refusal is unconditional; the paginator's stderr LINE is not.** That line is printed only under `KB_FETCH_LOUD`, which two of the six consumer bins set (`kbcard`, `dl-a0-backfill-triaged`); the other four — `next-dl`, `board-card-start`, `board-snapshot`, `board-stats` — read the paginator silently, which is what keeps a fail-soft display quiet, and each says so in its OWN words at its own surface. So "the tool's own words" is exactly right and "a line on stderr from the paginator" would not be. The predicate is the **envelope, not the row count** — a real empty result is `{"data":[],…,"meta":{…,"total":0}}` — so a **genuinely empty board is still a rc-0 success everywhere** and only an unreadable body refuses. Deliberately narrower than the co-vendored `promote-released-cards` mirror, which dies on zero *cards*: a mover can treat an empty board as never a working state, a read verb cannot. **One residual, named rather than implied** — the later-page half was the second, and card#6630's fix closed it **in this paginator** (and, in a second change, in the class's third instance: `bin/board-stats`'s cursor-paged changelog window, where the same envelope read as an exhausted log — measured, closed, and recorded in [`docs/CONSOLIDATION-PLAN.md`](docs/CONSOLIDATION-PLAN.md)): an unreadable body on page > 1 used to read as `[]`, which is a **short page**, which ENDS the scan, so the caller got rc 0 and a board it had only partly read. On a server that DECLARES `meta.total` the short-read census caught that at **rc 4** with a loud `INCOMPLETE` — this API declared it on every probe taken for card#6594, which was an observation and not a guarantee, so the SILENT case needed a server that omits it. **The census-caught case was not therefore harmless, and "a server that declares meta.total is unaffected" is measurably false** — rc 4 EMITS its partial array, and the two consumers that render on 3|4 rendered it: measured through the shipped bins against a page 1 of 200 rows with `meta.total: 201` and a page 2 of `{"error":…}`, `board-snapshot` printed a board line **derived from the truncated read** (`• Board 5 (kanban-board): in-flight 0`) with the `INCOMPLETE` warning on a stderr its SessionStart display does not show, and now prints `(board read failed — fetch rc=2)`. The refuse-policy consumers' disposition is unchanged on that server; only the rc in their message moves (4 → 2). It is now **rc 2** in the lib and a `die` in the mirror, reached *before* the census in both, because *page 2 was unreadable* and *the board is bigger than what arrived* are different operator actions. The census is unchanged and still runs. What remains: a board the token cannot see is answered by this API with the *same* well-formed empty envelope as a board with no cards, so that case still reads as an empty board here. The API behaviour is shared with the mirror; **the consequence is not** — `promote-released-cards` refuses it, because it dies on zero *cards* and can afford to (for a mover an empty board is never a working state), while `fetch_board_cards` must not adopt that predicate at all: a read verb has to let a genuinely empty board succeed, so a zero-row refusal would refuse a legitimate read. Closing this residual needs a membership signal the envelope does not carry, not a stricter row count. Every consumer of the paginator inherits the refusal, and what each does with it is its own documented policy — the dispositions below are the **rc-1** (page-1) ones; a page-2 refusal arrives as rc 2, which every consumer already had a disposition for, unchanged and registered in `tests/fetch-board-cards-caller-claims-selftest.sh`: `kbcard list` and `dl-a0-backfill-triaged` abort, `board-snapshot` prints `(board read failed — fetch rc=1)`, `board-stats` marks the stock section unavailable, `board-card-start` skips the move rather than falling through to a card-id token, and `next-dl`'s fallback board-max scan **refuses** on rc 1 as it already did on rc 2/3/4 — it used to keep a fail-soft posture there and mint from the local `CLAUDE_DECISIONS.md` scan alone with the board's DL floor dropped, which is how a used DL gets re-minted; that residual was **card#6631** and is closed (measured through `adopt-to-dl`: against a board answering `200` + `<html>502</html>` with a local floor of `DL-0300`, the old path stamped **DL-0301** on the card, and the new one aborts before any stamp with the reason on stderr). **Two bounds, stated because the refusal is not total — and the line is resolve-failure vs fetch-failure, not "a board is configured" vs "no board is configured":** a **resolve failure**, where no request is issued at all — `bin/next-dl`'s own header owns the member list, and it is not copied here, because the copy that used to stand in this spot named rcs 3/4/5 and went stale the day `kb_resolve_env` grew rcs 6 and 7 (an api host nobody declared; no token file declared) — and a **complete, successful read of a board that carries no `dl_number` stamp**, which exits `board_dl_max` the same way a resolve failure does. Both still mint from the header scan alone, and a named, reachable board reaches either — `bin/next-dl`'s own header and exit-code note own the enumeration, and name the known-open cases where a board answering `200` still minted. `kbcard archive`'s twin check swallows the rc and substitutes `[]`, which is the safe direction and is now measured rather than argued: the same card with an empty census returns `blocked … no surviving twin — archive withheld (fail-closed)` where a populated one returns `ok`, so a failed board read can only withhold more archives, never permit one. Two consequences worth relying on: a **read** never reports "no such card" / "no comments" / "no custom fields" for a body it could not read (those are claims about the board, and a read that never reached one cannot make them), and a **write** whose echo is unreadable is reported as UNCONFIRMED rather than printed. **One measured exception to the first, stated because a known hole is worth more than a clean sentence:** `comments` tests its list with `(.data.comments // []) | select(type == "array")`, and jq's `//` substitutes its right-hand side for `false` as well as for `null` — so the container test never sees a `comments` of `false`, and `{"data":{"id":505,"comments":false}}` prints **"card 505 has no comments" at rc 0**. The fix is known and moves that verb from rc 0 to rc 1, i.e. a change to what a **read** verb accepts, so it is ask-gated and open; it is filed with its now-closed write-path twin as one class in [`docs/CONSOLIDATION-PLAN.md`](docs/CONSOLIDATION-PLAN.md). What this does **not** cover, and one place it deliberately does: a `2xx` that is valid JSON of the wrong shape still reaches some **read** projections as an empty-but-plausible value, or exits at jq's rc 5 where the projection then indexes it — rejecting it there would change what those verbs *accept*, which is a separate decision. The exception is the one read whose result is re-sent as a **wholesale replacement** of what it read: `patch --tags/--type/--triaged` shape-tests the tag read — `.data` must be an **object** and its `tags` must be an **array** (or absent/null) — and refuses at **rc 2 with no PATCH** otherwise. Both halves are load-bearing, and so is the ORDER the second one is applied in: `{"ok":true}` and `{"data":null}` parse cleanly and yield `[]`, so a tolerant parse alone would let them destroy every tag on the card; a `tags` that is a JSON **object** does not fault either, because jq's `map` iterates an object's *values* — `{"tags":{"0":"keep-me"}}` with `--type` wrote `["keep-me","type:fr"]` and dropped every other tag; and the container test runs on the **near side of the `// []` default**, because jq's `//` yields its right-hand side for `false` exactly as it does for `null` — with the test downstream of that default, `{"tags":false}` was handed `[]` and `--triaged` PATCHed `{"tags":["triaged"]}` at **rc 0**, the same wipe reaching through the guard a third way. What the array **contains** is deliberately not tested (`{"tags":[1,2]}` still patches `[1,2,"triaged"]`) — that would change what this verb accepts and is a separate decision.
- **Fail-soft display/hook tools** (`board-snapshot`, `board-card-start`, hooks) stay non-blocking by design (a hook must not abort a checkout), but surface a **loud notice** on a truncated read rather than presenting it as complete — **on the channel that tool's consumer actually reads**, which is the half that makes the claim mean anything: a notice on a stream the consumer discards is not one. For `board-snapshot` that is **stdout**, the only stream its SessionStart hook surfaces (every count of a partial read carries a `≥` and each section carries its own `card list INCOMPLETE (fetch rc=…)` note — card#6365; the paginator's own `INCOMPLETE` line goes to stderr, which that hook throws away). A board it could not read **at all** says so in **both** sections too, for the same reason: an empty untriaged section under a header promising that none may be silently missed is a completeness claim about a board nobody read. For `board-card-start` the channel is the **durable log file**, because the installed `post-checkout` wrapper discards both streams.
- **Token never in argv.** Every API call feeds the bearer token to `curl` out-of-band via a stdin herestring (`-H @- <<<…`), never as a `-H "Authorization: Bearer …"` argv token — so it can't leak via `ps aux` / world-readable `/proc/<pid>/cmdline` on a multi-user host. The herestring also redirects a regular temp file onto fd 0 rather than a `/dev/fd` named pipe, so it works on native mingw64/Git-Bash curl (where `-H @<(…)` process substitution fails to open its fd).
- **Fail-closed host guard.** Before the writeback token is sent, the config-supplied `.release-pr.json` `api_base` is validated to be `https://` on the expected host (`$KANBAN_EXPECTED_HOST`, or a subdomain of it); a mismatch **refuses to send the token** (`promote-released-cards` exits non-zero; `board-card-start` warns loudly and stays fail-soft). `KANBAN_EXPECTED_HOST` is **required with no default** — if it is unset/empty the guard also fails closed, so an operator must set it in their promote-CI env for the token ever to be sent.
- **Fail-closed api-host preflight — and it covers the host env, not just the committed config.** The guard above judges the PR-editable `.release-pr.json` `api_base`. A second guard, on the same `$KANBAN_EXPECTED_HOST` and the same RFC 3986 authority parser, judges the api base the tools actually resolve from `~/.kanban-host.env` (or `$KANBAN_HOST_ENV`): before any token file is located, the resolved `KBCARD_API`'s host must be the declared host or a subdomain of it, or the run **refuses at setup** — `kbcard` and the `--board`-driven tools exit 2, `board-stats` exits 1, `board-snapshot` prints a SKIPPED line and stays non-blocking. Its predicate is the **host alone** (an `http://127.0.0.1` board is a legitimate install — with one exception that is not this guard's: `board-card-start` additionally requires `https://` before sending the token, so card automation on checkout does not run on a plaintext board; docs/INSTALL.md §3), and an unset/empty `KANBAN_EXPECTED_HOST` refuses too, because with nothing declared every host is unrecognised. This exists because an unrecognised endpoint used to surface twenty minutes later as an `HTTP 401`, long after a config rewrite nobody noticed (card#7245).

## `kbcard` free-text flags — the file form is the convention

The three `kbcard` flags that carry **prose** — text long enough that someone other than the caller may have written it — come in pairs: `--name` / `--name-file` and `--description` / `--description-file` on `create-card` and `patch`, `--content` / `--content-file` on `comment`. Pass **exactly one** of a pair — both is `rc 2`.

**Use the file form for any text you did not author yourself** — a description written by someone else, a bug report, a pasted log, a review comment. An inline value is expanded by the **caller's shell** before `kbcard` is started, so a `$(…)` or a backtick anywhere in that text **runs as a command** on the invoking box, and `argv` already holds its output by the time `kbcard` can look at it. Nothing in the tool can detect that — the expansion happened in another process — which is why this is a **convention plus a safe route**, and deliberately **not** a validator: a `$(`-sniffing check on the inline flag would be a check incapable of detecting the thing it names. The file form is the safe route because its bytes are read by `kbcard` itself and never meet a shell.

- The file argument is a **path**, absolute or relative. `-` is refused **by name** — it is not a stdin token here. The claim is about the token, not the descriptor: a caller who means stdin passes the path `/dev/stdin`, which is read like any other path.
- A missing, unreadable or **text-free** (empty / whitespace-only) file is `rc 2` **before any request**, so a bad invocation costs no traffic.
- What a file puts on the wire: interior newlines and leading whitespace **verbatim**, **trailing newlines trimmed**, and **CRLF normalized to LF** — a file written on Windows/Git-Bash would otherwise send a literal `\r`, which a reader renders as `?` at the end of every line; a *lone* `\r` is not a line ending and is left to that sanitizer.
- **`--content` applies all of that to its inline value too** (that pair is also *required* — neither source is `rc 2`, because for `comment` the text **is** the request). `--name` / `--description` are optional field setters whose inline value rides **verbatim**, exactly as it always has; an omitted pair leaves the field alone.

## `kbcard field` — custom-field schema

Per-board custom fields define which keys a card's `tasks.payload` may carry (an unregistered key 422s on a task write). The `field` verb reads that schema, reconciles enum option sets, and owns the definition lifecycle (create / delete / re-type). Board selection uses the global `--board` flag, like every other `kbcard` verb.

- **`kbcard --board <key> field list`** — list the board's custom fields (`id` / `key` / `label` / `type`); `enum` and `multi_select` fields include their full `{value,label}` option set. Reads the board index (`GET /boards/<id>/custom_fields.json`) — the only field read surface (there is no per-field GET).
- **`kbcard --board <key> field create --key <k> --label <l> --type <t> [--options a,b,c]`** — define a new field and print the **created field id** on stdout; that id is the write verification, and a `2xx` carrying no id is reported as an **unverified write** (rc 1) rather than printed as a plausible `null`. `--type` is one of `string number date enum multi_select boolean url`. `enum`/`multi_select` **require** `--options`; every other type **refuses** it (the server stores the array and never interprets it — the same silent no-effect `set-options` refuses). A key already defined on the board is **rc 2 before the POST**: a key is unique per board, so creating over the top is not a re-type — `field retype` is (it converts the type in place).
- **`kbcard --board <key> field delete --field <name|id> [--orphan-values]`** — drop a definition, **fail-closed on the carriers it can see**. The board is enumerated first and the denominator `N of M board cards carry <key>` **always** goes to stderr, so a census that *ran* and returned zero is distinguishable from one that never ran. With `N > 0` this **refuses (rc 2)** unless `--orphan-values`, which still prints a loud warning naming both consequences below. A board read that failed or came back **incomplete** (page cap, short read) refuses at rc 1 — a truncated denominator is not a denominator, and the dangerous shape is precisely a truncated read whose visible cards carry nothing. ⚠ **That refusal covers the incompleteness the read can DETECT, and one blind spot it cannot.** The census is `GET /tasks/search.json`, which applies the soft-delete scope and `archived_at IS NULL`, while both consequences below are **board-wide** — the definition delete leaves `tasks.payload` alone for *every* carrier and `purgeField` is `board_id` + `field_key` with no archive and no trash filter. So a board whose only carriers are archived reports `0 of M`, does not refuse, prints no orphan warning and purges the index for all of them; un-archiving one puts an undefined payload key back into the live set. A complete read returns none of those cards and reports no rc, so nothing can refuse on them: the scope is **disclosed on the denominator line itself** (both consumers of that census inherit it), and whether the refusal should widen to carriers the tool cannot see is a change to what this verb rejects — recorded as a request, not made here.
- **`kbcard --board <key> field retype --field <name|id> --to <type> [--options a,b,c] [--accept-ref-impact] [--restamp-dl]`** — change a field's **type**, as **one call** on the server's atomic conversion route (`POST /custom_fields/<id>/change-type.json`). The server converts the **definition** and every stored `tasks.payload` value keyed by it in **one transaction**, rebuilds the search index for the key inside it, and touches no other attribute — `placeholder`, `mask`, `multiline`, `is_filterable` and `position` all survive, which the client-side delete-and-recreate this replaces could not do. This verb issues **no delete, no recreate and no per-card cast**: there is nothing left here for a crash to leave half-migrated, and the whole cast matrix / capture / stranded-board apparatus that existed to make that window survivable is **deleted**, not kept in step.
  - **There is no dry run, and none is simulated.** `--check` exists only on the server's own `php artisan kanban:change-custom-field-type`; the HTTP route does not take it. **Preview-by-refusal** is what the API offers instead: the whole board is scanned **before** anything is written, so a conversion any card value blocks answers **422** naming **every** offending card — each with a `category` (`source_nonconformant` / `projection_impossible` / `target_rejects` / `ref_impact`) and the validator's own message — and leaves the board byte-identical. The refusal **is** the preflight.
  - **`from_type` is always sent.** Resolving `--field` already reads the definition's current type (there is no per-field GET, so the board index is read either way), which makes the compare-and-swap free rather than optional — and a definition whose type moved between that read and this write is its **own** outcome (**412**, *the field's type changed under you*, nothing written), never folded in with a 422.
  - **`--options` is a passthrough.** Every rule about it belongs to the server and is surfaced verbatim rather than re-derived here: options are **required** converting into `enum`/`multi_select` from a non-option source and are **never inherited from the stored column**, **optional** between the two option types (omitted = carried over verbatim), **prohibited** otherwise, and — the fourth, which is the one a re-run reaches — **refused on a request that does not change the type at all**, where `assertOptionsMatchTarget` (which runs *before* the same-type no-op short-circuit) calls them an *options edit* and sends them to `PATCH /custom_fields/<id>.json`. That last one is why a landed conversion carrying `--options` does **not** answer a re-run as a no-op: it answers **422**. The comma list is turned into the server's `[{value}]` wire shape and sent; nothing else about it is this tool's opinion. The list is split and trimmed, and an empty value or an empty list is refused before the wire — those two **are** the server's own rules (`options => array|min:1`, `options.*.value => required`), reached by derivation and not by coincidence, so they refuse nothing the wire would have accepted. ⚠ **One documented exception:** a **duplicate** value is refused at **rc 2** by this tool and the **server has no uniqueness rule on an option set at all** (`assertOptionsMatchTarget` validates the array, the value's presence/type/length and an optional label, and nothing more). The rule is `set-options`' — a converge-to-set target must be distinct — shared by `create`, and it applies here too, so `--options a,a` never reaches the wire. The refusal **says whose rule it is**, so nobody is sent to argue with the server about a rule the server does not have.
  - ⚠ **`--options` REPLACES the whole option set, so between `enum` and `multi_select` it destroys the definition's explicit labels.** The server assigns `$locked->options = $options` outright, and a comma list carries no labels, so every value written this way ends up with `label = value` — the server's default for an omitted label. The run **names each label it dropped**, off the definition it had already read (no extra request). **Omit `--options`** to carry the existing set over verbatim, labels included.
  - **`--accept-ref-impact` is the second half of a two-call handshake, and it never skips the first call.** The one refusal that can be opted into is a conversion that would **move** a card's external-reference correlation. The un-acknowledged POST is always made; its 422 reports the exact card id set under `meta.ref_impact_task_ids`; only then is a second POST sent acknowledging **exactly that set**. The server re-derives the set under the row lock and refuses one that grew or changed, so a set this client guessed would either be refused or — if it happened to match — would launder the one gate that makes a correlation move deliberate. Without the flag the ids and the server's message are printed, nothing is written, and the rc is non-zero. The two `meta` keys are capped differently — `meta.offenders` is truncated at the server's reporting cap while `meta.ref_impact_task_ids` is not — so when the run acknowledges more moves than the refusal named it says so on this path too, rather than showing 50 and acknowledging 200.
  - **`--restamp-dl` is a separate pass after a successful conversion, not part of it.** The cast matrix's text rule for a `number` source is `json_encode`, so the stored number `1` converts to the string `"1"` — **not** `"DL-0001"`. Correlation itself is not at risk (the server canonicalizes `DL-028` / `28` / `#28` to one key), but a custom-field DSL filter written as `DL-0001` **string-misses** a card storing `"1"`, so the conversion alone leaves a DL migration half-done. Each populated card's value is rewritten through the **one canonical DL renderer** (`kb_dl_canon`, the same one `next-dl` and `adopt-to-dl` stamp through) and **verified by re-reading the card**; a card already holding the canonical form is left **unwritten**, so a re-run costs no writes. ⚠ **The pass sees a smaller population than the conversion did, and no run of it can tell you the field is done.** The server's conversion population is every carrier of the key **including archived and soft-deleted cards** (`candidateQuery` is `withTrashed()` with no archive filter); this pass's census is a board read, which returns neither. The run compares the server's own `meta.converted_task_count` against its census, and that compare is **one-directional**: where the conversion touched more, a remainder is **proven** — counted, reported as its own outcome, at rc 1. Where it did not, **nothing is proven either way**, because the two numbers are counts taken at two different moments rather than sets (a card entering the live set between the conversion and the census masks an archived carrier one for one), and because a re-run against the field's current type is the server's **no-op** — no scan, `converted_task_count: 0` — so the difference is structurally zero whatever the board holds. So **every line this pass emits that could be read as "done" carries the census scope with it, unconditionally**, naming which of the two states the run is in; those cards are never read and never written here, and un-archiving one puts a non-canonical value back into the live set. Seven outcomes are reported as the seven different boards they are: **canonicalized** · **already canonical** · **PATCH failed** (the write did not complete, so never counted as verified — and never claimed untouched either: the transport cannot tell a timed-out `PATCH` the server committed from one it never received) · **read back different** · **the verification read could not observe it** (state UNKNOWN — a failed GET and a `2xx` carrying no readable value are the same non-observation, and neither supports a claim about that card) · **not a DL number at all** · **outside this pass's census** (the remainder above). Requires `--to string`.
  - **Every other outcome is reported as itself**, with the server's own body on stderr: **413** the conversion is over one of the server's **two** resource rails — the board-scan rail counts the board's cards, the examined-carriers rail counts the cards holding a value for *this field*, so the client names neither and the server's own message (echoed, because it also carries the operator-supervised escape hatch) says which — **404** the definition was deleted since the run read the field index, **422** in three shapes rather than the two the endpoint documents — the conversion's own refusals both carry `meta` and are told apart by the presence of `meta.offenders` (named cards vs a **pair** refusal: no conversion exists between those two types at all, decided before a single task row was read, so no card is at fault), while the **option rules** are a plain `ValidationException` carrying **no `meta` at all** and are reported as what they are, a request the server rejected as invalid (measured on the sandbox: reporting that third class as a pair refusal told the operator a conversion the server *does* define does not exist) — a **transport failure** (`000`, which every non-zero `curl` exit collapses to) an **UNKNOWN** outcome rather than a safe one — a timed-out or reset write may already be committed, so the run says it cannot tell and names the idempotent re-run — and a **`2xx` nothing can be read out of** an **unconfirmed** conversion at rc 1 that deliberately does **not** go on to restamp: the write landed, but this run cannot say what it landed as. **What the run tells you to re-run depends on the command it was given and on whether the arm can tell that it landed**, and the sentence is one owner fed both: without `--options`, re-running the exact command is safe on either arm — the conversion half answers as a server-side no-op. **With** `--options` there is no directive that is true both ways, because once the conversion has landed the identical command is a same-type request still carrying options, which the server refuses (422) as an options edit belonging to the `PATCH` route, while a conversion that has **not** landed still needs them. So the two arms say different things. The unreadable-`2xx` arm names the re-run **without** them outright — its `2xx` **is** the landed-ness guarantee, since the server does not answer `2xx` for a refusal. The `000` transport arm, which read no answer at all, prescribes the **definition read first** (`field list` — where the `412` arm already sends you) and branches on what it shows: the **target** type means the conversion **landed**, so re-run without `--options`; the **source** type means it did **not**, so re-run the exact command. That first step is correct whichever way the write went, which is the property no single directive on that arm can have. The `000` arm also prints the sentence **minus its restamp clause** — it names no pass on either branch, because it reports a response and only a `2xx` ever reaches the pass. On the unreadable-`2xx` arm, what the sentence says about the restamp pass depends on whether one was asked for: **with `--restamp-dl`**, the re-run also **runs** the pass this run skipped, and whether that pass *finishes* is its own reported outcome (a stored value that is not a DL number is canonicalized by no run of it); **without it**, the line names no pass at all — none was requested, so this run skipped none and a re-run runs none.
- **`kbcard --board <key> field set-options --field <name|id> --options a,b,c`** — an **idempotent converge-to-set** on an `enum`/`multi_select` field's options: after the call the option set equals **exactly** the given comma list, in that order. It reconciles by value (a second call with the same list detects no drift and **skips the PATCH** — a no-op it reports on stderr). Values only; each label defaults to its value (labels for retained values are not preserved across a rewrite). Refuses a non-`enum`/`multi_select` field, empty/duplicate values, and an unresolved `--field` (which then enumerates the board's defined fields). The consumer is a provisioning preflight that calls it with a full derived set and expects any drift to heal in one call.

> **Why `delete` is fail-closed, and why `retype` is not built out of it — two measured server behaviours** (pinned against the sandbox instance; both are load-bearing for anyone migrating a field by hand). **(A) Deleting a definition does not cascade to `tasks.payload`.** Resident values survive, orphaned, and are **never revalidated** — a later create over the same key leaves them holding whatever JSON type they were written as. **(B) Deleting *purges* the search-index side table for the key, and creating does *not* rebuild it.** Only a payload **write** touching the key re-indexes it. Composed, those make the obvious hand-rolled type migration — delete, create, done — produce a board that **reads migrated** (the definition says `string`) while every DSL filter on the key matches **zero** cards and every resident value still carries the old JSON type. Nothing about that state is visible without asking each card individually. That is why `delete` refuses a populated field outright instead of being the sharp half of a two-step nobody finishes. **`retype` does not compose those two routes at all**: the server's conversion route converts the definition and every stored value in one transaction and rebuilds the index inside it, so neither (A) nor (B) is on its path — and a type change made by hand through `delete` + `create` is still the trap above, which is what the refusal points at.

> **Observed option-removal semantic** (empirically pinned against the sandbox instance, board 1162; stated here and in `--help` because the server behavior is load-bearing for consumers): **removing an option is a definition-only change.** A card still holding a removed value **keeps it verbatim** in `tasks.payload` — the value is orphaned (no longer a defined option) but preserved, **not cleared and not cascaded**. **Whether the removal PATCH is refused, though, is a property of your server:** without kanban's DL-242 — in no kanban release through v0.41.0 — it is **not rejected** (HTTP 200) even while a card references the dropped value, and that card is stranded silently; with it, the same PATCH is refused **422**, naming the offenders, when the removal would strand a value the **current** definition still accepts. Two limits of that check, both easy to overstate: it is a **delta**, so a carrier whose value the current definition *already* rejects is skipped by design (refusing on it would leave the field uneditable, including the widening that would re-admit the value), and the board-**import** route still narrows unchecked — it is **not** the case that all narrowing is now checked. Either way `set-options` never mutates card data; converging a field's option set away from a value in use leaves that card's stored value intact (and now undefined). `add-option` / `rename-option` are intentionally not provided (deferred to v2).

## `kbcard comment` / `kbcard comments` — the card audit trail

- **`kbcard comment --task <id-or-ext> --content "text" | --content-file PATH`** — post a comment and print the **created comment id** on stdout. Text sourcing is the shared contract in [§ `kbcard` free-text flags](#kbcard-free-text-flags--the-file-form-is-the-convention), with the one difference stated there: this pair is **required** (neither source is `rc 2`, not a no-op — for `comment` the text *is* the request) and **both** its sources are normalized and blank-checked, so `--content "  "` is `rc 2` exactly as an all-whitespace `--content-file` is. A comment's own indentation is content and survives.
- **`kbcard comments --task <id-or-ext>`** — read them back, one block per comment (`comment <id> · user <user_id> · <created_at>` then the content, indented). Comment content is untrusted text going to a terminal, so every **C0 control character except the newline and the tab** (an embedded `ESC` is a terminal *command* — `ESC[2K ESC[1A` erases the attribution line above it) is rendered as `?`; the tab is exempt because it cannot move the cursor *backward*, so it cannot reach that line, while replacing it damages every pasted diff or indented block. The **header line's own fields come from the same untrusted body** and are sanitized too, more strictly — **every** C0 control there, newline and tab included, because a newline in `created_at` would forge a second attribution block where one in the content cannot (content is indented line by line). A card with none prints one explicit *no comments* line at rc 0 — a `2xx` **no comment list can be read out of** is never reported that way; it takes this verb's own `rc 1` refusal, per *Reliability posture* above (which owns that rule for every verb). Two body shapes are covered by it specifically because this verb renders rows rather than emitting them: a `.data.comments` that is **not an array**, and a row whose `content` is **not a string** — the latter would otherwise fail *part way through*, leaving a truncated audit trail that looks complete.

> **Measured semantics** (empirically pinned against the sandbox instance, board 1162), because each one is load-bearing for consumers: **(1)** adding a comment does **not** bump the card's `updated_at`, so the echoed comment id is the *only* cheap verification that the write landed — a success carrying no id is reported as an **unverified write** (rc 1) rather than printed as a plausible `null`. **(2)** There is **no comment read route** — `GET` on the comments path is `405` (POST only) — so `comments` projects the `comments` array the task-detail `GET` already carries, i.e. the same array `show` returns whole. **(3)** The request body is **flat** `{"content": …}`; the wrapped `{"comment":{…}}` form is refused (`422`). **(4)** The author is a bare `user_id` — that is the only author field a comment row carries. **(5)** `DELETE` on a comment is a **soft** delete — it `200`s echoing the row with `deleted_at` stamped, the row still live — and the task-detail array then **excludes** it rather than carrying it with that timestamp, so `deleted_at` is null on every row this read can return and is deliberately not rendered. **(6)** That array is **complete and ordered**, which is what makes projecting it an *audit-trail* read rather than a first-page one: **60** comments posted to one scratch card came back as **60** rows, `created_at` **ascending**, first and last matching the first and last posted, and the returned content set equal to the posted set (no gap, no duplicate) — the read is not paged and takes no page argument. Corroborated in the server's own source (`Task::comments()` is a `hasMany` ordered by `created_at` with **no limit**, eager-loaded whole by the task-detail resource), which is the argument that there is no cap at any *N*; the probe is what bounds the **observation** — no cap and no re-ordering at 60.

## `kbcard search` — find a card by what its body says

**`kbcard search <query> [--column COL] [--type ALIAS]`** — the board's own free-text search, printed as one **block per hit**: a `card <id> · stage <sid> · <name>` header line, then that card's **full `description`**, indented two spaces on every line. A card that matched on its name and carries no body says `(no description)` rather than printing an empty block, because an empty block reads as a rendering fault.

**Why the description is printed and not projected away.** `list` emits a fixed row set that excludes `description` (see *Reliability posture* above), so grepping a card **body** through it returns `0` whatever the board holds — the miss this verb exists to close. A search result that hid the field it had *matched on* would move that miss one layer over rather than fix it, so printing it is the verb's contract, not a formatting choice. The population is the server's match set, not the board, which is what makes printing unbounded free text affordable here.

**What the query is.** The endpoint's own `q=` token stream, sent **after** this board's `board_id=` term — a `board_id=` token of your own is ANDed with it, never swapped for it, so a query cannot retarget the read. The whole term is percent-encoded as one value, so a space, `&` or `#` in it adds no parameter. Practically: bare words are free text over `name` + `description`; **`name:<needle>` and `description:<needle>`** narrow to one column; and the rest of the DSL rides through unchanged (`tags:"x"`, `comments_count>=1`, `updated_at>:2026-08-01`, `custom_field_<key>:v`). A token the server does not recognise is **not refused** — it falls through and is searched as free text, so a mistyped filter silently becomes a word search.

**How a free-text word matches is the server's rule, and it is not one rule.** On the MariaDB instance each word is required and matched as a **prefix** through the `FULLTEXT(name, description)` index — `cat` reaches `category`, not `concatenate` — while a query carrying any word shorter than the index's minimum token length (the server pins that at **3**, MariaDB's default) falls back to a **literal substring match of the whole term**, which is a *phrase* and not an AND of words. If a multi-word query gives a surprising answer, suspect that fallback first — measured live against a real board: `pagination` matched **5** cards, `pagination truncated` **2**, and `a pagination` **0**, because the one-character `a` is under the minimum token length and routed the whole phrase to the substring path. **Comment text is not searched**: this endpoint's free text is `name` + `description` only, and `comments_count<op>N` filters on the **count**, never the content.

**Refusals and denominators.** `--column` / `--type` filter the matched set client-side exactly as on `list`, and add the same `<M> of <N>` stderr denominator line. A search that matched nothing prints one explicit line at **rc 0** — never a silent empty stdout — and a query that *did* match cards which the filter flags then removed says **that** instead, because they are different answers. A blank or whitespace-only query is **rc 2 before any request**: it matches every card on the board, which is not a search. An incomplete board read is **rc 1 with nothing printed** — a match set missing whatever was on the page that failed reads as *not on the board*, which is a wrong answer rather than a short one. Card bodies are untrusted text going to a terminal, so they pass through the same C0 sanitizer `comments` uses (the header line's fields under the stricter half of it).

`VERSION` holds the toolkit's semver.
