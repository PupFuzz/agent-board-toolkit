## [Unreleased]

### Added
- **card#5766** — **`kbcard list --swimlane none` (or `0`) filters to the LANELESS cards.** The write side could create a state the read side could not query: `create-card --swimlane none` (card#5671) and `patch --swimlane none` (card#4714, v0.19.0) both deliberately birth or leave a card lane-free, while `list --swimlane none` resolved `none` as a lane *name*, found no `KB_SWIMLANE_*` mapping, and failed rc 2 "swimlane 'none' is not defined on this board". That asymmetry was left open on purpose in #209 — widening what `list` accepts is a different decision from adding a create flag — and routed to the operator who actually runs lanes. **The answer came back as a census, not a preference** (roundtable #205, sola-pm, board 3 / 721 cards): laneless is not a transient state there but a standing **7%** — 50 cards, of which 23 are legitimately lane-free, 1 is genuinely cross-cutting, and **26 carry a `sola-<repo>:` title prefix naming exactly one repo**. The competing "laneless because untriaged" hypothesis was tested and does not survive (two spot-checked members are both tagged `triaged` and sit in `shipped_to_dev`), and a control rules out the prefix being a laneless dialect (the same prefix appears on 25 of 671 *laned* cards — the 52%-vs-3.7% concentration is the anomaly, not the convention). The decisive point is not that those 26 are misfiled — that is *unestablished, and unestablishable*, because no query returns them; they surfaced only as a side effect of answering the question. **The trap this deliberately avoids:** `_kbc_swimlane_value()` maps `none` → JSON `null`, and the list filter treats JSON `null` as *filter absent* — so the naive reuse of the write-side rule returns the **entire board** while looking correct. The filter is therefore transported as a **string** (`--arg`, absent = `""`) rather than JSON (`--argjson`, absent = `null`), which keeps "filter absent" distinguishable from "filter on laneless" and makes the laneless value the projection's own existing key for a lane-free card, `(null | tostring)` == `"null"` — the same key derivation the name-map lookup already uses, not a new comparison. The `none`/`0` spelling is hoisted into one owner, `_kbc_swimlane_is_laneless_ref()`, now shared by all three call sites (canon #5 — extracted at the third real caller, not copied a third time); `0` counts because lane ids are positive, so it never named a real lane, and it must be recognised *before* `swimlane_id()`, which passes any numeric through unvalidated. **Unchanged, and now extended to `list`:** a lane literally *named* `none` is unreachable by name and must be addressed by id; a typo'd lane name still fails rc 2 and enumerates the board's defined lanes. **Validated on a real swimlaned board** (a sandbox board carrying an actual lane, not a synthetic fixture): with one laned and one lane-free probe card present the populations genuinely differ — whole board 9, `--swimlane none` 8, `--swimlane 0` 8, `--swimlane <name>` exactly the laned probe — so the whole-board regression was *observable* there rather than hidden behind a board where every card happens to be laneless; probes hard-deleted, zero residue. All 13 new assertions were driven RED by five targeted mutations (JSON transport restored → the filter returns all 3 of 3 synthetic cards; laneless branch removed → `none` rejected rc 2; the `0` arm dropped; the predicate forced true; the laneless key derivation diverged), each reverted with the binary confirmed byte-identical after.
- **card#5671** — **`kbcard create-card --swimlane <name|id>` births a card directly on a lane** (roundtable #205, sola-pm). `create-card` accepted 16 flags and `--swimlane` was not among them, so it fell to the unknown-arg arm with rc 2 and no write — while `patch` and `list` both advertised `[--swimlane NAME-OR-ID]` two lines away in the *same* usage block, which is what made it reachable by reflex. Minting onto a lane therefore required create-then-patch, leaving a laneless window any lane-keyed reader or automation can observe. The create `POST` honours `swimlane_id` at birth — measured on a swimlaned board and asserted by a GET re-read rather than by the 2xx — so the flag rides the create body directly, with no internal create+patch composition and no laneless window. `--swimlane none` (or `0`) births a card explicitly laneless; an unresolved name fails rc 2 **before any write**, and that strictness deliberately did not change (the defect was the asymmetry that made the flag reachable, not the check that caught it). Shipped in #209; this entry was omitted from that PR and is added here — the gate that would have caught the omission is filed as card#5767.

- **card#5389** — **`agent-board-toolkit-runtime-check`'s `TOOLS` array was a second hand-maintained enumeration of `bin/`, it under-covered by 3 of 13, and its comment claimed it was derived.** The comment read *"every `bin/` entry of the runtime this script itself belongs to, falling back to the known names when run standalone"*; there was no derivation anywhere in the file (whole file read, not grepped) — the array was always the only tool set, and it was missing `dl-a0-backfill-triaged`, `dl-a1-register-field` and **the check itself**. The tool that exists to prove an install is honest could not see 3 of the 13 tools it installs, and said nothing about the gap. **Fixed by completing the list and GATING it, not by deriving it** (the card's (a)-vs-(b) fork, decided on measurement): a derivation is not available where it is needed — the script is standalone by design and runs from `PATH`, where under the copies topology the directory beside it is a general-purpose `~/.local/bin`, not a toolkit `bin/` — and (a) keeps a static fallback anyway, i.e. it is (b) **plus** a directory-sniffing heuristic, with the fallback still free to rot. A static list also behaves BETTER when this script and the runtime it judges are different versions: the ships-it-but-`PATH`-lacks-it warning re-checks `$root/bin/$m` per root, so a superset probe never cries wolf about a tool the judged runtime does not ship, whereas a derivation would have to pick one root's answer. Since the list ships in the same release as the `bin/` it enumerates, asserting set equality in CI gives every released runtime the same answer a derivation would. **The check itself is now in the set** — a stale copy of the checker is the one most worth reporting — resolved through `command -v` like every other tool, so running it by absolute path from a checkout that is not on `PATH` cannot make it report itself as a second runtime. **The gate READS THE SET BACK FROM THE TOOL rather than parsing its source:** on a `PATH` carrying none of the tools every name lands in `missing` and the no-roots arm prints the whole array on stdout, so the assertion is about the set the code ACTUALLY probes and survives any refactor of how the array is spelled — a source grep would instead pin the spelling and could pass over an array the code no longer reads. Driven **red** under three mutations against the live tree: a real bin dropped from `TOOLS` (named by the first direction), a phantom added (named by the second), and the readback channel broken by forcing `--quiet`, which fires both positive controls — the emptiness both absence assertions would otherwise pass on. **What a green run proves — the weakest property:** that two NAME SETS agree. Nothing about whether probing a given name is useful, nor about the legs that consume `TOOLS`. **Canon #5:** the public-`bin/` name rule now has two callers wanting it identically, so it is extracted to `tests/_bin-set-lib.sh` (`_public_bin_names`) and shared with `readme-bin-coverage-selftest.sh`; the other two `bin/` enumerations stay separate and each still states why at its own call site (card#5339's measurement — `no-task-wrapper-selftest.sh` must scan `_`-prefixed files, `help-output-selftest.sh` must skip directories). **Doc-sync:** the false header comment is replaced with what the code does, `runtime-check-selftest.sh`'s stale *"it deliberately does not scan itself"* note is corrected, and the `_public_bins` reference in card#5339's entry above is renamed. **⚠ This WIDENS what the tool reports on a real install** — an install whose symlink loop predates the `dl-*` tools now gets a warn-only install-gap line (rc unchanged), and a copy install carrying a stale `dl-*` or stale checker now fails rc 1 where it read `ok`; `bin/board-snapshot` discards the rc (`|| true`, `exit 0`), so SessionStart sees only the added message. **Filed, NOT fixed here:** `_kb-board-lib.sh`'s currency is never checked under the copies topology — a lib name cannot be on `PATH`, so it cannot enter `TOOLS` and the byte-compare never sees it; a stale copied lib beside byte-current copied tools reports `ok`, reproduced empirically with a positive control (card#5414). `promote/action.yml` is untouched, so no vendored surface moves.
- **card#5339** — **the `CLIS` registry that decides which CLIs get a `--help` assertion was hand-maintained, i.e. the same mechanism that missed a bin in the first place.** card#5334's repair for `agent-board-toolkit-runtime-check` — the one file card#5145's sibling audit never reached — was to APPEND its name to `tests/help-output-selftest.sh`'s `CLIS` array, so the N+1th bin to grow a `--help` was set up to be missed identically; fixing the instance without fixing the registry is canon #5/#7 left half-done. `CLIS` is now one half of a **completeness** assertion: every entry of `bin/` whose source carries `--help` must appear in `CLIS` or in a new `EXCLUDED` list, both directions asserted, and the three `EXCLUDED` bins (`adopt-to-dl`, `dl-a0-backfill-triaged`, `dl-a1-register-field`) each state their reason. **Deriving `CLIS` from the header idiom was rejected as WORSE than the status quo**, and the file says so: a CLI regressing from the `awk` form back to a `sed -n` range would drop OUT of a grep-derived required set and the suite would go green on the exact defect it exists to catch. The completeness form has no such hole — the required set stays hand-written and the derived scan can only ADD names to answer for. That same idiom grep does appear, but only to **challenge** an exclusion — a direction in which it can add a member and never silently drop one — so an `EXCLUDED` bin that later adopts the header form stops being excludable instead of sitting there silently; the three live `CLIS` members are asserted to carry the idiom first, as the presence witness that keeps the three `EXCLUDED` "does not carry it" checks from being a grep that can never match. The scan is the **broadest** matcher available on purpose: no comment filter and not the `-h|--help)` case-arm shape — a bin whose header merely discusses `--help` reads as unaccounted and goes red (noisy in the safe direction), whereas either narrowing could drop a real help arm silently. Directories are skipped because a directory has no source to scan — the **opposite** of the shared `_public_bin_names` (`tests/_bin-set-lib.sh`, extracted from `readme-bin-coverage-selftest.sh` by card#5389), which must not skip them; same directory, two checks, two correct answers, and the file says not to harmonize them. **What a green run proves — the weakest property:** for a `CLIS` member, that its `--help` reproduces that file's own contiguous header exactly (nothing about whether the header's PROSE is accurate); that every bin MENTIONING `--help` is named in one of the two lists — **not** that every bin offering help is, since one dispatching under another spelling entirely (`-?`, a `help` subcommand) mentions no `--help` and stays invisible; and for an `EXCLUDED` member, only that it does not use the header idiom — nothing about whether its help is correct or complete. **CHANNEL was outside this change and is asserted separately by card#5337, below, in this same release:** `adopt-to-dl` printed its usage to **stderr**, which this entry's assertions deliberately did not rule on in either direction, so the exclusion list encodes a FORM and never a verdict on that bug. - **card#5200** — **a hook that is executable but cannot be EXEC'd reported healthy.** The executable bit is not exec-ability: a hook with **CRLF line endings** or a **missing shebang interpreter** is `-x`, looks perfect, and makes git fail with `fatal: cannot exec '<hook>': No such file or directory` (verified against git 2.43) — so the card auto-move is dead while the check says ✓. ## [0.14.0] - 2026-07-15

**Minor — a security fix in the `api_base` host guard, plus the restoration of the board-env token precedence that v0.8.2 silently broke.** 2 PRs since v0.13.0 (#98, #97). Cards #4346/#4325.

**Read before upgrading — two consumer-visible changes.** (1) **[vendor]** a repo that vendored `promote-released-cards` **must re-vendor** to get the security fix; the vendored copy carries its own guard and does not track the toolkit. **[release-CI]** SHA-pinned action consumers get it with the pin bump (`promote/action.yml` is unchanged). (2) **[host]** if you set `KBCARD_TOKEN_FILE` in **both** a board env and `~/.kanban-host.env`, the **board's** token now wins where the host's silently did since v0.8.2 — a live change in *which credential is sent*. Full actions: `docs/UPGRADE.md` § v0.14.0.

### Security
- **SECURITY — the `api_base` host guard accepted a URL that sends the bearer token to an attacker-controlled host.** `kb_require_https_host` (`_kb-board-lib.sh`) and its standalone mirror `host_ok` (`promote-released-cards`) terminated the URL authority at **`/` alone**. RFC 3986 ends it at the first of **`/`, `?`, or `#`** — so with a delimiter placed before an `@`, the userinfo strip (`${h##*@}`) reached past it and lifted a fake host out of the query/fragment:

  ```
  api_base: https://evil.example#@kanban.your-host.tld
  guard parses host -> kanban.your-host.tld  -> ACCEPTED
  curl connects to  -> evil.example          -> bearer token sent to the attacker
  ```

  Because `api_base` is read from the **committed, PR-editable** `.release-pr.json`, a pull request alone was enough: for `board-card-start` a maintainer merely checking out the branch leaked their kanban token, and for `promote-released-cards` a repo running promote on untrusted config would leak the `KANBAN_WRITEBACK_TOKEN` CI secret. Neither required any access to `$HOME` or `git config`. Both copies now terminate the authority at `[/?#]`. Verified end-to-end against a listener standing in for the attacker: the pre-fix hook delivered the bearer token, the fixed hook sends nothing and names the real host in its refusal. Legitimate values — subdomains, `:port`, real `user:pw@` userinfo, queries — are unaffected.

  It survived because the guard had **no decision coverage**: it was wired and ran on every checkout, but nothing had ever asked it to judge a hostile URL. New `tests/kb-host-guard-selftest.sh` (+ CI job) pins the matrix and additionally asserts the two copies agree — they are sync-paired by comment only, and both carried the identical defect.

  **[vendor] Action required:** `promote-released-cards` changed, so a repo that **vendored** it must re-vendor (UPGRADE §3) to get the fix. **[release-CI]** consumers of the SHA-pinned composite action get it with the pin bump — `promote/action.yml` itself is unchanged.
### Fixed
- **A board env's `KBCARD_TOKEN_FILE` is honored again — the documented precedence is restored.** `kbcard` honored it from v0.4.2 through v0.8.1 (`v0.8.1:bin/kbcard:440`, *"after host + board env are sourced, so a config-file `KBCARD_TOKEN_FILE` is honored"*). The **v0.8.2 shared-library extraction** consolidated six divergent copies of the config resolution onto the two that had the source order backwards (`next-dl`, `dl-a1-register-field`) and **silently regressed** it: from v0.8.2 through v0.13.0 a board-env `KBCARD_TOKEN_FILE` was ignored and the host/default token was sent to every board. The docs were right; the code drifted. One ladder now serves every tool — **board > host > ambient > `~/.kanban-dev-token`** — as a property of source order (host sourced first, board second) rather than six hand-rolled precedence tests. **Operator-visible where a board env *and* the host env both set `KBCARD_TOKEN_FILE`:** the board's token now wins, changing which credential is sent — see the `docs/UPGRADE.md` v0.14.0 entry.
- **A board env that sets the board-independent `KBCARD_API` is refused, loudly.** Same inverted order, same silence: v0.4.2–v0.8.1 ignored one (as INSTALL.md documented, because `API` was frozen before the board env was sourced), while v0.8.2–v0.13.0 sourced the board env *first* and so silently **honored** it — quietly re-pointing the tool at another host. `kb_resolve_env` now returns rc 4 and names the offending file; `next-dl` no longer swallows that message (it muted stderr, leaving a bare "config incomplete" while losing both the atomic DL claim and the board's `dl_number` seed — the DL-154 re-mint collision class).
- **`board-snapshot` no longer goes dark on a host with no `~/.kanban-dev-token`.** It read one token up-front and `exit 0`'d when that file was missing, so a host using only per-board tokens rendered **nothing**. It now reads each board's token as it renders that board, honoring that board's `KBCARD_TOKEN_FILE`; a board whose token is unreadable reports itself instead of blanking the entire snapshot.
- **`board-card-start` attributes a failed card read to its actual cause.** `get()` used `curl -f`, so an unreachable API, a rejected token (401/403), and a server error were all an empty body — every one reported as **"card … does not exist"**, sending an agent to hunt a missing card instead of a broken token. Each cause is now distinct in the durable diagnostic log. (The status is returned on stdout: `$(get …)` is a subshell, so a global set inside it cannot reach the caller.)

### Changed
- **`board-card-start`: per-board tokens are a host-local opt-in, and `git config kanban.board-id` outranks `.release-pr.json`.** The hook consults a board env's `KBCARD_TOKEN_FILE` **only** when the repo's board id came from the repo-local `git config`; a board id from the committed, PR-editable `.release-pr.json` keeps the host/default token (identical to prior behavior). Reordering the two sources alone would not have closed this — they are documented mutually-exclusive populations, so the inversion only helps the population that never had the exposure; gating the *capability* on the trusted source is the actual fix. The committed value is now digits-validated (`^[0-9]+$`) before it keys a board-env lookup.
- **Reading a board env is now clean-slate** (`kb_board_env_get`): every key is unset before the file is sourced, so a key the file does not set reads as **empty** instead of inheriting whatever is in the environment. Board envs `export` their keys, so in an operator shell that sourced one board's env, that board's values are live for every later tool. Scope, precisely: stage ids are unique to one board, so an inherited id never matches another board's cards — the reachable cases are `board-snapshot` (a board env with no `KB_BOARD_ID` would render a *different* board's cards under this board's label, or abort the subshell under `set -u`) and a board env missing a required stage id (the guard would pass on an inherited value and PATCH a stage that isn't on that board). `board-snapshot` now also says so (`• <label>: (env … sets no KB_BOARD_ID)`) rather than silently rendering nothing.
- **`board-card-start` resolves its board env once**, using it for both the stage ids and the token — the two lookups were separate matchers, free to disagree about which file wins when two board envs claim the same `KB_BOARD_ID`. A duplicate `KB_BOARD_ID` now warns (which file wins is arbitrary either way; being silent about it was the defect), and the stage ids are read newline-delimited so an unset optional `KB_STAGE_HELD` cannot shift another id into its place.
- **`kb_load_host_token`'s `gated`/`unconditional` mode flag is gone**, replaced by `kb_load_host_env`. The two modes differed only because the gate conflated "source the host env" with "let the host's `KBCARD_API` win"; separating those makes one behavior serve both callers. It also fixes the gated bug where a stray ambient `KBCARD_API` skipped the host env entirely, dropping the host's `KBCARD_TOKEN_FILE` — `board-snapshot` was the only `gated` caller, so it was the only tool affected.

### Added
- **`tests/kb-board-lib-selftest.sh` + a CI job** — network-free unit checks for the shared config resolution under a scratch `HOME`: the full token ladder in all four cases, the `KBCARD_API` refusal and its message, the failure return codes, the board-env matcher (no-match, a leaked `KB_BOARD_ID` false-match, duplicates, an unparsable env), and token paths containing spaces. The ladder is a property of source *order*, which is precisely how it regressed unnoticed for five minor versions — nothing exercised it.
